# 09 — Session Skills and Guidance

Part of the [Loom Plan product vision](index.md).

This section defines what each planning session is told and how: the brief, the opening message,
the skills each step uses, the closing message, the conventions every session must produce, the
limits the guidance states, the model and effort per session kind, and how the user's own
`CLAUDE.md` files sit beside all of it. Section 07 owns the launch; this section fills in the
brief, the opening message, the skills, and the model it leaves open.

## The model in one paragraph

Every session the app starts gets three things at launch, all generated by the server from text
embedded in the `loom` binary: a **brief** appended to its system prompt (the rules every planning
session follows, plus where the project stands and what this session is for), an **opening
message** that names the step and the target document, and a **plugin** directory holding the
planning skills and the summary agents. Nothing is installed into `~/.claude`, and nothing in the
project changes. A session started for one step can move to another inside the same chat, because
every step's skill is in the plugin and the brief only names the starting point.

## What each session kind gets

| Kind                  | Brief                                    | Opening message                                             | Skills it loads                      | Model, effort (default) |
| --------------------- | ---------------------------------------- | ----------------------------------------------------------- | ------------------------------------ | ----------------------- |
| Authoring, spec steps | common brief + starting point            | step, target, the skill to load                             | the step's skill; others as it moves | opus, medium            |
| Authoring, plan steps | common brief + starting point            | step, target, the skill to load                             | the step's skill; others as it moves | opus, high              |
| Summary (background)  | summary brief                            | the summary ids to rebuild                                  | `loom-plan:summaries`                | sonnet, high            |
| Refinement (subagent) | the agent definition                     | written by the authoring session                            | none; the agent prompt carries it    | per level (below)       |
| Pressure (section 11) | `loom pressure`'s completion instruction | `/loom-plan:pressure <plan>` or `/loom-plan:address <plan>` | the command itself                   | the `[pressure]` keys   |

Section 07 lists the four kinds; the two authoring rows are one kind whose model depends on the
starting step (below, "Models and effort"); section 11 owns the pressure kind.

## Delivery

Three channels, each used for what it carries best:

| Channel                                   | Carries                                                        | Why this channel                                            |
| ----------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------- |
| `--append-system-prompt-file <brief>`     | rules that hold for every turn; the project's state at launch  | read on every turn, survives compaction, never shown in chat |
| positional prompt                         | the step, the target, the skill to load                        | starts the first turn with no input delivery (section 07)   |
| `--plugin-dir <session dir>/plugin`       | step skills, summary agents, the pressure commands             | loaded for this session only; no install, no user files     |

Section 07's launch line carries `--plugin-dir <session dir>/plugin`, and its session directory
holds `brief.md` and `plugin/`, both deleted with it.

Channels not used:

- **Installing into `~/.claude`.** Planning skills would load into every Claude Code session the
  user runs, with their descriptions resident in each one. A plugin passed per launch keeps them
  in planning sessions only. (My call.)
- **A `SessionStart` hook's `additionalContext`.** The brief would arrive as a hook message and
  again after every compaction; the appended system prompt already does both, and section 07
  registers hooks for state and the path guard.
- **Editing any `CLAUDE.md` or `.claude/settings*.json`.** `loom plan` writes nothing into the
  project outside `doc/` (section 02).

## The plugin

The plugin is generated per session from sources in the repository, embedded in the binary the
way loom embeds its other assets (`loom/src/assets/install.rs:51`, `install_all`), and written to
`<session dir>/plugin/` at launch:

```text
plugin/
  .claude-plugin/plugin.json      name "loom-plan"
  skills/brainstorming/SKILL.md   the discussion procedure (below)
  skills/kickoff/SKILL.md
  skills/vision/SKILL.md
  skills/section/SKILL.md
  skills/metaplan/SKILL.md
  skills/plan/SKILL.md
  skills/refine/SKILL.md
  skills/review/SKILL.md
  skills/knowledge/SKILL.md
  skills/summaries/SKILL.md
  agents/summary.md               document-summary rebuilder
  agents/overview.md              overview rebuilder
  commands/pressure.md            pressure sessions only (section 11)
  commands/address.md             pressure sessions only (section 11)
```

Plugin skills and agents are namespaced (`doc/loom/knowledge/conventions/guidance-channels-and-plugin-scope.md`,
"Loom Assets Outside ~/.claude Need a Plugin"), so the session sees `loom-plan:section`,
`loom-plan:summary`, and so on. The names cannot collide with the user's own skills.

The sources live at the repository root beside `skills/`, `agents/` and `commands/`, in
`plan-plugin/`. Two files are not copies: `commands/pressure.md` and `commands/address.md` are the
existing `commands/pressure.md` and `commands/address.md`, and `skills/knowledge/SKILL.md` embeds
`commands/distill.md`'s routing rules, so each text has one source. At render time the agent files
get their `model` and `effort` frontmatter from the resolved configuration (below), the way loom's
own agent files carry them (`agents/loom-senior-software-engineer.md:5-6`); the subagent tool
takes no effort parameter, so the frontmatter is the only way to set a subagent's effort.

`skills/brainstorming/SKILL.md` is adapted from the superpowers plugin's `brainstorming` skill so
it works inside loom's conventions: it writes into `doc/product/` and `doc/plans/` at the paths of
section 03, never into `docs/superpowers/`; it makes no commits; and it ends when the discussion
settles, with no hand-off to `writing-plans`. The superpowers plugin is MIT-licensed (Copyright
(c) 2025 Jesse Vincent). The license permits copying and modifying on one condition: the
copyright notice and the permission notice stay with every copy or substantial portion. The
adapted skill therefore carries the full MIT notice with that copyright line, and the source file
in `plan-plugin/` keeps it in the same place, so the embedded and the rendered copies both carry
it.

An authoring session's plugin carries the skills and the two agents; a summary session's carries
`summaries` and the two agents; a pressure session's carries only the two commands.

## The common brief

Every authoring session's `brief.md` has the same body, then a starting-point block. The body
states, in this order:

1. **What this session is.** A planning session started by `loom plan`. The user reads the chat
   in a browser and cannot see the terminal: ask in plain text, one question at a time, never with
   the question tool (section 07 denies it); slash commands run as in the terminal, except those
   the planner marks terminal only.
2. **The documents are the truth, and the next session starts cold.** Record each decision in the
   document it affects as soon as the user settles it, in the section that covers the topic.
   Nothing a later session needs may live only in this conversation (vision, "Sessions start
   cold"). The body also covers the stub and link-line duties of "Stubs, link lines and settled
   documents" below.
3. **The conventions** of section 03, "What the writing sessions keep to", quoted as a list, plus
   the step conventions below.
4. **What this session may write** (below, "Write limits").
5. **The turn-end duty.** After any turn that edited documents: run `loom plan check` and fix what
   it reports, before the reply. The duty rebuilds no summary; "Summaries after a turn" below
   says who does.
6. **The closing message** and what to do when it arrives (below).

The **starting-point block** is generated per session:

```markdown
## Starting point

Step: 2, Product spec.
Target: doc/product/<feature>/section_05.md, listed in the vision as "05 | Concept mode | The product overview, …".
Skill: loom-plan:section.

Project state at launch (it may change; re-read the files before relying on it):
- Vision: present, 12 sections listed, 4 written (01, 02, 03, 04).
- Metaplans: none.
- Plans: 6 unlisted (`PLAN-…`), 2 running, 31 done.
- Locked plan files: doc/plans/<feature>/IN_PROGRESS-PLAN-foo.md, doc/plans/<feature>/IN_PROGRESS-PLAN-bar.md.
```

The state lines come from the project checklist of section 01 at the moment of launch. They save
the session a walk of `doc/` and tell it which gaps exist around its target. (My call.)

## Steps and their skills

Each skill holds the procedure and the conventions for one kind of work. The brief names the
starting skill; the session loads another when the user moves the chat to other work ("now the
next section").

### `loom-plan:brainstorming`: the discussion procedure

Loaded by `loom-plan:vision`, `loom-plan:section` and `loom-plan:metaplan` to run their
discussion; it is no step of its own and has no row in the offers table. It holds the
brainstorming procedure (one question at a time, choices where the answer space is small, two or
three approaches with trade-offs and a recommendation before a direction settles) with loom's
changes listed above under "The plugin". The step skill that loaded it names the target document.

### `loom-plan:kickoff`: starting new work

Starts without a target file. The skill asks what the user wants to build and settles the size:
a feature with a vision, product sections, a metaplan and plans, or one standalone plan with no
product spec or metaplan. It asks before writing and proposes the size, a name and, for a feature,
sections with clear topic ownership in the proposal block the app renders.

After each turn that changes the state, the skill ends its reply with a `loom-kickoff` fenced
block containing the current size, name, problem, settled decisions, open questions and proposed
sections. Each section is settled, being worded or open. The proposal uses `proposal: true`;
the app offers Change sections for a feature and no control for a plan. The size is the offer the
kickoff began with, and the user names or renames the work in the conversation; the skill puts the
name in its block, and Taking shape only displays it. The skill keeps the taking-shape block
current.

Nothing is written under `doc/` until the user presses Write the vision or Write the plan, which
confirms the size and name and sends the exact creation grant; conversational agreement alone
grants no writes. For a feature, the skill
loads `loom-plan:vision` to write `doc/product/<feature>/index.md` and continues on that target.
For a standalone plan, it loads `loom-plan:plan` to write `doc/plans/PLAN-<slug>.md` with
`Implements: none` and briefs under `doc/plans/briefs/<slug>/`. The granted target must be new;
the skill keeps that write scope even when the loaded skill ordinarily allows related edits.

### `loom-plan:vision`: the vision discussion

Target: `doc/product/<feature>/index.md`. The feature name comes from the opening message and
also names `doc/plans/<feature>/`. The skill runs its discussion through `loom-plan:brainstorming`:
ask about the problem, the users and the goals one question at a time, offering choices where the
answer space is small; propose two or three approaches with their trade-offs and a recommendation
before settling a direction; write the vision as the discussion settles each part, never at the
end.

The vision it produces:

- a level-1 title, then the sections a reader needs to judge the direction. The default outline is
  this project's own vision: Problem, Vision, Principles, Users, Goals, Non-goals, Anti-goals,
  Specification sections, Decisions. The user may drop or add any of these.
- a `## Specification sections` heading followed by a table whose first column is the zero-padded
  section number, then the section's name and what it covers (section 01, "Vision"). This is the
  only part the app parses, and the skill says so.
- a `## Decisions` list for decisions that span sections, each naming the section numbers it
  binds.

The same skill handles the offers "fix the vision's section list" and "add this unlisted section
to the vision" (section 01): both are edits to the table.

### `loom-plan:section`: one product section

Target: `doc/product/<feature>/section_<nn>.md`, with a two-digit section number. Before writing,
the session reads the feature's vision and every section already written, which bind it;
it reads `doc/loom/knowledge/INDEX.md` and pulls only the
topics the section touches; it reads the source code a rule rests on. Then it discusses the
section's open decisions with the user through `loom-plan:brainstorming`, one at a time, and
writes as each settles.

The section it produces:

- `# <nn> — <Title>`, then the back-link line `Part of the [<vision title>](index.md).`;
- a short paragraph saying what the section covers and which other sections it leans on;
- decisions under headings that name their topic, stated plainly; a rule that rests on current
  code cites it as `path:line`;
- `(My call.)` after any decision the session made that the user, the vision or an earlier
  section did not, so a reviewer can find what nobody asked for;
- `## Open questions` for points still open, each a list item with the question, the options, and
  the session's recommendation;
- `## Out of scope for this section`, naming the section that owns each excluded topic.

These are the conventions the sections of this specification follow; the skill makes them the
default for every project. (My call.)

Guided mode drafts one section with the user. A draft-all opening names every missing section
and the teammate count; the skill uses the shared team procedure under `loom-plan:plan` below,
with `loom plan check` for the lead's consistency pass. Each teammate follows the section
conventions above and leaves unresolved choices under `## Open questions`.

### `loom-plan:metaplan`: the metaplan or its follow-ups

Target: `doc/plans/<feature>/index.md`, the feature's one metaplan (section 01). A first session
writes the file. Once it exists, a session appends new entries under a `## Follow-ups` heading in
it, creating the heading when it is absent, and leaves finished entries unchanged.

The procedure is the same `loom-plan:brainstorming` discussion, over how to cut the product into
plans: what each plan delivers, which product sections it implements, the order, and what each
needs from another. The session reads the feature's product spec, the metaplan, every plan in any
state and, for follow-ups, the done plans' run reviews (section 03), so a new entry never repeats
work that is written, running or done.

The metaplan it produces:

- a level-1 title and an introduction stating the goal and what it builds on;
- one entry per plan, a level-2 heading that names the plan file in backticks before the plan
  exists, `## <n>. <Title> (`PLAN-<slug>.md`)`, followed by three or four paragraphs: what the
  plan delivers, the product sections it implements by number, what it depends on and what
  depends on it, and its risks;
- prose headings for anything that is no entry ("Policy notes"), with no plan file name in them;
- entry order as the intended execution order.

It also handles "add this unlisted plan to a metaplan".

The `Plan follow-ups` offer opens this skill with the message `Append follow-up entries under
"## Follow-ups" in doc/plans/<f>/index.md.`, followed by the item or the text the user started it
from (section 11, "After plans complete").

### `loom-plan:plan`: one loom plan

A feature plan or draft-all session requires a settled metaplan, or one that is not settleable
because every plan is done. Draft, revised, stub-changed and upstream-changed metaplans block
the start; the offer says "Settle the metaplan first". A free chat asks the user to settle it
first. Plan follow-ups are not gated.

Target: `doc/plans/<feature>/PLAN-<slug>.md`, the slug the metaplan entry names. A standalone
plan targets `doc/plans/PLAN-<slug>.md` with `Implements: none` and has no metaplan.
The skill states the app conventions and then loads loom's own plan-writing skill,
`loom-plan-writer`, which owns every part of plan authoring. The app conventions:

- the plan's title and, directly under it, the `Implements:` line (section 03), its sections taken
  from the metaplan entry and confirmed with the user; `Implements: none` for a plan that
  implements no product section; section identifiers resolve inside `doc/product/<feature>/`;
- the metaplan entry's description is the plan's scope; a change of scope goes back into the
  entry in the same turn;
- feature briefs under `doc/plans/<feature>/briefs/<slug>/`, standalone briefs under
  `doc/plans/briefs/<slug>/`, referred to by full path;
- `loom plan verify <plan>` after writing, with every error fixed before the turn ends.

Several missing plans can be written in one chat. The session may hand each plan to its own
subagent with the metaplan entry, the conventions above, and the decisions the chat made; it
reviews each plan when the subagent returns. A draft-all opening instead uses the section and
plan skills' team mode: one authoring session leads one team of at most five teammates, fewer
when fewer documents are missing. Other authoring sessions use guided mode.

The shared team procedure:

- The lead reads the vision or metaplan, the product sections the plans implement and the settled
  decisions. It writes a short shared brief in the permitted runtime drafts directory: terms,
  decisions, which document owns each topic and the cross-references to expect.
- The lead assigns each teammate its documents and the brief, with exactly one owner per file.
  Plan teammates load `loom-plan-writer` and own their plans' brief bundles too.
- Teammates coordinate through `SendMessage` while drafting, agreeing on terms, settling overlaps
  and identifying which document owns a topic. They leave unresolved choices explicit.
- Each teammate writes only its assigned files. The run's missing documents and plan brief
  bundles are its complete write scope under `doc/`, including turn-end duties. Needed changes
  to the vision, metaplan, summaries or other files outside that scope are reported to the user.
- After every teammate finishes, the lead makes one consistency pass: terms, cross-references,
  duplicated or missing topics, `Implements:` lines and agreement between briefs and plans.
  It runs `loom plan check` for sections or `loom plan verify <plan>` for each plan, and corrects
  only files within the run's scope.
- The lead hands back a review queue in document order (the vision's table, or the metaplan for
  plans), the order the sidebar and queue use, starting at the first document. Each entry gives
  its open-question count and a note on what the pass changed, including when no changes were needed, and anything
  unresolved. It starts no second team. Stopping the team leaves written documents in place.

The draft-all launch enables in-process teammates; the bridge reads their transcripts for tokens
and document assignments and does not render their messages (sections 07 and 12). (My call.)

`loom-plan-writer` itself carries the `Implements:` line in its skeleton and its plan template
(`skills/loom-plan-writer/SKILL.md`, `references/plan-template.md`), and documents the anchored
form and the `Implements (stage:<id>):` line, so plans written outside the app carry them too
(vision, Decisions, "Product-to-plan links").

### `loom-plan:refine`: refining any document

Used for every chat that starts from a document or a passage, with no gap behind it (section 10
owns how a passage is attached). The skill: read the document and the documents it binds or is
bound by (a section's vision; a plan's metaplan entry and the sections in its `Implements:` line);
make the change the user asks for; carry the change into every document that states the same
thing, in the same turn, or record the conflict under `## Open questions` in the document that
cannot change; keep headings that summaries cite unless the change is about the heading. When an
attachment is a finding, it reads the feature's `findings.md` for the finding's About nodes and
status.

### `loom-plan:review`: reviewing the feature

Target: `doc/plans/<feature>/findings.md`, the feature's findings ledger (section 11, "After a
run"). The skill asks what the user saw (running the feature, reading code, reading a run review),
reads code and documents read-only, and appends one entry per finding in the ledger format below.
It writes nothing else.

```markdown
## F-1 Rebuild threshold ignores briefs

About: PLAN-feat-planner-03-summaries.md#stage:scheduler, section_04#rebuild-budget
Source: REVIEW-PLAN-feat-planner-03-summaries.md#open-findings (scheduler, 1a2b3c4d5e6f)
Status: open

The rebuild budget counts plan summaries but not brief changes.
```

An entry is a `## F-<n> <title>` heading with the next free number, then `About:`, optional
`Source:` and `Status:` lines, then one text paragraph. `About:` names the most specific nodes
(`section_NN#<anchor>`, `PLAN-<slug>.md#stage:<id>`, `vision#<anchor>`, `metaplan#<anchor>`).
`Status:` is `open`, `planned PLAN-<slug>.md`, `folded metaplan#<entry anchor>` or
`dismissed: <reason>`. The review skill writes `Status: open` and, as `Source:`, either no line or
`Source: review <YYYY-MM-DD>`.

### Stubs, link lines and settled documents

A document has three layers: a stub that exists before it and sets its scope, the body, and the
summary generated from the body. A product section's stub is its row in the vision's table; a
plan's stub is its metaplan entry. Every authoring skill keeps these duties:

- **Stubs.** When a body's scope moves past its stub, the session updates the stub in the same
  turn or asks. `loom-plan:vision` and `loom-plan:section` keep a vision row a true one-line scope.
  `loom-plan:metaplan` and `loom-plan:plan` keep an entry and its plan agreeing.
- **Covers.** Every metaplan entry carries a `Covers:` line directly under its heading paragraph,
  naming the most specific spec headings it delivers (`section_NN#<anchor>`, or `section_NN` when
  the plan covers the whole section). The one exception is an entry whose plan covers no section:
  it has no `Covers:` line, and `none` is not a token. A follow-up entry takes its line from the
  finding's About.
- **Implements.** A plan's `Implements:` line names headings where the plan covers part of a
  section. A stage that covers a narrower part adds `Implements (stage:<id>): section_NN#<anchor>,
  ...` in the plan's prose. The entry's `Covers:` and the plan's `Implements:` agree; a scope
  change updates both in the same turn.
- **Findings.** `loom-plan:metaplan` reads `findings.md` when planning follow-ups. Planning a
  finding: it writes the follow-up entry, then sets the finding's `Status:` line to `planned
  PLAN-<slug>.md`. Folding a finding: it edits the entry, whose plan has not started running, so its paragraphs include the
  finding, then sets `Status:` to `folded metaplan#<entry anchor>`.
- **Settled lines.** No skill writes or edits a `Settled:` line. A turn that edits a document
  holding one says so in the reply.

### `loom-plan:knowledge`: changing the knowledge base

The knowledge base is read-only in the app, and changes reach it only through `loom knowledge`
run by a chat session. This skill carries the routing and the current-truth rules of
`commands/distill.md`, with one change: the user's message names what to record, so the skill does
not read `loom memory pending`, which holds stage journals a planning session has nothing to do
with. Every write goes through `loom knowledge update`, `replace-section`, or `annotate` (and
`delete-section` only to remove a section that a heading miss appended), never a file tool.

## Recording as you go, and the closing write

Sessions record each decision as it is made, so a crash loses at most the open questions
(vision, "Sessions start cold"). The brief says what counts as recorded: the decision is written in
the document it binds, in plain words a reader without the chat understands, with the reason when
the reason is not obvious.

When an agent judges its work complete, it writes settled decisions and every open point under
`## Open questions` in the documents, then ends its final assistant text with a fenced `loom-done`
block containing `{"decisions": [...], "questions": [...]}`. Only the final block of the last
assistant text counts. The chat closes at Stop after background agents drain; a queued or delivering
user message cancels the end. The bridge sends no closing message for this end.

When the user ends the session (section 07, "Interrupt and end"), the server delivers this message:

```text
loom plan is ending this session; nobody will answer further questions.
1. Write into the documents every decision this conversation settled that is not in them yet.
2. Add every point still open as an item under "## Open questions" in the document it concerns,
   with the options and your recommendation.
3. Finish the turn-end duty for what you changed.
Then reply "Closing write done." followed by a fenced block whose info string is loom-closing,
holding one JSON object {"decisions": [...], "questions": [...]}: one plain sentence for each
decision this conversation settled and for each point it left open. Then stop.
```

The brief tells the session to expect this message and to ask nothing after it. When there is
nothing to write, the reply comes at once, with empty lists. The server delivers the closing
message only when the user sent at least one message; a chat with none ends without a model turn.
(Wording: my call.)

## Write limits

The brief states these limits so a session declines with a reason before it hits a denial;
section 12 enforces them.

- **Documents only.** Writes go under `doc/`. Code, configuration, and the project's `CLAUDE.md`
  are out of scope for a planning session.
- **Locked plans.** Files with the `IN_PROGRESS-`, `DONE-` or `RETIRED-` prefix, and everything
  under `doc/plans/<feature>/archive/` or `doc/plans/archive/`, are read-only (vision, Decisions, "Locked plans"). So is a locked
  plan's brief bundle: stages that start later in a run read the briefs committed at that time,
  so an edit would run half the plan on one version and half on another. (My call.) Asked to
  change any of these, the session says why it cannot and offers what can be done: a correction
  to running or finished work becomes a follow-up entry in the metaplan or a refinement of the spec.
- **Run reviews.** `REVIEW-*.md` files are never edited (section 03).
- **Knowledge.** Nothing under `doc/loom/knowledge/` is written with a file tool; every change
  runs through `loom knowledge`.
- **Summaries.** Nothing under `doc/loom/summaries/` is written directly; summaries change only
  through `loom plan summary seal` (section 04).
- **No git and no execution.** A planning session never stages, commits, branches, or runs
  `loom init`, `loom run`, or `loom pressure`. Committing and starting execution are the user's
  acts (vision, Decisions, "Approval"; section 11).
- **Settled marks.** A session never writes or edits a `Settled:` line; the reader's Mark settled
  action writes it (section 10, "Settling a document"). A session that edits a document holding
  one says so in its reply ("section 04 was settled; it now reads revised").

## Summaries after a turn

The authoring session leaves the summaries its turn made out of date to the server: the
background summary session rebuilds the stale and missing ones once five minutes have passed
from the end of the turn with no further change to their inputs, and the user's Rebuild press
starts one at once (section 04, "Who rebuilds what"). A reader working through open questions
and "My call" items in the chat therefore gets one rebuild after the last change, not one per
turn. The common brief and every step skill say so: the turn ends with `loom plan check`, and the
session spawns no summary subagent for what the turn changed.

The authoring plugin still carries the two agents, for the one rebuild a chat makes itself: a
summary sentence the session finds misstating a document that is right (section 10, "When the
summary is wrong"). Their definitions hold the whole procedure: rebuild only the ids given,
write only the draft file, never edit a source document, release a claim it cannot seal. Their
`model` and `effort` frontmatter is filled from section 04's configuration when the session
starts (above, "The plugin"), so a subagent runs on the level's model and effort without the
session choosing one.

## Summary sessions

A background summary session (section 04, "Background") gets the summary brief: it rebuilds
summaries and nothing else; it never asks the user anything, because nobody is there; it follows
the `loom-plan:summaries` skill, which works the batch leaves first, one `loom-plan:summary`
subagent per document summary, then the overviews itself. Its opening message lists the ids:

```text
loom plan: rebuild summaries.
Rebuild: feat-planner/product/section_03, plans/delivery-truth, overview/feat-planner/product.
Load the skill loom-plan:summaries.
```

The session runs on the overview model, since it writes the overviews itself (section 04,
"Models").

## Checking conventions: `loom plan check`

Sessions get the same reading of the tree the app has. `loom plan check [--json]` prints the
project checklist of section 01 and every convention problem the app detects in `doc/`: a vision
table the app cannot parse, a section file the table does not list, a document without a level-1
title, a metaplan entry naming no plan file, a missing, duplicate, or broken `Implements:` line, a
broken cross-reference (section 03), a brief reference that does not resolve. It reads only files,
needs no running server, and exits non-zero when the checked files have a problem. (My call: a
malformed vision table otherwise breaks detection silently until the user notices the spine;
the detector exists in the server anyway.) It sits beside `loom plan verify` and
`loom plan summary` (section 02).

## Models and effort

| Session or agent            | Default model      | Default effort     | Configuration keys                                         |
| --------------------------- | ------------------ | ------------------ | ---------------------------------------------------------- |
| Authoring, spec steps       | opus               | medium             | `[plan] spec_authoring_model`, `spec_authoring_effort`     |
| Authoring, plan steps       | opus               | high               | `[plan] plan_authoring_model`, `plan_authoring_effort`     |
| Summary (background)        | sonnet             | high               | `[plan] overview_model`, `overview_effort` (section 04)    |
| `loom-plan:summary` agent   | haiku              | high               | `[plan] document_summary_model`, `document_summary_effort` |
| `loom-plan:overview` agent  | sonnet             | high               | `[plan] overview_model`, `overview_effort`                 |
| Pressure steps (section 11) | as `loom pressure` | as `loom pressure` | `[pressure]` keys                                          |

The `[plan]` model and effort keys follow one scheme, `<role>_model` and `<role>_effort`, shared
with section 04. The user selects the background summary backend with `[plan] summary_backend`:
`claude` (default) or `codex`. The table's summary defaults apply to Claude. For Codex,
`[plan] summary_codex_model` defaults to `gpt-6.1-terra` and `summary_codex_effort` to `high`.
A Codex summary job runs `codex exec` in the background with the workspace-write sandbox
rooted at the project, plus write access to `drafts/` and `claims/` in the runtime directory
(`~/.loom/plan/<project-key>/`). It has no tmux attach link; the running rebuild's record in the
summary panel shows the job's log path (`<runtime>/codex-logs/<session>.log`) instead, and it
records no cost.

The pressure steps keep the existing `[pressure]` keys
(`doc/loom/knowledge/conventions/model-and-effort-config.md`), so a pressure run started from the
app and one started from a terminal resolve the same way.

**Spec steps** are the product-spec work: step 1 (vision), step 2 (product sections), a refinement
started on a document under `doc/product/`, and a knowledge change. **Plan steps** are step 3
(metaplans), step 4 (loom plans), a refinement started on a document under `doc/plans/`, and plan
follow-ups. A chat started by sending a message counts as a plan step when its first
attached document is under `doc/plans/`, and as a spec step otherwise. Spec steps run at medium
effort, plan steps at high: a plan fixes the stages,
files and acceptance criteria every execution session follows, and a mistake there costs a run.

Every key resolves with loom's existing precedence, per key: project `.loom/work/config.toml`
when present, then `~/.loom/config.toml`, then the built-in default
(`doc/loom/knowledge/conventions/model-and-effort-config.md`). The `[plan]` keys join the typed
key registry (`loom/src/user_config/keys.rs`), so `loom config` and the dashboard's settings
dialog edit them with no extra wiring.

One session keeps one model: the bridge marks `/model` and `/effort` terminal only (section 07),
because `/model` opens a terminal dialog and `/effort` saves the user's default for new sessions. The starting step picks the model at launch; a chat that moves to another step keeps it.

## The user's `CLAUDE.md` files and other ambient guidance

Section 07 launches with `--setting-sources user,project`, so a planning session loads what any
Claude Code session in the project loads: the user's `~/.claude/CLAUDE.md`, the project's
`CLAUDE.md`, user and project settings, their hooks, and the user's skills and plugins. Loom
neither edits nor suppresses any of it. The rules for living beside it:

- **No conflict by construction.** The brief restates nothing a `CLAUDE.md` might say
  differently about style or tooling; it covers only what is specific to planning: paths, kinds,
  write limits, the turn-end duty, the closing write.
- **Paths and conventions.** Where a `CLAUDE.md` names a different place or form for planning
  documents, the session follows the brief, since the app reads only the section 03 paths, and
  tells the user once that their instructions disagree.
- **Loom's own global rules** (the `CLAUDE.md` loom installs) already agree: plans only under
  `doc/plans/`, knowledge only through `loom knowledge`, no commits unless asked, no branches.
  Their rule that corrections become knowledge applies to facts about the code. A correction about
  the product is a decision and goes into the document it affects.
- **Loom's global hooks** run in planning sessions as in any user session (section 07 sets none of
  the stage variables). The plans-path guard agrees with section 03; the prompt-submit skill
  suggestions may name loom skills, which is harmless.
- **Third-party planning skills.** `superpowers:brainstorming` and `superpowers:writing-plans`,
  where installed, write their own design documents under `docs/superpowers/`, commit them, and
  hand off to their own plan format. The brief tells the session not to invoke them; discussions
  run through the plugin's own `loom-plan:brainstorming` (above, "The plugin"), which the app
  ships, so it does not depend on a plugin the user may not have and writes only at section 03's
  paths.
