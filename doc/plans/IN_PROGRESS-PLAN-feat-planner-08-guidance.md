# Plan: Session guidance and the `loom-plan` plugin

Implements: section_09

## Overview

Every session `loom plan` starts gets three things at launch, generated by the server from text
embedded in the `loom` binary: a brief appended to its system prompt, an opening message naming
the step and target, and a per-session `loom-plan` plugin directory holding the planning skills
and the two summary agents (`doc/product/section_09.md`). This plan writes that text, embeds it,
renders it per session kind, adds the four `[plan]` authoring keys, and switches plan 7's
session launch from its `ChecklistGuidance` to the rendered guidance, and serves each
session's brief for the chat's Brief link. Metaplan entry:
`doc/plans/metaplan-planner-ui.md`, "8. Session guidance and the `loom-plan` plugin".

It depends on plan 1 (`loom::planning` checklist, offers, project view), plan 4 (the summary
CLI the skills and agents call, the `[plan]` config section and `SummaryModels`), plan 6
(`plan_session::kind::SessionDir`) and plan 7 (the launch that consumes the brief and plugin).
Plans 9, 10 and 11 start sessions through it.

## Goals

- `plan-plugin/` at the repository root: `.claude-plugin/plugin.json` named `loom-plan`, nine
  skills (`brainstorming`, `vision`, `section`, `metaplan`, `plan`, `refine`, `retro`,
  `knowledge`, `summaries`), agents `summary` and `overview`. The pressure commands are the
  existing `commands/pressure.md` and `commands/address.md`, taken from the embedded
  `commands/` table at render time, with no second copy.
- Embedded in the binary through `loom/build/assets.rs::generate_embedded_assets` as
  `crate::assets::PLAN_PLUGIN`; never installed by `install_all`.
- `loom::planning::guidance`: per-kind plugin render into `<session dir>/plugin/` (agent
  `model`/`effort` frontmatter from resolved config), `brief.md` (common brief plus the
  starting-point block from plan 1's checklist), the opening message for every offer in section
  09's table, the summary session's brief and opening message, and the closing message.
- `GET /api/session/brief?session=<id>` for section 08's Brief link (brief, model, effort,
  label), and `PlanGuidance` installed into plan 7's `GuidanceSlot`.
- `planning::guidance::StartBlocks`, a block persisted as `<runtime dir>/config-block.json`
  that plan 11 sets after a Codex step changes session configuration; every session kind refuses
  to launch while it exists, across restarts.
- `[plan] spec_authoring_model`, `spec_authoring_effort`, `plan_authoring_model`,
  `plan_authoring_effort` in the typed key registry, so `loom config` and the dashboard's
  settings dialog edit them.
- `skills/loom-plan-writer/SKILL.md` and `references/plan-template.md` carry the `Implements:`
  line in their skeletons; `commands/pressure.md` and `commands/address.md` forbid edits to the
  `## Pressure tests` section.
- Non-goals: launching sessions (plan 7), chat rendering of opening and closing messages (plan
  9), the summary scheduler (plan 10), pressure runs (plan 11). No CLI surface is added, so no
  completions entry.

spawned and nothing is retried).

### 2. `integration-verify`

Full gate, reviewers, wiring proof: a planning session started through plan 7's spawn path has
`brief.md` and `plugin/` rendered for its kind. The operator run of one session per skill family
(vision, section, metaplan, plan) on a scratch repository is the `#[ignore]` test
`operator_session_loads_its_step_skill`, which the stage cannot run (it needs a logged-in Claude
Code); the stage records the command for the operator in `loom memory`.

### 3. `knowledge-distill`

Curates the stage memories; adds the plugin layout and render rules to the knowledge base.
