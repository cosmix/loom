# Completion Recovery

> HMAC attestation, exit_reason

## A Restart-Sync Brief Must Enumerate Every Post-Build Graph State, Not Catch-All the Rest

`sync_resumed_node` (`orchestrator/core/loop_recovery/resume.rs:22`) reconciles the in-memory
`ExecutionGraph` with on-disk stage files after a daemon restart. A brief for it that said "catch-all
for every graph state other than `WaitingForInput`/`Queued`" under-specified the real state space: a
dependent stage read from disk in directory order can still legitimately be `WaitingForDeps` right
after a restart (its dependency stage file simply hasn't been read yet), and `refresh_ready_status`
later promotes it to `Queued` on its own — but the catch-all clause raced that promotion and could
leave the graph reporting `Executing` while disk said `WaitingForDeps`, a dependents-before-dependency
ordering bug. **Prevention:** a restart-sync brief must enumerate every state the post-build graph can
legally be in for EACH stage relationship (not just "everything else"), and its test suite needs a
dependents-before-dependency ordering case specifically, not just single-stage state checks.

## Completion Evidence Attestation and Session Exit Reasons

> How a completed/parked/stalled session's disposition is proven trustworthy, and how stall is told apart from context exhaustion.

**Completion is a host job.** `loom stage complete` relays a `complete` request. The daemon queues a `Complete` host job, runs the completion checks in a child on the host, and completes the stage only when it applies a passing run (`host_verify/apply.rs`). A failed run is recorded as a failure checkpoint from the job result. The completion gates (test integrity and the review gate) run at apply through `daemon::check_completion_gates`, not in the session. See [Host Verification Jobs](verification-v2-gates.md).

**`Session.exit_reason: Option<SessionExitReason>`** (`models/session/types.rs::SessionExitReason`) is an independent field alongside `SessionStatus`, with variants `Completed`, `Crashed`, `ContextCeiling`, `Stalled`, `OperatorStop`, `CriteriaBlocked`, `Replaced`. It exists because a bare `SessionStatus` conflated "why a session stopped" with "what state it's in" — display/status/recovery code all needed the reason independently. `mark_session_terminal_reason` routes nonterminal-origin records (e.g. `Spawning`, a session killed before it ran) directly, NOT through `try_transition`, because the general state-machine transition table doesn't accept `Spawning -> ContextExhausted` as legal even though it's a real crash path — a lesson from replacing `mark_session_context_exhausted`, which set status directly: **when a new primitive replaces a writer, diff their accepted input states before assuming the general transition path covers every case the specific one did.** A stalled judge (an adjudicator that stops making progress) keeps status `Crashed` with `exit_reason: Stalled` — NOT a dedicated `Stalled` status — because judge-respawn logic keys on `Crashed` (`orchestrator/core/event_handler/stalled_judge.rs:73`); an adjudication verdict close is `Completed`/`Completed`; an accepted retirement is `Replaced`. Every full `Session { .. }` struct literal across the tree (~27 files, including ones outside any single stage's file ownership: `coherence.rs`, `monitor/parked.rs`, `inbox_drain`, e2e/integration tests) must be updated whenever this field changes shape — a `rg '\bSession \{$'` count is not proof of the true site list, since it also matches function return-type arrows like `-> Session {`; read hits before acting on a structural grep count, or let the compiler enumerate breakages after the field lands.

**Completion evidence HMAC attestation** (`loom/src/handoff/completion/attest.rs`) closes a forgery path: `handoffs/` is sandbox-writable by any agent (`commands/handoff/create.rs:26`), so an untrusted diagnostic written into a folded checkpoint could otherwise fabricate a repeated "verified" blocker and get a stage killed and parked — violating the invariant that untrusted diagnostics cannot create verified authority, complete, or park a stage. Trusted writers only — the host-job application (`host_verify/apply_rejection.rs`, which records attempt evidence and receipts) and receipt persistence — sign evidence, nonce observations and accepted receipts with a host-only key (`ATTESTATION_KEY_FILE = "completion-attestation.key"`, `attestation_key(work_dir)` in `attest.rs:20`) at `<work_dir>/completion-attestation.key`, created `0600` on first trusted use. The block refusal (`stage_service/control_block.rs`), `loop_recovery/park.rs`, `recover_hung.rs`, `monitor/completion_blockers.rs` and `status` read ONLY the attested view via `handoff/generator/lookup.rs:load_trusted_session_checkpoint`, never the raw handoff file. The key MUST persist across daemon restarts (attested checkpoints are replayed after restart) and must NOT join the daemon shutdown control-file cleanup list (`daemon/server/core.rs`, which removes `orchestrator.sock`/`.pid`, `admin.token`, `user.token`, `orchestrator.complete`) — rotating it at shutdown would silently untrust every prior trusted blocker and verified checkpoint; tokens may rotate because clients re-read them per-connection, attestations cannot. **Sandbox gap:** the stage-sandbox read deny-list (`fs/permissions/constants.rs`) names only `user.token`/`admin.token` explicitly, so the key is readable by a sandboxed agent unless it is added there. The host criteria hide it (`verify/criteria/confine_protected.rs`). Verify before trusting a new secret file's confidentiality inside a stage sandbox.

**Merge/fold tie-break on equal timestamps:** a fold over chronologically-ordered inputs (checkpoint merge, handoff merge, heartbeat observation merge) must prefer the LATER input on an exact tie, never keep-self/keep-earlier — second-precision RFC3339 timestamps make same-second updates common (e.g. a same-nonce ack-lost update and a new-fingerprint attempt landing in the same second), and a `self.latest` default on ties silently drops the newer evidence. This bit `checkpoint.rs` `merge_from` (kept `self.latest` on equal `observed_at`) and was then found again in `merge_observation` (used strict `>` while siblings already used `>=`) — the same latent mistake in three related folds. **Prevention:** any new fold over timestamped inputs needs an explicit equal-timestamp test case, and should default to `>=` (prefer incoming) not `>` (prefer self).

**`merge_session_handoff` / HandoffV2 fold:** takes `origin: Option<HandoffOrigin>` and returns `Unchanged` only when the semantic fold equals the newest exact-session artifact AND the incoming origin is `None` or equal to it (`RedBand` also compares `context_tokens`) — an `AgentCeiling` handoff that folds to an equal predecessor must still write a NEW artifact when its origin differs, because the daemon watches origin to decide what to do next; a fold that only compared content would silently swallow that write. No live-job-id field was added to `HandoffV2` — no producer of live job ids exists yet, so it would be dead data.

**Status derivation — writer-ownership-unknown vs parked-and-confirmed** (`fs/session_files/exact.rs:156`, consumed by `commands/status/`): `writer-ownership-unknown` = stage `NeedsHumanReview` + an actionable blocker for `stage.session` + that session record not yet terminal; `parked-and-confirmed` = `NeedsHumanReview` + session terminal (`ContextExhausted`/`CriteriaBlocked`). W3 escalates an unknown or surviving writer to `NeedsHumanReview` with a `review_reason` naming the session, and NEVER marks that session terminal itself — there is no durable "writer disposition" field (adding one would need its own merge/fold rules), so the session record staying non-terminal IS the signal that ownership is still unresolved; the exact-locked session record remains the sole source of truth for confirmed retirement.

**`knowledge_complete` commit selector** (`commands/stage/knowledge_complete.rs`, `handoff/completion/identity.rs`): a knowledge-distill stage runs in the MAIN checkout with no `loom/<stage>` branch, so `expected_stage_commit` resolves `Knowledge -> main checkout HEAD` (not a stage branch head). One shared selector keeps the host-job application, the monitor and status comparing the same commit for every stage type; add no second implementation.

**A stage stuck `waiting-for-input` blocks its own completion, and cannot self-resolve from inside the sandbox:** a stage file can carry status `waiting-for-input` even though the orchestrator never called `AskUserQuestion` — the session just waited between turns on background subagents. `loom stage complete` in that state still runs every acceptance criterion and goal-backward check to green, but the application refuses it with `stage ... is not executing` (`host_verify/apply.rs::validate_active_identity`). `loom stage resume <stage>` CANNOT be run from inside the stage session — `.loom/work/stages` is read-only there (EROFS on the `.tmp` write) and the daemon control socket is unreachable. **Prevention:** before the final completion attempt, check the stage file's own status (or `loom status`, which shows `?` and hints `loom stage resume`); if it reads `waiting-for-input`, the run needs the OPERATOR to run `loom stage resume <stage>` from outside the sandbox before the completion can be accepted.
