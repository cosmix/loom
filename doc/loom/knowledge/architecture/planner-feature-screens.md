# Planner Feature Screens

> Spine

A feature's screens sit under one layout route. Product contract: `doc/product/feat-planner/` (index, `section_05.md`, `section_06.md`); the design record is `web/src/plan/ui/DESIGN.md`, set by a designer worker and read by every later worker.

## Layout route and landing

`/f/:feature` is `FeatureLayout` (`feature/feature-layout.tsx`): the spine beside an `Outlet`, with no spine while `projectAtom` is null. Children (`router.tsx`): `vision` (`VisionPage`: the vision's summary page through `ConceptRoute`, then a "Read the full vision" link to its source; a feature with no vision shows the offer to start one), `metaplan` (`MetaplanPage`: the feature's one metaplan, `index.md`, as a summary page through `ConceptRoute`, key `<f>/metaplan/index`, Source one click away), `source/*` (`FeatureSourcePage`), `product[/:doc]` and `engineering[/:doc]` (`ConceptRoute`, summary pages), `run` (`run-page.tsx`) and `built` (`built-page.tsx`). There is no `pressure` route: `/f/<f>/pressure` renders "No such page". `plans/:doc`, `/new`, `/changes` and `/files/*` keep their own routes; `?step=` is gone with no redirect.

- **Landing.** `landingPath(checklist)` (`landing.ts`) sends the index route to `built` when every plan is done (`isBuilt`: the checklist's current step is `ready_all_done` and every live plan row is `done`), else to `product` when the feature has a product spec (`has_product`), else to `engineering` when a metaplan is listed, else to `vision`, which offers to start one. `BuiltPage` sends an unfinished feature to `landingPath` with a replacing `Navigate`. A path no child matches renders a `LoadState` error.
- **Source stays in the feature.** A document of a feature (its vision, `doc/product/<f>/…`, `doc/plans/<f>/…`) opens its source at `/f/<f>/source/<repo path without doc/>`, built by `featureSourceHref(feature, repoPath, options)` (`feature/source-href.ts`; `featureOfDocPath` names the owner and is null for a standalone plan). `FeatureSourcePage` refuses a path that belongs to another feature or to none ("Not a document of this feature"). `featureSourceHref` with a null feature yields the file-mode `/files/…` address, which drops the `doc/` prefix (`reviewHref` of a top-level run review in `doc/plans/` is `/files/plans/<review file>`, while a feature-owned review opens at `/f/<f>/source/plans/<f>/…`), so `sourceHref`, `sourceAddress` and `passageHref` (`concept/page-heading.tsx`, `concept/passage.tsx`) are one-line calls and the branch lives once. Source buttons and passage chips on feature pages link there; `/files/*` is the file browser and keeps its own chrome. The open-questions chip links into the feature only on summary pages: file mode keeps `/files/…#open-questions` (`review/review.test.tsx` pins it). The chat's viewed document maps `/f/<f>/source/<rel>` like `/files/<rel>` (`chat/viewed-document.ts`), so "Viewing <name>" survives the move.
- **Concept and Source are two views of one row.** The heading's Summary/Source switch is a two-state control. On a source route the spine's current row is the summary row of that document (`summaryPathnameOfSource`, `spine-model.ts`: the vision and the metaplan map to their group's target), and `spine.tsx` sets `data-view="source"` on the nav so a CSS `::after` writes "Source" under the current row (`spine.css`) without a DOM node. A non-plan file under `doc/plans/<f>/` (briefs, notes) belongs to no group and has no current row (the server classes it `Other`). `groupOfDocPath` tests the run-review name (`REVIEW_FILE`, `/^REVIEW-/`) before the plan name (`PLAN_FILE`), because `PLAN_FILE`'s optional uppercase prefix also matches `REVIEW-`; `REVIEW_FILE` is looser than the server's rule (`REVIEW-<plan slug>` directly in the plan home or `archive/`, `kinds.rs`), so a stray file named like `REVIEW-<anything>` shows as Run in the spine ([follow-up](../concerns/planner-follow-ups-followups.md#spine-and-pages)).
- **Vision page.** The vision summary has id `<f>/product/vision` (at most 8 sentences, [summary store](summary-store.md#store-layout-and-ids)); the product overview still cites the vision's sections directly, and `concept/body.rs` links a vision citation to the product overview only at overview level, so an overview citation of the vision opens straight to its passage with colour 0, while the vision summary page links to itself.
- **Metaplan page.** The metaplan summary id is `<f>/metaplan/index`; it belongs to neither overview ([summary store](summary-store.md#store-layout-and-ids)). A feature has one metaplan, so the page has no file segment and the breadcrumb reads "Metaplan". `pageKeyOfSummaryId` (`api/page-key.ts`) accepts only `<f>/metaplan/index`. Follow-ups are entries under `## Follow-ups` in that file.

## Spine

`Spine` (`spine.tsx`, model in `spine-model.ts`: `spineGroups`, `groupOfPathname`) is `nav aria-label="Feature documents"`, the only place a feature's progress is drawn. Groups are the five document steps in workflow order (`GroupId`: vision, product, metaplan, plans, run); the route's own group is always open, the others toggle and persist per feature through `projectPref("spine-expanded")`. `NextAction` (`next-action.tsx`) heads it: one sentence and at most one button; a feature with no gap shows the sentence only. The pace choice, draft-team panel and section or plan queue (`gaps.tsx`) mount above the overview through `ConceptRoute`'s `above` slot, on `product` and `engineering` only. The wire still has a Pressure test step (`steps.ts` lists no page for it); the server step mark, the home card's sr-only list and `loom plan check` report it ([follow-ups](../concerns/planner-ui-repair-followups.md#planner-redesign-follow-ups)).

- **Plan rows carry the pressure record.** A plan row (`spine-row.tsx`, `spine.css`) is the mono slug followed by two 14px glyphs on one line: the plan's state and its pressure record (`PressureBadge`, `.plan-spine__badge`; wording and icons shared with the plan page's chip through `PRESSURE_TESTED`, `NOT_PRESSURE_TESTED` and `pressureIcon` in `files/heading-parts.tsx`). The words stay in the link as `.sr-only` and as the glyph wrapper's `title`; a retired plan shows its state and no record. A done plan's state glyph (`data-state="done"`) and the tested flask light green (`spine.css`, tokens `--tone-completed`); the running roundel, the written pencil, the retired glyph and the untested gauge stay muted. The Built page and the run reviews belong to the Run group (`GROUP_OF_PAGE`, `groupOfDocPath`); a feature has one metaplan, so `metaplanChildren` is gone. A note with no glyph (a section's "not written") stays a visible word. Words beside the glyphs filled the 18rem column and cut the slug to a few letters ([the mistake](../mistakes/planner-polish.md#spine-plan-rows-lost-the-plan-name-to-their-badges)).

## Offers have one owner each, decided by id

No screen draws an offer twice. `paceOfferIds(checklist, scope)` and `pageDrawsPrimary(checklist, pathname)` (`page-offer.ts`) decide whether the page draws the checklist's primary; when it does, the spine shows the sentence only. Owners: the pace cards on an overview (only when they draw that primary's id), a missing document's page, a written plan's page (its Pressure test button for its own slug and its Start a run), the Run page for every `start_run` primary, and the **Built page** for Plan follow-ups. A queue row whose offer equals the primary reads "Next" with no button. A finished feature has no primary offer: `Plan follow-ups` (`Offer::PlanFollowUps`, id `plan-follow-ups`, offered at `CurrentStep::ReadyAllDone`, `planning/checklist/offers.rs`) is its secondary, and the Run page draws none; it only links to the Built page ("Every plan is done. See what was built"). `Plan follow-ups` is an authoring offer: its opening asks the session to append entries under `## Follow-ups` in `doc/plans/<f>/index.md`, and the checklist's step-4 gap ("Write plan <slug>") then drives the rest. The Compare spec with build and New metaplan round offers (and the `loom-plan:retro` skill) no longer exist. `PrimaryOffer` is not in the chat panel, which offers New chat and context prompts. `/new` starts the same offer for any feature that has a metaplan, done or not (`guidance/start.rs` `follow_up_start`).

## Built page

`/f/<f>/built` (`built-page.tsx`, `built-model.ts`, `built.css`) is what a finished feature lands on. It reads `checklist.built` (`BuiltView`, `plan_server/wire/checklist_built.rs`: the newest run review of each done plan, the `## Spec Conformance` items and the candidates) and draws four sections: Done plans (with each plan's review link, `reviewHref`), Spec check, Candidate follow-ups and Something else. A candidate is an open finding or an open question from those reviews with the stage and the review as its source line; **Plan this** runs the Plan follow-ups offer seeded with `followUpSeed(candidate)` (the text plus "open finding from REVIEW-x.md, stage <id>") and is described by the candidate's text (`DisabledReason` `describedBy`). A question recorded under both Spec Conformance and Open Questions is listed once, as a candidate. Something else is a free-text field whose button is the screen's one primary, labelled by the offer; with no usable offer the page links to New work. `built` is optional in the strict schema because hand-built test checklists omit it; `builtOf` supplies the empty view. The spine files the page under the Run group.

## Run reviews

`fs::plan_review::generate` writes `doc/plans/REVIEW-<plan id>.md` at the top of `doc/plans/` for every plan, feature plans included; `commit.rs` commits it. `kinds::classify` gives `DocKind::RunReview` to a review in a plan's home, its `archive/`, or the top of `doc/plans/` and `doc/plans/archive/`, and `plan_server/review/built.rs` `run_review_paths` searches the same places ([the mistake](../mistakes/planner-design-brainstorm.md#a-feature-plans-run-review-is-written-where-nothing-looks-for-it)). The review's last three sections are bullet lists in one format written by `review_item_line` (`fs/plan_review/sections.rs`): ``- **<stage name>** (`<stage-id>`): <text>``, the name escaping `\` and `*`, whitespace runs collapsed. `planning/run_review.rs` `review_items(review, ReviewSection)` is the one parser that reads them back, from the last line equal to the heading (raw memory text earlier in the review may repeat it); the writer and the parser share the heading constants.

- `## Spec Conformance`: the decisions and questions integration-verify recorded with the prefix `spec-conformance:`, prefix removed ([the duty](signal-generation.md#product-sections-block-integration-verify-only)).
- `## Open Questions`: every question recorded during the run. A `spec-conformance:` question appears here too; the Built view lists it once.
- `## Open Findings`: a suggestion whose latest receipt outcome is neither `Implemented` nor `Discarded` (none, `Promoted`, `Merged`, `Deferred`), and a note or decision whose latest outcome is `Deferred`. The latest receipt is the one with the greatest timestamp across every journal, a tie resolved by journal name order. The review is written after knowledge-distill resolves every entry, so "still pending at completion" would always be empty; the receipt outcome decides. A deferred `spec-conformance:` decision appears in both Spec Conformance and Open Findings ([follow-up](../concerns/planner-follow-ups-followups.md#run-review)).

## Wire and names

The wire has six steps (`planning/checklist.rs::Step`: Vision, ProductSpec, Metaplan, Plans, PressureTest, Run; `Step::name()` is the one display name). The `Review` step is gone, and so is `ChecklistView.title`: a feature is named by its slug in the switcher, eyebrow, cards, breadcrumbs, chat and the browser tab, and a document keeps its own heading. `wire/checklist_card.rs::card_facts` fills `metaplans` and `plan_rows` on the view (rows come from the cached `Feature.metaplans` entries, winning plan paths, `Project::text` and `latest_pressure_date`; the conversion lives in `checklist_rows.rs`). `plan_rows` are listed from the metaplan's plan headings, not a table. `wire/fixtures/*.json` have no writer test (`checklist_fixture_matches_serde_output` only reads them), so they are hand-edited when `ChecklistView` changes, and a removed `Step` variant is searched for in `loom/tests/fixtures/planning/check_schema.json`.

## Run page

`useRunRead` fetches `/api/run/state` once on arrival, and a failed read says so instead of "Nothing is running"; the server sends no `run_state` frames, so a page that shows run state names what refreshes it. `fetchRunState` (`run/use-run.ts`) applies an overtaken answer while `runStateAtom` is null, because the debug server answers one request at a time (about 5 s for `state_view`). Start a run targets the `start_run` offer's plan, else the preselected run-state plan, else the first written row, only for a written row of this feature. A plan's pressure record is drawn on its spine row and its plan page; no page lists the records. The page draws no follow-up offer: once every plan is done it shows one line linking to the [Built page](#built-page) (`plan-fine` and `plan-page__link`; no stylesheet defines `plan-page__note`).
