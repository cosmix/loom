# Planner Feature Screens

> Spine

A feature's screens sit under one layout route. Product contract: `doc/product/feat-planner/` (index, `section_05.md`, `section_06.md`); the design record is `web/src/plan/ui/DESIGN.md`, set by a designer worker and read by every later worker.

## Layout route and landing

`/f/:feature` is `FeatureLayout` (`feature/feature-layout.tsx`): the spine beside an `Outlet`, with no spine while `projectAtom` is null. Children (`router.tsx`): `vision` (`VisionPage`: the vision's summary page through `ConceptRoute`, its heading ledger holding a Source row with a "Read the full vision" button; a feature with no vision shows the offer to start one), `metaplan` (`MetaplanPage`: the feature's one metaplan, `index.md`, as a summary page through `ConceptRoute`, key `<f>/metaplan/index`, Source one click away), `source/*` (`FeatureSourcePage`), `product[/:doc]` and `engineering/:doc` (`ConceptRoute`, summary pages; the product overview draws the section gaps and Settle all specs), `coverage` (`CoveragePage`) and `findings` (`FindingsPage`), the two [trace pages](planning-trace.md#coverage-and-findings-pages). `engineering` and `run` are redirects to `metaplan`: there is no engineering overview, and the metaplan page, the Plans home, draws the Run and Findings rows (see [Run and Findings rows](#run-and-findings-rows)), the plan gaps, pace cards and queue. There is no `pressure` or `built` route: `/f/<f>/pressure` and `/f/<f>/built` render "No such page". `plans/:doc`, `/new`, `/changes` and `/files/*` keep their own routes; `?step=` is gone with no redirect.

- **Landing.** `landingPath(checklist)` (`landing.ts`) sends the index route, whether or not every plan is done, to `product` when the feature has a product spec (`has_product`), else to `metaplan` when a metaplan is listed, else to `vision`, which offers to start one. The header's feature switcher (`header/feature-switcher.tsx`) links each feature to `/f/<f>`, so the feature name lands by the same rule. A path no child matches renders a `LoadState` error.
- **Source stays in the feature.** A document of a feature (its vision, `doc/product/<f>/…`, `doc/plans/<f>/…`) opens its source at `/f/<f>/source/<repo path without doc/>`, built by `featureSourceHref(feature, repoPath, options)` (`feature/source-href.ts`; `featureOfDocPath` names the owner and is null for a standalone plan). `FeatureSourcePage` refuses a path that belongs to another feature or to none ("Not a document of this feature"). `featureSourceHref` with a null feature yields the file-mode `/files/…` address, which drops the `doc/` prefix (the source of a top-level run review in `doc/plans/` is `/files/plans/<review file>`, while a feature-owned review opens at `/f/<f>/source/plans/<f>/…`), so `sourceHref`, `sourceAddress` and `passageHref` (`concept/page-heading.tsx`, `concept/passage.tsx`) are one-line calls and the branch lives once. Source buttons and passage chips on feature pages link there; `/files/*` is the file browser and keeps its own chrome. The open-questions chip links into the feature only on summary pages: file mode keeps `/files/…#open-questions` (`review/review.test.tsx` pins it). The chat's viewed document maps `/f/<f>/source/<rel>` like `/files/<rel>` (`chat/viewed-document.ts`), so "Viewing <name>" survives the move.
- **Concept and Source are two views of one row.** The heading's Summary/Source switch is a two-state control. On a source route the spine's current row is the summary row of that document (`summaryPathnameOfSource`, `spine-model.ts`: the vision and the metaplan map to their group's target), and `spine.tsx` sets `data-view="source"` on the nav so a CSS `::after` writes "Source" under the current row (`spine.css`) without a DOM node. A non-plan file under `doc/plans/<f>/` (briefs, notes) belongs to no group and has no current row (the server classes it `Other`). `groupOfDocPath` puts a run review (`REVIEW_FILE`, `/^REVIEW-/`) and a plan (`PLAN_FILE`) in the Plans group; `PLAN_FILE` alone misses `REVIEW-DONE-PLAN-`, whose prefix has no dash. `REVIEW_FILE` is looser than the server's rule (`REVIEW-<plan slug>` directly in the plan home or `archive/`, `kinds.rs`), so a stray file named like `REVIEW-<anything>` shows in Plans ([follow-up](../concerns/planner-follow-ups-followups.md#spine-and-pages)).
- **Vision page.** The vision summary has id `<f>/product/vision` (at most 8 sentences, [summary store](summary-store.md#store-layout-and-ids)); the product overview still cites the vision's sections directly, and `concept/body.rs` links a vision citation to the product overview only at overview level, so an overview citation of the vision opens straight to its passage with colour 0, while the vision summary page links to itself.
- **Metaplan page.** The metaplan summary id is `<f>/metaplan/index`; it belongs to neither overview ([summary store](summary-store.md#store-layout-and-ids)). A feature has one metaplan, so the page has no file segment and the breadcrumb reads "Metaplan". `pageKeyOfSummaryId` (`api/page-key.ts`) accepts only `<f>/metaplan/index`. Follow-ups are entries under `## Follow-ups` in that file.

## Spine

`Spine` (`spine.tsx`, model in `spine-model.ts`: `spineGroups`, `groupOfPathname`) is `nav aria-label="Feature documents"`, the only place a feature's progress is drawn. Groups are the four document steps in workflow order (`GroupId`: vision, product, metaplan, plans); the route's own group is always open, the others toggle and persist per feature through `projectPref("spine-expanded")`. It draws no offer. `SpineHead` (`trace/spine-head.tsx`) heads it: the trace's top attention item as one "Next" link ([head](planning-trace.md#browser)), none for a Help scene (`sample`). The pace choice, draft-team panel and section or plan queue (`gaps.tsx`) mount above the page through `ConceptRoute`'s `above` slot, on the product overview (section gaps) and the metaplan page (plan gaps) only. The wire still has a Pressure test step (`steps.ts` lists no page for it); the server step mark, the home card's sr-only list and `loom plan check` report it ([follow-ups](../concerns/planner-ui-repair-followups.md#planner-redesign-follow-ups)).

- **Rows and the trace.** The Product spec group lists its overview and one row per section; the Plans group lists its overview and one row per plan. Each group closes with its ledger: Coverage is the last child of Product spec and Findings the last child of Plans (`instrumentChild`, `feature/spine-instruments.ts`), each led by its `INSTRUMENT_GLYPHS` icon (`ui/glyphs.tsx`, shared with the Help topics) and reading the trace's figures (headings covered of total; open findings in `--tone-warning`), with no reading until the trace loads. `GROUP_OF_PAGE` maps `coverage` to the product group and `findings` to the plans group. A run review (`REVIEW-*`) belongs to Plans too, with no row of its own. `spineGroups(checklist, trace)` gives each row one leading glyph (`rowGlyph`, below); the vision and metaplan rows carry theirs on the group (`SpineGroup.glyph`). The metaplan group owns the shared metaplan target: the Plans head links there without receiving `aria-current`, so selection and route mapping tell the two heads apart. A group head shows amber "Not all settled" only once the trace has loaded; with no trace no head or row claims Draft or a settle word. Group counts are the server checklist's ("12/12", "3/14"), not counts of settled sections. Without the trace (not loaded yet, or a Help scene) no row claims "Draft" or a settle word.
- **One glyph per row.** `rowGlyph` picks it once, by precedence: a retired plan, a running plan, attention, settled, a done plan, not written, else draft. Attention (revised, stub changed, upstream changed) is the amber seal in `--tone-warning`; a settled row's seal and a done plan's check are green (`--tone-completed`); not written is a dashed circle; draft an empty seal; a retired plan the archive glyph. The kind is `data-glyph` on `.plan-spine__glyph` (`spine-row.tsx`); the glyph is `aria-hidden`, its word is the `title` and a `.sr-only` word after the name, so a row's accessible name still reads "Settled", "Changed since you settled it", "Running" or "Done". A running plan draws `LiveDot` (`ui/activity-glyphs.tsx`, through `spine-row.tsx` and the `running` entry in `ui/glyphs.tsx`); the roundel belongs only to the header activity pill ([busy signs](planner-web-shell.md#roundel-and-busy-text)).
- **Short slugs.** A plan row shows `shortSlug(feature, slug)` (`trace/model.ts`: the slug without its `<feature>-` prefix) in mono, with the full slug in `title`. The pressure record is not on the row (no flask, no badge): it stays as `.sr-only` words (`PressureWord`) and the plan page draws it ([the mistake](../mistakes/planner-polish.md#spine-plan-rows-lost-the-plan-name-to-their-badges)). The current row keeps `aria-current="page"` and has no gutter dot.
- **`settleable` gates every settle mark.** `TraceDoc.settleable` (`planning/trace/build/docs.rs`) is true for a written, unlocked document, except the vision and metaplan of a feature whose plans are all done; a stub, a locked plan and that finished vision or metaplan carry no settle state, gap, control or count. Product sections stay settleable because a follow-up plan can still change what they promise. Every web reader goes through `shownSettle`, never `doc.settle` ([model](planning-trace.md#the-trace-model)).

## Offers have one owner each, decided by id

No screen draws an offer twice. The spine draws no offer. Owners: the pace cards on an overview (`paceOfferIds`, `page-offer.ts`), a queue row (`queue.tsx`; it reads "Next" with no button only when a pace card draws its offer), a missing document's page and an empty state's offer (`concept/empty-states.tsx`), a written plan's page (its Pressure test button and its Start a run), the metaplan page's `RunPanel` for every `start_run` primary, and the Findings page for `review_feature` (its header button, the screen's primary only when the checklist's primary is that offer) and for `address_findings` (its header button, built from the trace by `addressOffer`, `trace/findings-model.ts`). `plan_follow_ups` is not the Findings page's: no finding card carries a planning action, and the follow-up candidates are the actionable ledger entries only ([candidates](#follow-up-candidates)). A `pressure_test` offer is drawn only on its own plan's page; `fix_vision_table` has no screen. A finished feature has no primary offer: `Plan follow-ups` (`Offer::PlanFollowUps`, id `plan-follow-ups`, offered at `CurrentStep::ReadyAllDone`, `planning/checklist/offers.rs`) is its secondary, and `Review the feature` (`Offer::ReviewFeature`, id `review-feature`, secondary on any feature with a running or done plan, `extras`) is secondary on every such feature. `/new` starts `Plan follow-ups` for any feature that has a metaplan, done or not, through Follow-up with the feature picked (`guidance/start.rs` `follow_up_start`). `Plan follow-ups` is an authoring offer: its opening asks the session to append entries under `## Follow-ups` in `doc/plans/<f>/index.md`, and the checklist's step-4 gap ("Write plan <slug>") then drives the rest. `Review the feature` is an authoring offer with skill `loom-plan:review` (`plan-plugin/skills/review/SKILL.md`) and a null wire target: it opens one interactive authoring session that imports and verifies findings into `doc/plans/<f>/findings.md` (its opening target, `guidance/opening.rs`). `Address the findings` (`Offer::AddressFindings`, id `address-findings`) is never in a checklist; it starts a team session ([Address Run](planning-trace.md#address-run)). The Compare spec with build and New metaplan round offers (and the `loom-plan:retro` skill) do not exist. `PrimaryOffer` is not in the chat panel, which offers New chat and context prompts.

## Follow-up candidates

`ChecklistView.candidates` (`plan_server/wire/checklist_candidates.rs`, `ledger_candidates`) lists the actionable entries (open and verified by the trace's checks, `TraceFinding::actionable`) of the feature's findings ledger, `doc/plans/<f>/findings.md`, in ledger order. An entry the run-review import wrote is a finding or a question by its `Source:` anchor, names its stage, and names the newest run review of its plan (`newest_review`: the greatest Generated stamp among `run_review_paths`, else the last path); a hand-written entry names `review` as its stage and the ledger as its source. `/new`'s Follow-up lists the picked feature's candidates as toggle pills (`FollowUpSuggestions`, `new/kickoff-starters.tsx`): a pill puts `followUpSeed(candidate)` (`new/follow-up-features.ts`: the ledger id, the first line of the text, and "open finding from REVIEW-x.md, stage <id>") on a line of its own in the field. `candidates` is optional in the strict schema because hand-built test checklists omit it; `followUpFeatures` reads an absent list as empty.

## Run reviews

`fs::plan_review::generate` writes `doc/plans/REVIEW-<plan id>.md` at the top of `doc/plans/` for every plan, feature plans included; `commit.rs` commits it. `kinds::classify` gives `DocKind::RunReview` to a review in a plan's home, its `archive/`, or the top of `doc/plans/` and `doc/plans/archive/`, and `plan_server/review/built.rs` `run_review_paths` searches the same places ([the mistake](../mistakes/planner-design-brainstorm.md#a-feature-plans-run-review-is-written-where-nothing-looks-for-it)). The review's last three sections are bullet lists in one format written by `review_item_line` (`fs/plan_review/sections.rs`): ``- **<stage name>** (`<stage-id>`): <text>``, the name escaping `\` and `*`, whitespace runs collapsed. `planning/run_review.rs` `review_items(review, ReviewSection)` is the one parser that reads them back (`ReviewSection` names Open Questions and Open Findings, the two sections the findings import reads), from the last line equal to the heading (raw memory text earlier in the review may repeat it); the writer and the parser share the heading constants.

- `## Spec Conformance`: the decisions and questions integration-verify recorded with the prefix `spec-conformance:`, prefix removed ([the duty](signal-generation.md#product-sections-block-integration-verify-only)).
- `## Open Questions`: every question recorded during the run. A `spec-conformance:` question appears here too.
- `## Open Findings`: a suggestion whose latest receipt outcome is neither `Implemented` nor `Discarded` (none, `Promoted`, `Merged`, `Deferred`), and a note or decision whose latest outcome is `Deferred`. The latest receipt is the one with the greatest timestamp across every journal, a tie resolved by journal name order. The review is written after knowledge-distill resolves every entry, so "still pending at completion" would always be empty; the receipt outcome decides. A deferred `spec-conformance:` decision appears in both Spec Conformance and Open Findings ([follow-up](../concerns/planner-follow-ups-followups.md#run-review)).

## Wire and names

The wire has six steps (`planning/checklist.rs::Step`: Vision, ProductSpec, Metaplan, Plans, PressureTest, Run; `Step::name()` is the one display name). The `Review` step is gone, and so is `ChecklistView.title`: a feature is named by its slug in the switcher, eyebrow, cards, breadcrumbs, chat and the browser tab, and a document keeps its own heading. `wire/checklist_card.rs::card_facts` fills `metaplans` and `plan_rows` on the view (rows come from the cached `Feature.metaplans` entries, winning plan paths, `Project::text` and `latest_pressure_date`; the conversion lives in `checklist_rows.rs`). `plan_rows` are listed from the metaplan's plan headings, not a table. `wire/fixtures/*.json` have no writer test (`checklist_fixture_matches_serde_output` only reads them), so they are hand-edited when `ChecklistView` changes, and a removed `Step` variant is searched for in `loom/tests/fixtures/planning/check_schema.json`.

## Run and Findings rows

The metaplan page, the Plans home, carries the run in its heading's ledger (`concept/header-ledger.tsx`; `MetaplanPage` in `feature/document-page.tsx` passes Run, Settling and Findings as `ConceptRoute`'s `ledger` and the Plans gaps as `above`). `RunRow` (`feature/run-panel.tsx`) holds the run line (`runSentence`, `run-scope.ts`) with its glyph, the Codex notice under it, one Start a run button (a blocked start draws its reason as a lock line from `useStartRunReason`, `run/plan-run-actions.tsx`) and the dashboard link. `FindingsRow` reads "N open" with an "Open findings" link and is drawn only once the ledger holds a finding. Each ledger row is a `<section>` named by its label, so tests find it with `getByRole("region", { name: "Run" })`; a test that mocks `ConceptRoute` renders both `ledger` and `above`. `useRunRead` fetches `/api/run/state` once on arrival, and a failed read says so instead of "Nothing is running"; the server sends no `run_state` frames, so a panel that shows run state names what refreshes it. `fetchRunState` (`run/use-run.ts`) applies an overtaken answer while `runStateAtom` is null, because the debug server answers one request at a time (about 5 s for `state_view`). Start a run targets the `start_run` offer's plan, else the preselected run-state plan, else the first written row, only for a written row of this feature (`startControl`); the button is the screen's primary only when the checklist's primary is the `start_run` offer. A plan's pressure record is drawn on its spine row and its plan page; no page lists the records. The panel draws no follow-up offer: once every plan is done its line reads "Every plan is done."

## Modes and ownership

The file-mode editor (`web/src/plan/editor/`) has two modes over one CodeMirror document: live preview (default) and source. `createSourceEditor` (`codemirror.ts`) puts the mode in `modeCompartment`; `setMode` is one `reconfigure`, so text, selection and undo history survive a toggle. `modeExtension` returns `lineNumbers()` for source and `livePreview(...)` plus the `cm-live-preview` editor class for preview, so line numbers belong to Source only. `baseExtensions` holds no line numbers; the merge and diff views add them through `withLineNumbers` and always show source.

`editor-mode.ts` remembers the mode per project under `storageKey(project_key, "editor-mode")`: `readEditorMode` answers `preview` for no project key, blocked storage or an unknown value, and `writeEditorMode` writes nothing in those cases. `edit-body.tsx` holds the mode state and writes it on every toggle. The toolbar (`edit-toolbar-controls.tsx` `FormatButtons`) calls `SourceEditorHandle.format(command)`, which runs a `FormatCommand` from `md-commands.ts` and refocuses the view.

## Live preview decorations

`live-preview.ts` exports `livePreview(options)`: `inlinePreview` (a `ViewPlugin`), `fenceField` (a `StateField`) and `followLinks`. It draws over the Markdown source and changes the document only when a task box is clicked (`toggleTask`), so an untouched save writes the bytes the editor holds.

- **Reveal rule.** `hideRun` hides a marker run (emphasis stars, heading hashes, link brackets and destination) unless a selection range touches that line (`touches`, inclusive at both ends); the cursor line shows its raw source. A run never spans lines. Decorations rebuild on a doc, selection or viewport change and when the syntax tree grows (the parse is incremental, so a long document decorates as it parses).
- **Widgets.** `SpanWidget` draws the bullet, the quote bar and the fence's language label; `CheckboxWidget` draws a task box that carries its own click listener (widget DOM ignores editor events) and cancels the browser's toggle, so a read-only editor keeps the document's state.
- **Block styling.** Heading lines take `cm-lp-h1..6`, table lines `cm-lp-mono` with dimmed pipes, fenced code `cm-lp-code[-first|-last]` lines. The closing fence is hidden from the previous line's end (`[prevLine.to, closeLine.to]`), not through its own break: a replace that merges lines keeps only the first line's line decorations, so hiding through the break made the next line (a heading) inherit the code ground.
- **Mod-click.** `followLinks` calls `onFollowLink(href)` for Ctrl or Cmd plus a primary-button click on a `Link` or `Autolink` URL (an `Image` is skipped). `hrefAt` returns null for a `.cm-line` or `.cm-content` target, because a browser targets the line element for unstyled text, and resolves the syntax node at side 1 only, so text that starts where a link ends never reaches back into it. `destination` strips `<...>` and backslash escapes the way the reading view parses them. `useFollowLink` (`edit-body.tsx`) sends the href through `resolveLink`: a `doc` or `anchor` target navigates with `toAddress`, an `external` one opens a new tab with `noopener,noreferrer`, and `outside` or `text` does nothing ([markdown rules](../conventions/plan-web.md#markdown-renderer-rules)).
- **Typography.** `theme.ts` sets `fontVariantLigatures: "none"` for source and preview alike: Inter's `calt` drew `-->` of an HTML comment as an arrow.
- **Language.** `markdown({ base: markdownLanguage, codeLanguages })` (GFM: tasks, strikethrough, tables, autolinks). The merge and diff views share the base, so `TableHeader` highlights as a heading and `TaskMarker` as an atom there.

## Formatting commands

`md-commands.ts` (`inline`, `togglePrefix`, `link`, `quote`, `heading`, `codeBlock`, `table`, `formatCommand`, `formatKeymap`, `saveKeymap`) edits the selection as one transaction, so one undo reverses it. Every formatting command returns false in a read-only state; `formatKeymap` binds Mod-b, Mod-i and Mod-k and returns true even when the command did nothing, so the browser's own Mod-k and the default keymap's Mod-i never run. `saveKeymap` (Mod-s to `onSave`) lives in this file only to keep `codemirror.ts` under 400 lines and does not refuse read-only. `heading` cycles none, 1, 2, 3, none.

## Lazy loading

`EditMode` is a `React.lazy` chunk (`web/src/plan/files/reading-column.tsx`) inside a `Suspense` whose fallback is the "Loading editor" `role="status"` line, the pattern help uses. The chunk is `edit-mode.js` (about 21 kB); `plan.js` stays near 412 kB, under the 500 kB warning ([the bundle rule](../conventions/plan-web.md#live-preview-editor-rules)). A failed `edit-mode.js` fetch is not retried ([concerns](../concerns/planner-ui-repair-followups.md#live-preview-editor-reviewer-suggestions)).

## Failure and validation surfaces

SourceEditor and MergePanel show Aurora ErrorPanel inside role=alert when the lazy editor cannot load, retaining reload guidance. ValidationPanel groups errors into an error HazardPanel, and warning buckets into one warning HazardPanel; notes stay outside the hazards. Source-line jump buttons and the explicitly offered Save with errors action retain their behavior. In file mode, plan/validation-list.tsx applies the same grouping to the document heading validation popover, preserving stage links and location text. plan/stages-panel.tsx wraps unreadable YAML in ErrorPanel and keeps the raw metadata visible; reading-column.tsx wraps a failed document refresh in a warning HazardPanel with Retry and keeps the earlier document text visible. Stripes stay in the header; body text remains neutral. The backend unavailable modal is documented in planner-web-shell.md#backend-unavailable-modal.

## Planner Uploads and Kickoff Drafts

Two stores outside the repository, both under the planner's runtime directory, with the commands and transcript rules that use them. Web side: [Planner Web Shell](planner-web-shell.md).

## Upload route

`POST /api/attachments` (`plan_server/uploads/`, installed by `routes::install_all`) takes a raw body and stores it under its content hash. Rules:

- **Role.** The holder, and any browser while nobody holds authoring (`HolderOrTake`): a fresh New work page attaches before its first message takes authoring, and a `Holder` rule would refuse that upload. Another browser's hold, read-only mode and `stopping` still refuse it.
- **Types.** `plan_session::attachments::stored::MEDIA_TYPES`: `image/png`, `image/jpeg`, `image/gif`, `image/webp`, `application/pdf`, `text/plain`, `text/markdown`. The gate refuses a wrong `Content-Type` (415) and an oversized `Content-Length` (413) before it reads the body; the handler then checks the bytes against the declared type (422): magic bytes for images and PDF, UTF-8 for text.
- **Caps.** 10 MiB a file (`MAX_UPLOAD_BYTES`); 256 MiB for the store (`MAX_STORE_BYTES`), past which the answer is 507 with a one-line reason; the whole body must arrive inside the request's 30 s budget (`request.rs` `BODY_TIME_LIMIT`).
- **Storage by content.** `<runtime>/attachments/<first 16 hex of sha256>.<ext>` plus a sidecar `<id>.json` (name, type, size, `stored_at`; read back up to 4 KiB). The same bytes uploaded twice are one file. The directory is 0700 and every write goes through `safe_fs` (temp name opened `O_CREAT|O_EXCL|O_NOFOLLOW`, renamed into place), ordered against the cap check, `touch` and the sweep by one process-wide lock. The runtime directory is not created by `start_with_routes` (only `run()` does), so the handler calls `create_runtime_dir` before the first write.
- **Names.** The display name is the `name` query parameter (percent-encoded, at most 1024 decoded bytes, `MAX_PARAM_BYTES`); the client cuts it to 120 code points before encoding (`attachments/upload.ts`). One `clean_name` in `attachments/stored.rs` strips control and format characters (`context/format_chars.rs`) for both the upload check and the resolver. A name is never used in a path.
- **Answer.** `{id, name, media_type, bytes}`. A chat command names the file by id (`AttachmentInput` kind `file {id, name}`); `plan_session::attachments::resolve_input(project, attachments_dir, input)` maps the id to the absolute path, and an unknown or malformed id is refused. `resolve(project, DocumentAttachmentInput)` keeps its signature for documents, so the document tests are unchanged. The client never sends a path and never receives one.
- **What the session sees.** The delivered block names the absolute path, media type, size and name, and the session reads the file with Read. The planning session sandbox has a read-only grant on `<runtime>/attachments` (`ensure_runtime_grants`, `plan_session/sandbox/mod.rs`, runs before every launch; contract `guard_allows_reads_of_attachments_and_denies_writes`). The transcript chip carries `{id, name, media_type, bytes}`; a Read or Grep tool row of a stored file is shown as `attachment <id>.<ext>` (`transcript/tools.rs` `display_path`), never the runtime path.
- **Expiry.** `uploads::install` sweeps files older than 30 days (`KEEP_SECONDS`) at every server start. Re-uploading a stored file refreshes its `stored_at` (`uploads::touch`), and so does every write of a draft that references the file, so an unfinished draft's attachments live as long as the draft. The sweep opens the store with `safe_open_dirfd` and removes through `safe_remove_in_workdir`; it does not follow a symlinked store directory.

## Kickoff drafts

A kickoff survives its session as `<runtime>/kickoffs/<session id>.json` (`plan_server/chat/drafts.rs`, commands in `draft_cmd.rs`). The session id must be a lowercase hyphenated uuid, because it becomes a file name.

- **Shape.** `Draft {session, started_at, updated_at, size, finished, messages, shape, attachments, target, live}`: `size` is the size the kickoff was started with, copied from the session's `KickoffScope` (written at start by `team.rs` `prepare_scope` from the offer: `kickoff` is a feature, `kickoff-small` a standalone plan) and never changed by the agent's `loom-kickoff` block; `finished` is true when the agent's done fence ended the session; `messages` are the user's typed texts (at most 40, 4096 bytes each, cut at a character boundary with `[…]`; the first and the newest are kept); `shape` is the agent's last `KickoffShape`, and its `name` is the draft's name (`Draft::name()`); `attachments` are the start command's inputs as the browser sent them (at most 10); `target` is the confirmed document's path, set by `confirm_kickoff`. A file over 256 KiB is not read and none is written larger; a file that fails to parse is skipped with a warning and left in place.
- **Writes.** At start, on every shape change, on every user send, on rename and on confirm, and again with `live: false` (and `finished` when the done fence ended it) on `BridgeEvent::Ended`, which carries the end cause. Every read-modify-write holds `ChatState::drafts`, because the bridge listener, the dispatch thread and the `Ended` handler all write.
- **`live` is computed on read.** A view's `live` is the stored flag AND the bridge's current chat session being this one, so after a restart every draft reads `live: false`; the stored flag is never read alone.
- **Landing needs a finished session.** `store.rs` `landed` is true when a locked spelling of the confirmed plan exists (`IN_PROGRESS-`, `DONE-`, `RETIRED-`, or any spelling under `archive/`: it went into execution), or when `finished` is true and the confirmed document exists. A document that exists while the session did not finish is half-written work: the draft stays under Unfinished so it can be continued or deleted. A landed draft is deleted on the store's next read or write (the change is published to open tabs) and never listed. Ended drafts older than 30 days go at server start.
- **Wire.** `GET /api/kickoffs` answers `{drafts: [KickoffDraftView]}`, `KickoffDraftView {session, name, size, problem, started_at, updated_at, live}`; a `kickoff_drafts` socket message carries the same list (both schema arms and a fixture, as every `PlanMessage` variant needs). `GET /api/kickoffs/<session>` (`drafts/handlers.rs` `detail`) answers `KickoffDraftDetail {draft, shape, messages, written, committed}`: `written` lists the files the confirmed grant created that exist now (document first) and `committed` says whether HEAD holds any of them; a target the grant check refuses lists nothing.
- **Commands.** There is no rename command: the user names the work in the conversation and the agent's `loom-kickoff` block carries the name. `confirm_kickoff {size, name}` is sent only by the Write button (`new/write-kickoff.tsx`) while `target` is null; it arms the write grant and tells the agent the user asked for the write now (`kickoff_cmd.rs` `confirmation`, which takes its paths from `scope::kickoff_target`). `continue_kickoff` starts a new kickoff whose opening carries the draft: the shape's name (in the opening text, "The work is named `<name>`."), the size, the whole shape and the attachments that still resolve (one that no longer does is named in the opening as no longer available); the replacement draft is written before the old one is deleted, and a refused or failed start leaves the old draft as it was.
- **Set aside.** `set_aside_kickoff {session, now}` (`draft_cmd.rs` `set_aside`) ends the running kickoff and keeps its draft. An unconfirmed kickoff (no `target`) has nothing to write and `now: true` means stop at once: both tear down (`EndMode::Teardown`). A confirmed one goes through `Bridge::close_within` (`bridge/end_plan.rs`) with `SET_ASIDE_BOUND` (60 s): it interrupts the running turn so the closing message reaches an idle agent, then plans a final write bounded by that value through `Bridge::end_within`. Once an end is planned the running turn is its closing turn and is left alone; a repeated request only lowers the bound, and a later `now: true` hardens it to a teardown. The 600 s `final_write_bound` stays for ordinary chat ends and server drain. While the session is ending the web notice reads "is being set aside…" and offers Stop now (`new/draft-view.tsx`).
- **Discard and Delete.** `discard_kickoff {session, delete_files}` (`draft_cmd.rs` `discard`) holds `ChatState::starting()`, so it orders against a Continue of the same draft, and refuses a live draft ("Set it aside first"). Continue takes authoring like a start (`TakeIfFree`) and discard allows no holder, because an ended kickoff has already released the starter's authoring; both refuse another browser's hold. Without `delete_files`, a draft whose confirmed target has files on disk is refused with `WROTE_FILES`; the web page lists `written` first and offers Delete for good. With `delete_files`, `drafts/delete.rs` `remove_written` derives the files from the draft's stored target, checked byte for byte against `scope::kickoff_target(size, name)` (the request names no path), and refuses a target of another size than the draft's. It refuses an executing plan (a locked spelling of the document, taken from `store.rs` `locked_spellings`), unlinks the document, then removes the plan's bundle through `fs/safe_fs/write/tree.rs` (`safe_remove_tree_in_workdir`, at most 64 levels deep, one open descriptor per level). A bundle removal that fails after the document went ends its error with "is already deleted"; the draft stays so a retry finishes the removal.

## The opening in the transcript

The kickoff's first user record is one `<pasted_content>` item holding the generated guidance and the typed text (`guidance/provider.rs` joins them with a blank line). The bridge shows each once, and the seam is a file: when an offer opening is joined with typed text, the guidance provider writes the typed part to `SessionDir::opening_typed()` (`opening-typed.txt` in the session directory, 0600, `write_opening_typed` in `guidance/provider.rs`), and `Session::configure` reads it (`read_opening_typed`, `bridge/start.rs`; absent, unreadable or blank means one item) into `Opening.typed`, so the split never comes from searching the joined text. The opening is then sent as two items, the guidance (a collapsed origin item) and the typed text (a visible user item), and the one recorded prompt replaces both (`plan_session/transcript/opening.rs`). `isMeta` records, which Claude Code writes after a Skill tool result with the skill body as list content, are skipped before their text is used (`records.rs`); Skill tool rows never render. The `loom-kickoff` fence the assistant ends each reply with is for the server only, and `withoutKickoffFence` (`web/src/plan/chat/kickoff-fence.ts`) drops it from assistant text, streaming included ([the mistake](../mistakes/planner-review-fixes.md#a-structured-block-and-a-composite-opening-were-never-replayed-through-the-transcript)).

A sent item and its recorded prompt can arrive in either order: the `UserPromptSubmit` hook confirms delivery (`set_delivery` makes `s-N` Delivered) before the plain human record, so the mapper (`opening.rs`) matches a Delivered sent item as well as a pending one, or both would stay ([the mistake](../mistakes/planner-review-fixes.md#a-sent-item-and-its-record-arrived-in-the-opposite-order)). In the browser, one `commandPendingAtom` guards the Size control and the proposal against a double dispatch.
