# Planner Feature Screens

> Spine

A feature's screens sit under one layout route. Product contract: `doc/product/feat-planner/` (index, `section_05.md`, `section_06.md`); the design record is `web/src/plan/ui/DESIGN.md`, set by a designer worker and read by every later worker.

## Layout route and landing

`/f/:feature` is `FeatureLayout` (`feature/feature-layout.tsx`): the spine beside an `Outlet`, with no spine while `projectAtom` is null. Children (`router.tsx`): `vision` (`VisionPage`: the vision's summary page through `ConceptRoute`, then a "Read the full vision" link to its source; a feature with no vision shows the offer to start one), `metaplan[/:file]` (`MetaplanPage`: the metaplan's summary page through `ConceptRoute`, key `<f>/metaplan/<stem>`, Source one click away; the bare route shows `index.md` through `firstMetaplan`, `spine-model.ts`), `source/*` (`FeatureSourcePage`), `product[/:doc]` and `engineering[/:doc]` (`ConceptRoute`, summary pages) and `run` (`run-page.tsx`). There is no `pressure` route: `/f/<f>/pressure` renders "No such page". `plans/:doc`, `/new`, `/changes` and `/files/*` keep their own routes; `?step=` is gone with no redirect.

- **Landing.** `landingPath(checklist)` (`landing.ts`) sends the index route to `product` when the feature has a product spec (`has_product`), else to `engineering` when a metaplan is listed, else to `vision`, which offers to start one. A path no child matches renders a `LoadState` error.
- **Source stays in the feature.** A document of a feature (its vision, `doc/product/<f>/…`, `doc/plans/<f>/…`) opens its source at `/f/<f>/source/<repo path without doc/>`, built by `featureSourceHref(feature, repoPath, options)` (`feature/source-href.ts`; `featureOfDocPath` names the owner and is null for a standalone plan). `FeatureSourcePage` refuses a path that belongs to another feature or to none ("Not a document of this feature"). `featureSourceHref` with a null feature yields the file-mode `/files/…` address, so `sourceHref`, `sourceAddress` and `passageHref` (`concept/page-heading.tsx`, `concept/passage.tsx`) are one-line calls and the branch lives once. Source buttons and passage chips on feature pages link there; `/files/*` is the file browser and keeps its own chrome. The open-questions chip links into the feature only on summary pages: file mode keeps `/files/…#open-questions` (`review/review.test.tsx` pins it). The chat's viewed document maps `/f/<f>/source/<rel>` like `/files/<rel>` (`chat/viewed-document.ts`), so "Viewing <name>" survives the move.
- **Concept and Source are two views of one row.** The heading's Summary/Source switch is a two-state control. On a source route the spine's current row is the summary row of that document (`summaryPathnameOfSource`, `spine-model.ts`: the vision and a lone metaplan map to their group's target), and `spine.tsx` sets `data-view="source"` on the nav so a CSS `::after` writes "Source" under the current row (`spine.css`) without a DOM node. A non-plan file under `doc/plans/<f>/` (briefs, notes) maps to the metaplan group with no current row ([follow-up](../concerns/planner-ui-repair-followups.md#planner-review-fixes-unchecked-here-and-reviewer-suggestions)).
- **Vision page.** The vision summary has id `<f>/product/vision` (at most 8 sentences, [summary store](summary-store.md#store-layout-and-ids)); the product overview still cites the vision's sections directly, and `concept/body.rs` links a vision citation to the product overview only at overview level, so an overview citation of the vision opens straight to its passage with colour 0, while the vision summary page links to itself.
- **Metaplan page.** A metaplan summary id is `<f>/metaplan/<stem>`; it belongs to neither overview ([summary store](summary-store.md#store-layout-and-ids)). `pageKeyOfSummaryId` (`api/page-key.ts`) tests the metaplan scope before it computes `listed`. With several metaplans the breadcrumb reads only "Metaplan" ([follow-up](../concerns/planner-ui-repair-followups.md#planner-polish-unchecked-here-and-reviewer-suggestions)).

## Spine

`Spine` (`spine.tsx`, model in `spine-model.ts`: `spineGroups`, `groupOfPathname`) is `nav aria-label="Feature documents"`, the only place a feature's progress is drawn. Groups are the five document steps in workflow order (`GroupId`: vision, product, metaplan, plans, run); the route's own group is always open, the others toggle and persist per feature through `projectPref("spine-expanded")`. `NextAction` (`next-action.tsx`) heads it: one sentence and at most one button; a feature with no gap shows the sentence only. The pace choice, draft-team panel and section or plan queue (`gaps.tsx`) mount above the overview through `ConceptRoute`'s `above` slot, on `product` and `engineering` only. The wire still has a Pressure test step (`steps.ts` lists no page for it); the server step mark, the home card's sr-only list and `loom plan check` report it ([follow-ups](../concerns/planner-ui-repair-followups.md#planner-redesign-follow-ups)).

- **Plan rows carry the pressure record.** A plan row (`spine-row.tsx`, `spine.css`) is the mono slug followed by two 14px glyphs on one line: the plan's state and its pressure record (`PressureBadge`, `.plan-spine__badge`; wording and icons shared with the plan page's chip through `PRESSURE_TESTED`, `NOT_PRESSURE_TESTED` and `pressureIcon` in `files/heading-parts.tsx`). The words stay in the link as `.sr-only` and as the glyph wrapper's `title`; a retired plan shows its state and no record. A note with no glyph (a section's "not written") stays a visible word. Words beside the glyphs filled the 18rem column and cut the slug to a few letters ([the mistake](../mistakes/planner-polish.md#spine-plan-rows-lost-the-plan-name-to-their-badges)).

## Offers have one owner each, decided by id

No screen draws an offer twice. `paceOfferIds(checklist, scope)` and `pageDrawsPrimary(checklist, pathname)` (`page-offer.ts`) decide whether the page draws the checklist's primary; when it does, the spine shows the sentence only. Owners: the pace cards on an overview (only when they draw that primary's id), a missing document's page, a written plan's page (its Pressure test button for its own slug and its Start a run), and the Run page for every `start_run` primary. A queue row whose offer equals the primary reads "Next" with no button. A finished feature has no primary; `RefineSpec` and `NewMetaplanRound` are secondaries drawn on the Run page only. `PrimaryOffer` is not in the chat panel, which offers New chat and context prompts.

## Wire and names

The wire has six steps (`planning/checklist.rs::Step`: Vision, ProductSpec, Metaplan, Plans, PressureTest, Run; `Step::name()` is the one display name). The `Review` step is gone, and so is `ChecklistView.title`: a feature is named by its slug in the switcher, eyebrow, cards, breadcrumbs, chat and the browser tab, and a document keeps its own heading. `wire/checklist_card.rs::card_facts` fills `metaplans` and `plan_rows` on the view (rows come from the cached `Feature.metaplans` entries, winning plan paths, `Project::text` and `latest_pressure_date`; the conversion lives in `checklist_rows.rs`). `plan_rows` are listed from the metaplan's plan headings, not a table. `wire/fixtures/*.json` have no writer test (`checklist_fixture_matches_serde_output` only reads them), so they are hand-edited when `ChecklistView` changes, and a removed `Step` variant is searched for in `loom/tests/fixtures/planning/check_schema.json`.

## Run page

`useRunRead` fetches `/api/run/state` once on arrival, and a failed read says so instead of "Nothing is running"; the server sends no `run_state` frames, so a page that shows run state names what refreshes it. `fetchRunState` (`run/use-run.ts`) applies an overtaken answer while `runStateAtom` is null, because the debug server answers one request at a time (about 5 s for `state_view`). Start a run targets the `start_run` offer's plan, else the preselected run-state plan, else the first written row, only for a written row of this feature. A plan's pressure record is drawn on its spine row and its plan page; no page lists the records.
