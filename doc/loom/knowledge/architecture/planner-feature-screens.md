# Planner Feature Screens

> Spine

A feature's screens sit under one layout route. Product contract: `doc/product/feat-planner/` (index, `section_05.md`, `section_06.md`); the design record is `web/src/plan/ui/DESIGN.md`, set by a designer worker and read by every later worker.

## Layout route and landing

`/f/:feature` is `FeatureLayout` (`feature/feature-layout.tsx`): the spine beside an `Outlet`, with no spine while `projectAtom` is null. Children (`router.tsx`): `vision` (`VisionPage`: the vision's summary page through `ConceptRoute`, then a "Read the full vision" link to its source; a feature with no vision shows the offer to start one), `metaplan` (`MetaplanPage`: the feature's one metaplan, `index.md`, as a summary page through `ConceptRoute`, key `<f>/metaplan/index`, Source one click away), `source/*` (`FeatureSourcePage`), `product[/:doc]` and `engineering[/:doc]` (`ConceptRoute`, summary pages; the engineering overview also draws `RunPanel`, see [Run panel](#run-panel)), `coverage` (`CoveragePage`) and `findings` (`FindingsPage`), the two [trace pages](planning-trace.md#coverage-and-findings-pages). `run` is a redirect to `engineering`. There is no `pressure` or `built` route: `/f/<f>/pressure` and `/f/<f>/built` render "No such page". `plans/:doc`, `/new`, `/changes` and `/files/*` keep their own routes; `?step=` is gone with no redirect.

- **Landing.** `landingPath(checklist)` (`landing.ts`) sends the index route, whether or not every plan is done, to `product` when the feature has a product spec (`has_product`), else to `engineering` when a metaplan is listed, else to `vision`, which offers to start one. The header's feature switcher (`header/feature-switcher.tsx`) links each feature to `/f/<f>`, so the feature name lands by the same rule. A path no child matches renders a `LoadState` error.
- **Source stays in the feature.** A document of a feature (its vision, `doc/product/<f>/…`, `doc/plans/<f>/…`) opens its source at `/f/<f>/source/<repo path without doc/>`, built by `featureSourceHref(feature, repoPath, options)` (`feature/source-href.ts`; `featureOfDocPath` names the owner and is null for a standalone plan). `FeatureSourcePage` refuses a path that belongs to another feature or to none ("Not a document of this feature"). `featureSourceHref` with a null feature yields the file-mode `/files/…` address, which drops the `doc/` prefix (the source of a top-level run review in `doc/plans/` is `/files/plans/<review file>`, while a feature-owned review opens at `/f/<f>/source/plans/<f>/…`), so `sourceHref`, `sourceAddress` and `passageHref` (`concept/page-heading.tsx`, `concept/passage.tsx`) are one-line calls and the branch lives once. Source buttons and passage chips on feature pages link there; `/files/*` is the file browser and keeps its own chrome. The open-questions chip links into the feature only on summary pages: file mode keeps `/files/…#open-questions` (`review/review.test.tsx` pins it). The chat's viewed document maps `/f/<f>/source/<rel>` like `/files/<rel>` (`chat/viewed-document.ts`), so "Viewing <name>" survives the move.
- **Concept and Source are two views of one row.** The heading's Summary/Source switch is a two-state control. On a source route the spine's current row is the summary row of that document (`summaryPathnameOfSource`, `spine-model.ts`: the vision and the metaplan map to their group's target), and `spine.tsx` sets `data-view="source"` on the nav so a CSS `::after` writes "Source" under the current row (`spine.css`) without a DOM node. A non-plan file under `doc/plans/<f>/` (briefs, notes) belongs to no group and has no current row (the server classes it `Other`). `groupOfDocPath` puts a run review (`REVIEW_FILE`, `/^REVIEW-/`) and a plan (`PLAN_FILE`) in the Plans group; `PLAN_FILE` alone misses `REVIEW-DONE-PLAN-`, whose prefix has no dash. `REVIEW_FILE` is looser than the server's rule (`REVIEW-<plan slug>` directly in the plan home or `archive/`, `kinds.rs`), so a stray file named like `REVIEW-<anything>` shows in Plans ([follow-up](../concerns/planner-follow-ups-followups.md#spine-and-pages)).
- **Vision page.** The vision summary has id `<f>/product/vision` (at most 8 sentences, [summary store](summary-store.md#store-layout-and-ids)); the product overview still cites the vision's sections directly, and `concept/body.rs` links a vision citation to the product overview only at overview level, so an overview citation of the vision opens straight to its passage with colour 0, while the vision summary page links to itself.
- **Metaplan page.** The metaplan summary id is `<f>/metaplan/index`; it belongs to neither overview ([summary store](summary-store.md#store-layout-and-ids)). A feature has one metaplan, so the page has no file segment and the breadcrumb reads "Metaplan". `pageKeyOfSummaryId` (`api/page-key.ts`) accepts only `<f>/metaplan/index`. Follow-ups are entries under `## Follow-ups` in that file.

## Spine

`Spine` (`spine.tsx`, model in `spine-model.ts`: `spineGroups`, `groupOfPathname`) is `nav aria-label="Feature documents"`, the only place a feature's progress is drawn. Groups are the four document steps in workflow order (`GroupId`: vision, product, metaplan, plans); the route's own group is always open, the others toggle and persist per feature through `projectPref("spine-expanded")`. It draws no offer. `SpineHead` (`trace/spine-head.tsx`) heads it: the trace's top attention item as one sentence and one primary button ([head](planning-trace.md#browser)), none for a Help scene (`sample`). The pace choice, draft-team panel and section or plan queue (`gaps.tsx`) mount above the overview through `ConceptRoute`'s `above` slot, on `product` and `engineering` only. The wire still has a Pressure test step (`steps.ts` lists no page for it); the server step mark, the home card's sr-only list and `loom plan check` report it ([follow-ups](../concerns/planner-ui-repair-followups.md#planner-redesign-follow-ups)).

- **Rows and the trace.** The Product spec group lists its overview and one row per section; the Plans group lists its overview and one row per plan. Each group closes with its ledger: Coverage is the last child of Product spec and Findings the last child of Plans (`instrumentChild`, `feature/spine-instruments.ts`), each led by its `INSTRUMENT_GLYPHS` icon (`ui/glyphs.tsx`, shared with the Help topics) and reading the trace's figures (headings covered of total; open findings in `--tone-warning`), with no reading until the trace loads. `GROUP_OF_PAGE` maps `coverage` to the product group and `findings` to the plans group. A run review (`REVIEW-*`) belongs to Plans too, with no row of its own. `spineGroups(checklist, trace)` gives each row one leading glyph (`rowGlyph`, below); the vision and metaplan rows carry theirs on the group (`SpineGroup.glyph`). Group counts are the server checklist's ("12/12", "3/14"), not counts of settled sections. Without the trace (not loaded yet, or a Help scene) no row claims "Draft" or a settle word.
- **One glyph per row.** `rowGlyph` picks it once, by precedence: a retired plan, a running plan, attention, settled, a done plan, not written, else draft. Attention (revised, stub changed, upstream changed) is the amber seal in `--tone-warning`; a settled row's seal and a done plan's check are green (`--tone-completed`); not written is a dashed circle; draft an empty seal; a retired plan the archive glyph. The kind is `data-glyph` on `.plan-spine__glyph` (`spine-row.tsx`); the glyph is `aria-hidden`, its word is the `title` and a `.sr-only` word after the name, so a row's accessible name still reads "Settled", "Changed since you settled it", "Running" or "Done". A running plan draws the planner's roundel (`BusyRoundel`, `busyLabel=""`, `idleLabel=""`) in the glyph box: the roundel marks the header activity pill and this row ([busy signs](planner-web-shell.md#roundel-and-busy-text)).
- **Short slugs.** A plan row shows `shortSlug(feature, slug)` (`trace/model.ts`: the slug without its `<feature>-` prefix) in mono, with the full slug in `title`. The pressure record is not on the row (no flask, no badge): it stays as `.sr-only` words (`PressureWord`) and the plan page draws it ([the mistake](../mistakes/planner-polish.md#spine-plan-rows-lost-the-plan-name-to-their-badges)). The current row keeps `aria-current="page"` and has no gutter dot.
- **`settleable` gates every settle mark.** `TraceDoc.settleable` (`planning/trace/build/docs.rs`) is true for a written, unlocked document, except the vision and metaplan of a feature whose plans are all done; a stub, a locked plan and that finished vision or metaplan carry no settle state, gap, control or count. Product sections stay settleable because a follow-up plan can still change what they promise. Every web reader goes through `shownSettle`, never `doc.settle` ([model](planning-trace.md#the-trace-model)).

## Offers have one owner each, decided by id

No screen draws an offer twice. The spine draws no offer. Owners: the pace cards on an overview (`paceOfferIds`, `page-offer.ts`), a queue row (`queue.tsx`; it reads "Next" with no button only when a pace card draws its offer), a missing document's page and an empty state's offer (`concept/empty-states.tsx`), a written plan's page (its Pressure test button and its Start a run), the Plans overview's `RunPanel` for every `start_run` primary, and the Findings page for `review_feature` (its header button, the screen's primary only when the checklist's primary is that offer) and for `plan_follow_ups` (the Plan this and Fold into entry actions on each open finding, `followUpsOffer`, `trace/findings-model.ts`). A `pressure_test` offer is drawn only on its own plan's page; `fix_vision_table` has no screen. A finished feature has no primary offer: `Plan follow-ups` (`Offer::PlanFollowUps`, id `plan-follow-ups`, offered at `CurrentStep::ReadyAllDone`, `planning/checklist/offers.rs`) is its secondary, and `Review the feature` (`Offer::ReviewFeature`, id `review-feature`, secondary on any feature with a running or done plan) is secondary on every such feature. The Findings page cannot wait for the checklist's `plan_follow_ups`, which exists only once every plan is done, so `followUpsOffer` builds one from the trace for any feature that has a metaplan, and the server accepts `plan-follow-ups` for such a feature (`guidance/start.rs` `follow_up_start`, [candidates](#follow-up-candidates)); with no metaplan the cards say so (`NO_OFFER`). `/new` starts the offer for any feature that has a metaplan, done or not, through Follow-up with the feature picked. `Plan follow-ups` is an authoring offer: its opening asks the session to append entries under `## Follow-ups` in `doc/plans/<f>/index.md` (a seed from Plan this or Fold into entry takes precedence, [seeds](planning-trace.md#findings-actions)), and the checklist's step-4 gap ("Write plan <slug>") then drives the rest. `Review the feature` is an authoring offer with skill `loom-plan:review` (`plan-plugin/skills/review/SKILL.md`) and a null wire target. The Compare spec with build and New metaplan round offers (and the `loom-plan:retro` skill) do not exist. `PrimaryOffer` is not in the chat panel, which offers New chat and context prompts.

## Follow-up candidates

`ChecklistView.candidates` (`plan_server/wire/checklist_candidates.rs`, `ledger_candidates`) lists the open entries of the feature's findings ledger, `doc/plans/<f>/findings.md`, in ledger order. An entry the run-review import wrote is a finding or a question by its `Source:` anchor, names its stage, and names the newest run review of its plan (`newest_review`: the greatest Generated stamp among `run_review_paths`, else the last path); a hand-written entry names `review` as its stage and the ledger as its source. `/new`'s Follow-up lists the picked feature's candidates as toggle pills (`FollowUpSuggestions`, `new/kickoff-starters.tsx`): a pill puts `followUpSeed(candidate)` (`new/follow-up-features.ts`: the ledger id, the first line of the text, and "open finding from REVIEW-x.md, stage <id>") on a line of its own in the field. `candidates` is optional in the strict schema because hand-built test checklists omit it; `followUpFeatures` reads an absent list as empty.

## Run reviews

`fs::plan_review::generate` writes `doc/plans/REVIEW-<plan id>.md` at the top of `doc/plans/` for every plan, feature plans included; `commit.rs` commits it. `kinds::classify` gives `DocKind::RunReview` to a review in a plan's home, its `archive/`, or the top of `doc/plans/` and `doc/plans/archive/`, and `plan_server/review/built.rs` `run_review_paths` searches the same places ([the mistake](../mistakes/planner-design-brainstorm.md#a-feature-plans-run-review-is-written-where-nothing-looks-for-it)). The review's last three sections are bullet lists in one format written by `review_item_line` (`fs/plan_review/sections.rs`): ``- **<stage name>** (`<stage-id>`): <text>``, the name escaping `\` and `*`, whitespace runs collapsed. `planning/run_review.rs` `review_items(review, ReviewSection)` is the one parser that reads them back (`ReviewSection` names Open Questions and Open Findings, the two sections the findings import reads), from the last line equal to the heading (raw memory text earlier in the review may repeat it); the writer and the parser share the heading constants.

- `## Spec Conformance`: the decisions and questions integration-verify recorded with the prefix `spec-conformance:`, prefix removed ([the duty](signal-generation.md#product-sections-block-integration-verify-only)).
- `## Open Questions`: every question recorded during the run. A `spec-conformance:` question appears here too.
- `## Open Findings`: a suggestion whose latest receipt outcome is neither `Implemented` nor `Discarded` (none, `Promoted`, `Merged`, `Deferred`), and a note or decision whose latest outcome is `Deferred`. The latest receipt is the one with the greatest timestamp across every journal, a tie resolved by journal name order. The review is written after knowledge-distill resolves every entry, so "still pending at completion" would always be empty; the receipt outcome decides. A deferred `spec-conformance:` decision appears in both Spec Conformance and Open Findings ([follow-up](../concerns/planner-follow-ups-followups.md#run-review)).

## Wire and names

The wire has six steps (`planning/checklist.rs::Step`: Vision, ProductSpec, Metaplan, Plans, PressureTest, Run; `Step::name()` is the one display name). The `Review` step is gone, and so is `ChecklistView.title`: a feature is named by its slug in the switcher, eyebrow, cards, breadcrumbs, chat and the browser tab, and a document keeps its own heading. `wire/checklist_card.rs::card_facts` fills `metaplans` and `plan_rows` on the view (rows come from the cached `Feature.metaplans` entries, winning plan paths, `Project::text` and `latest_pressure_date`; the conversion lives in `checklist_rows.rs`). `plan_rows` are listed from the metaplan's plan headings, not a table. `wire/fixtures/*.json` have no writer test (`checklist_fixture_matches_serde_output` only reads them), so they are hand-edited when `ChecklistView` changes, and a removed `Step` variant is searched for in `loom/tests/fixtures/planning/check_schema.json`.

## Run panel

The Plans overview carries the run: `RunPanel` (`feature/run-panel.tsx`, mounted by `router.tsx` above the Plans gaps) holds the run line (`runSentence`, `run-scope.ts`), one Start a run button and the dashboard link. `useRunRead` fetches `/api/run/state` once on arrival, and a failed read says so instead of "Nothing is running"; the server sends no `run_state` frames, so a panel that shows run state names what refreshes it. `fetchRunState` (`run/use-run.ts`) applies an overtaken answer while `runStateAtom` is null, because the debug server answers one request at a time (about 5 s for `state_view`). Start a run targets the `start_run` offer's plan, else the preselected run-state plan, else the first written row, only for a written row of this feature (`startControl`); the button is the screen's primary only when the checklist's primary is the `start_run` offer. A plan's pressure record is drawn on its spine row and its plan page; no page lists the records. The panel draws no follow-up offer: once every plan is done its line reads "Every plan is done."
