## Module map

Bare `loom plan` runs `plan_server::run(&PlanServeArgs)` (`loom/src/plan_server/mod.rs`): `root::resolve_project` (a git repository, never a `loom/` stage worktree), `server_runtime_paths` (a set `LOOM_PLAN_STATE` is ignored with a warning), `create_runtime_dir`, `lock::acquire`, `launch_command`, `install_stop_handler`, `lock.publish`, `announce`, `serve_until_stopped`; none of it waits for the project. `launch::start_owned(Launch)` binds (`web_server::listener::bind_listener`, `DEFAULT_PORT = 7272`, walking forward when no `--port` is given), mints the token (`web_server::token::mint`), builds `BindInfo` and an unloaded `PlanContext`, starts the accept loop thread `loom-plan-accept` that calls `web_server::serve`, and spawns `loom-plan-load` (`loading.rs`). That thread runs the read-only detection, the watcher baseline, `Project::load` (`PlanContext::load_project`, filling a `OnceLock`), `routes::install_all`, the watcher and the 1 s tick (`watch.rs`), then records `LoadState::Ready`; a failure prints its cause and stops the server. `start(ServerOptions)` is `start_owned` plus a wait for the load, and touches neither the lock nor the runtime directory, so tests call it directly.

While the load runs, `PlanRouter::hold_until_loaded` holds admitted `/api/*` requests and `/ws` upgrades in `Lane::Held` (`MAX_HELD = 48`, leaving the connection reserve), for up to `LOAD_WAIT` (60 s). The answers are 503 `loading` on a full lane or a timeout, 503 `stopping` on a stop, and 500 `load_failed`, whose fixed text names no host path. The page shell, assets and token bootstrap answer at once.

## Shared web_server layer

`loom/src/web_server/` is the transport both servers use. `serve(listener, Arc<dyn Router>, running, ServeConfig)` owns the accept loop, the per-connection timeouts, the head gate and the `Host` gate, then calls `Router::upgrade` (head only peeked: WebSocket handshakes, token bootstrap; return `None` when finished) and `Router::handle` (one consumed head plus body prefix). `ConnInfo` hands the router the connection's own `local` address, the `AccessPolicy`, the `Limits` and the `running` flag. `serve` fails closed before accepting when the policy is remote and carries no `Auth`, waits up to 3 s for connections on stop, and sleeps 50 ms after a failed `accept`. `AccessPolicy::new(local, Option<Auth>)` is infallible; each server builds its own `Auth` (`Auth::new(token, cookie_name)`; `Debug` is redacted). `ServeConfig.thread_name` names connection threads (`loom-plan-conn`). `http::write_response_with_headers` carries extra headers (the planning `Referrer-Policy`). The shared 503 bodies and log lines say "dashboard"; the planning server emits them verbatim.

## Gate order

Every `/api/*` request and `/ws` upgrade passes these checks in order. `gate::admit` runs first: `Host` (403), exact `Origin` equal to `http://<Host>` on every POST and every WebSocket (403; the dashboard's loopback-alias leniency does not apply), the access cookie `loom_plan_<port>` (401), the browser identity. The load hold follows, because the role check can take authoring. `gate::check_route` runs last: the body's `Content-Type` and `Content-Length` (415/413, before any body byte is read), then the route's `Role`. The browser cookie is `loom_plan_browser_<port>`; both cookies are `Path=/; HttpOnly; SameSite=Strict`. An HTTP request without a valid browser cookie gets a minted `BrowserId` and a `Set-Cookie`; a WebSocket without one is refused 401 (the app calls `GET /api/server` first). A minted id reaches only `Role::Viewer` routes: on `Holder`/`HolderOrTake` routes it is refused 401, and `Presence::name_of` does not record it, so the presence map is bounded by browsers that send their cookie back. `GET /?token=<token>` with the right token sets the access cookie, the browser cookie when absent, and redirects to `/`; a wrong token or a foreign `Origin` is 403. Planning responses carry `Referrer-Policy: no-referrer`. Bodies are read with `Read::take` bounded by the gate-checked `Content-Length` (`request::read_body`), not `web_server::http::read_body`.

## Route modules

`uploads/` (`POST /api/attachments`) and the kickoff draft store in `chat/drafts.rs` (`GET /api/kickoffs`) are described in [Planner Uploads and Kickoff Drafts](planner-uploads-and-drafts.md). A route module `plan_server/<name>/mod.rs` contributes `routes() -> Vec<RouteSpec>` with one line in `routes::all_routes()` and, if it needs state, `install(&Arc<PlanContext>)` with one line in `routes::install_all()`. `RouteSpec { method, path, body, role, handler }`: `path` is exact unless it ends in `/`, which makes it a prefix; `HEAD` is answered by `GET` routes; `Role` is `Viewer` (any holder of the access cookie), `Holder`, or `HolderOrTake` (any browser takes authoring when nobody holds it). `find()` returns the first match, so `routes.rs` tests `first_duplicate(&all_routes())` for a `(method, path)` collision. Later plans hang their own state on `ctx.extensions()` (one typed slot per type) and register `ctx.on_batch` hooks and `ctx.shutdown()` hooks. `install_hub_hooks` runs first so `hello` is the first frame every WebSocket receives.

## Wire model and parity

Wire types live in `plan_server/wire/` (`message.rs`, `server.rs`, `presence.rs`, `checklist.rs`, `concept.rs`) and mirror `web/src/plan/api/schema.ts`. `PlanMessage` (`type` tag, snake_case, `deny_unknown_fields`): `Hello(Box<Hello { you, server, checklist, presence, authoring }>)`, `Presence`, `Authoring`, `Checklist`, `ServerStopping`, `Refused`, `TreeChanged`, `DocChanged`, `Validation`, `ConceptChanged`. `ClientMessage`: `SetName { name }`, `Reading { path }`. Two checks keep Rust and TypeScript equal: JSON fixtures in `web/src/plan/api/fixtures/` are round-tripped by Rust tests (`assert_fixture` in `message.rs`) and parsed by the web tests, and `wire/tests_schema.rs` reads `schema.ts` with `include_str!` and asserts every serialized enum value is a quoted entry of the matching exported array. A new wire enum variant, or a changed fixture, needs the schema array and fixture updated in the same change. The dashboard's equivalent is `commands/status/web/schema_parity.rs`; the two helpers differ and are not shared.

## WebSocket

`ws::run_connection` serves one admitted connection: 250 ms socket timeout, a protocol `Ping` every 10 s, `MAX_INBOUND_BYTES = 256 KiB`. The connection holds a `Lane::WebSocket` slot from `web_server::limits` (shared `MAX_WEBSOCKETS = 48`); past it the upgrade answers 503 `busy`. `PlanHub` (`ws/hub.rs`) is the planning server's own hub — it does not use `web_server::hub::Hub`, because it sends to single connections as well as broadcasting — with a 64-frame queue per connection and a slow connection dropped. A connection registers before its `on_open` hooks run, so a broadcast made by a hook (or concurrently) is queued behind the open frames, which are a snapshot at least as new as anything queued before them. `ws::dispatch::dispatch` runs on the connection's own thread between reads and must return quickly; a frame that does not parse as `ClientMessage` never reaches it and is answered `Refused { command: "frame" }`. The server sends only protocol pings, which browser JS cannot observe, so the client has no half-open watchdog until the server also sends a text heartbeat.

## Presence and authoring

`BrowserId` is the cookie value and never leaves the server; `PublicId` is what other tabs see. `Presence` records a browser only through `public_id`, `set_name` and `opened`; names are at most 32 characters (`presence.rs`, matched by `MAX_NAME_CHARS` in `web/src/plan/header/name-prompt.tsx`); the browser that set a name first keeps it and a later namer shows as "Viewer N". `Authoring` (`authoring.rs`) names the holder as a `BrowserId`, so every tab of the holding browser holds authoring. The holder is away once its last connection closes and frees after `GRACE` (600 s) unless a tab reconnects; `Authoring::tick` runs from the 1 s tick with the time passed in so tests drive it. `Take::HolderOnly` never takes authoring; `Take::TakeIfFree` takes it when nobody holds. Refusals: `NotHolder { holder }`, `NoHolder`, `ReadOnlyMode`, `Stopping` (the holder is refused too while stopping). `AuthoringEvent` (`Taken`, `Away`, `Back`, `Freed`) reaches subscribers after the internal lock drops, so two concurrent changes can arrive out of order: treat events as hints and re-read `holder()`. A browser that takes authoring over HTTP and never opens a WebSocket is never marked away, so authoring does not free until restart. `POST /api/save` is the one `HolderOrTake` route: the gate takes free authoring for the requesting browser before the handler runs. `ReadOnly::detect()` (`prereq.rs`) lists missing tmux, Claude Code or its login, and the Linux sandbox prerequisite; any problem makes the server read-only and nobody takes authoring.

## Shutdown

`lifecycle::line` prints timestamped lines. The first stop signal calls `begin_shutdown`: `Shutdown::begin` first (it sets the stopping flag, so a racing `TakeIfFree` already sees the server as stopping, and drains every registered `ShutdownHook` concurrently, naming the ones still running), then a `ServerStopping` broadcast; the accept loop, WebSockets and routes stay up while hooks drain. The second signal exits at once (`std::process::exit`). `RunningServer::stop` clears the accept flag, stops the watcher and tick and joins them. The watcher and tick share threads with later plans' batch hooks and authoring subscribers, with no `catch_unwind`: a panicking hook silently freezes the project view or the grace timer.

## Runtime directory and lock

The runtime directory is `<loom user dir>/plan/<project key>` (`planning::runtime::server_runtime_paths`; `LOOM_PLAN_STATE` belongs to planning sessions and is ignored by the server). `create_runtime_dir` makes it mode 0700 through `safe_create_dir_all`/`safe_open_dirfd`, which open with `O_NOFOLLOW`: a symlinked `~/.loom` or `$LOOM_HOME` stops `loom plan` from starting. `lock::acquire` returns `Held(ServerLock)` or `Running(LockRecord { pid, start_time, url, token })` (`lock.rs`); `plan_server::run` installs the stop handler (`install_stop_handler`) before it announces the URL, so a client acting on the URL can SIGINT a server that drains; the held lock publishes the base URL and token once the server is listening, so a second `loom plan` prints the running server's link through `startup::already_running_lines` (passed through `inline_safe`) and exits 1 with `AlreadyRunning`, or asks for a retry while the first is still starting. The lock opens by path (`lock.rs`), safe because its parents were just validated.

## Open points

Reviewer suggestions nobody implemented, each checked against the tree. File-mode follow-ups are under "File mode follow-ups" below.

- **Token and hardening gaps.** `browser::open` passes the tokenized URL to `xdg-open` as argv, readable by another local user through `/proc/<pid>/cmdline` while the opener runs; section 02 mandates opening the URL, so closing it needs a spec decision (for example opening a 0600 redirect file in the runtime directory). Refusals written by the shared layer (Host 403, head errors, 503 at the cap) and tungstenite's handshake errors carry no `Referrer-Policy`; the bodies are plain text without links. `lock::acquire` opens the lock by path rather than relative to the directory fd, and no test plants a symlink inside the runtime path. `Auth` and `Admitted` have redacted `Debug`; keep it when adding fields.
- **Unbounded inputs.** `read_body` has a per-read bound but no total deadline, although `POST /api/save` reads up to 1 MiB; add a wall-clock bound. `Presence::public_id` records every distinct well-formed cookie for the life of the process, and `set_name`/`reading` broadcast to up to 48 connections with no per-connection rate limit; both need the access cookie.
- **Shared module carries dashboard wording and dashboard-only code.** The 503 bodies and logs in `web_server/unserved.rs`, `head.rs`, `ws.rs` and the accept-error log in `serve.rs` say "dashboard" and reach planning clients; the dashboard's tests pin those bodies, so neutral wording needs a name in `ServeConfig` and a test update. `token::cookie_name` hardcodes `loom_dashboard_<port>`, `auth::resolve_process_token` is dashboard-only, and `web_server/access_tests.rs` imports the dashboard's `ServeOptions`; moving `resolve_process_token` next to `AccessPolicy::resolve` in `commands/status/web/mod.rs` would remove the test dependency on `commands`.
- **Duplicated helpers.** `request.rs::read_body` and `web_server::http::read_body` have separate body-reading implementations: the shared reader also has a total deadline and shutdown cancellation, while planning uses its gate-checked content length; `ws/conn.rs` repeats `SOCKET_TIMEOUT`, `send_pending` and the tungstenite config of `web_server/ws.rs`; random hex minting is hand-written in `web_server/token.rs`, `daemon/server/tokens.rs` and `csrf.rs` (a shared `random_hex(n) -> io::Result<String>` would also remove the `/dev/urandom` panic in `PublicId::mint`, `ids.rs:51`, which runs under the presence mutex); `router.rs` passes `ws::MAX_INBOUND_BYTES` while `mod.rs` builds `Limits::new` with it (read `conn.limits.max_inbound_bytes()`); `gate::check_role` re-derives the public id `router::call` already computed; `web_server/bootstrap.rs:46` drops the `write_redirect` result with `let _ =` while the planning router logs it; `ws/hub.rs::connections_of` is `pub` but test-only.
- **Hook failures freeze things silently.** `watch.rs` runs later plans' batch hooks and authoring subscribers on shared threads with no `catch_unwind`, and `RunningServer::stop` drops the join result. `PlanContext::project()` hands out a std `RwLock` read guard while the watcher takes the write lock: a second `ctx.project()` in one call stack can deadlock behind a waiting writer.
- **Authoring.** Events can arrive out of order (subscribers re-read `holder()`); a browser that takes authoring over HTTP without a WebSocket never goes away; `web/src/plan/state/atoms.ts::canAuthorAtom` lets the holder author while stopping although the server refuses every `TakeIfFree` then, and `authorBlockReasonAtom` is `null` while server state is unloaded.
- **Web shell gaps.** `web/src/plan/api/socket.ts` writes `lastMessageAt` and never reads it (a watchdog needs a server text heartbeat first); the checklist skeleton never resolves to an error when the socket cannot connect (the "Connection lost" banner belongs to the chat panel plan); `header/tabs.tsx` has no narrow-width strategy, so the header overflows at 390 px once plans register about 200 px of tabs; `header/popover.tsx` and `ui/dialog.tsx` use `data-open:`/`data-closed:` animation variants that never match Radix's `data-state`; `header/step-tracker.tsx` marks the current step with `bg-muted` on `bg-card` (low contrast); `header/share.tsx` copy state never returns to idle, so a repeat click announces nothing; `header/presence.tsx` renders a focusable list item with no action.
- **Tests.** `plan_server/tests/mod.rs::an_omitted_port_walks_past_a_busy_default` returns early when 7272 is taken and passes vacuously beside a running `loom plan`; `loom/tests/web_server_contracts.rs` has no loopback skip (failing loudly is defensible for contracts); the share-link test in `plan-shell.contracts.test.tsx` cannot detect a retained tokenized link (stub the third open's fetch as never-resolving and assert the URL is absent); the `wire/tests_schema.rs` helper overlaps the dashboard's and is not shared.

## File mode

`plan_server/files/` (`routes()` in `mod.rs`, `install(ctx)` in `routes::install_all`, before `search::install`) serves the document tree, documents, diffs and saves. Paths on the wire are `doc/`-relative (path=a.md for doc/a.md); `wire::paths::to_doc_rel` converts, and the web client sends the `doc/`-relative form (`web/src/plan/files/api.ts`; see [the client-side mistake](../mistakes/plan-server-delivery.md#the-web-client-sent-repo-relative-paths-to-doc-relative-routes-2026-10-27)).

| Route | Role | Does |
| --- | --- | --- |
| `GET /api/tree` | Viewer | `FileTree` built by `tree.rs` from `TextStore::current` (content-hash check, no disk read under the project guard) |
| `GET /api/doc` | Viewer | `doc::doc_view`: text truncated at 1 MiB, the `LockView`, a plan's view (`plan_view.rs`, `implements_links` from `product_sections(&project.tree)`), the knowledge index (`knowledge_index.rs`) |
| `POST /api/save` | HolderOrTake | `save::save_route`, text body capped at `doc::MAX_EDIT_BYTES` (1 MiB) |
| `GET /api/diff/head`, `/api/diff/turn` | Viewer | `diff.rs`: working copy against `HEAD`, or a turn's pin against its end text |
| `GET /api/search` | Viewer | `search/` (below) |

**Editability** is owned by `doc.rs` (`editable`, `lock_view`, `entry_kind`, four notice consts): Markdown in the plain `doc/` area only. A running plan is `LockKind::Running`; retired plans (including `doc/plans/archive/PLAN-*.md`, which `planning::paths::name_reason` locks as `PlanState(Done)` before the Archive rule) and run reviews are `Done`; a brief of a locked plan carries the plan's repo-relative path in `LockView.plan`; knowledge and the summary store are locked with their own notices.

**Save order** (`save::save_document`): authoring with `Take::HolderOnly` (`NoHolder` passes) → path syntax (`check_relpath_syntax`) → discovered → editable → no symlink (discovery flag, then `symlink_component` on disk now) → text over 1 MiB → re-read the file and compare `normalized_hash` with the opened hash (`Conflict` returns the current text and hash, nothing written) → plan validation (`Invalid` unless `with_errors=1`, "Save with errors") → `require_authoring(TakeIfFree)` → `replace_no_follow` (`fs/safe_replace.rs`: temp file plus rename; a failed directory fsync after the rename is logged and returns `Ok`) → `TextStore::refresh_path`. The HTTP gate has already taken free authoring for a `HolderOrTake` route, so only direct callers of `save_document` see authoring taken as late as the last steps. Refusals map to 403 (authoring, locked, symlink), 404, 400 (path), 413, 409 (conflict), 422 (invalid; `request.rs::reason_phrase` has no 422 entry, so the status line reads "Unknown") and 500. The hash check and the rename are not serialised: two saves from one holder can still lose one.

**Text store and pins** (`texts.rs`): `TextStore` holds every discovered document's text and `normalized_hash` (never the summary store), keeps the root it loaded, and follows the watcher (`apply`) and the server's own writes (`refresh_path`). `begin_turn` and `end_turn` re-read disk at that moment; an ended turn keeps only the documents it changed (a second `end_turn` returns the recorded changes, so a later plan must not expect a pin for an unchanged document), and the store keeps the newest `MAX_TURNS = 64` turns. Diffs read pins from it. The head diff runs `git rev-parse --verify --quiet HEAD:./<path>` (exit 1 means not in `HEAD`, shown as an untracked file; other git failures answer 500), checks `cat-file -s` against 1 MiB, then `cat-file blob`; `./` is deliberate, because the argument is a revision expression that `--` cannot guard.

**Validation cache** (`validate.rs`): `ValidationCache` (in `ctx.extensions()`) holds each unlocked plan's `ValidationView`, produced by `commands::plan::verify::report::verify_text` plus `plan::inputs::collect_inputs_with_text` for the input set. `spawn_validation` runs the first pass on thread `loom-plan-validate` after the URL prints and broadcasts `validation` then `tree_changed` per plan; `/api/doc` validates an uncached unlocked plan on request without storing it. Batch revalidation and the pass serialise on FileMode's published-tree mutex. A cached view also depends on state the `doc/` watcher cannot see (git commit state behind the "inputs not committed" note), so it can stay stale until a document touches the plan. `plan_server::load` takes `watch::baseline` before `Project::load` and the stores, so an edit made during startup arrives as the first batch.

**Search** (`search/`): `SearchIndex` is built synchronously in `search::install` from the `TextStore` and kept current by a batch hook. Results are chunked per `##` section with a heading path and an anchor (each chunk is matched to the next level-2 heading with the same line text by a forward cursor, so a `##` inside a fence does not shift anchors); a quoted query is a literal, case-sensitive match (`literal_snippet`), otherwise ranked terms; `Scope` (`all`, `product`, `plans`, `knowledge`) filters and results are capped at 50. The index lives in memory only; nothing is cached under `.loom/`.

**Wire**: `tree_changed`, `doc_changed` (`hash` is `None` both for a deleted file and for an unreadable or oversized one) and `validation` are `PlanMessage` variants mirrored in `schema.ts` and the fixtures; `tests_schema::all_plan_messages` covers them.

**Plan verify split**: `commands/plan/verify.rs` is the thin CLI (`execute`, `--json`, exit code); `verify/report.rs` owns the result (`VerifyReport`, `VerifyPlan`, `VerifyError`, `VerifyWarnings`, `YamlLocation`, all `pub`) and the pure entry points `verify_text(repo_root, plan_path, text)` and `verify_path(path) -> Result<VerifyReport, EarlyFailure>`. `VerifyReport.stopped` is `#[serde(skip)]`; human mode bails with the first error when it is set. `verify_text` reports "missing file" for the plan itself when the path does not exist on disk, so tests of `validate_plan` write the plan file first. The save route and `loom plan verify --json` share it, and a test pins that they agree on fixture plans.

## File mode follow-ups

Reviewer suggestions nobody implemented, each checked against the tree.

### Server

- **Throughput.** `search/index.rs`: `score_chunks` clones every chunk's token vector per query and each `IndexedChunk` keeps one `(String, f32)` per token occurrence (about 8 to 10 times the text, unmeasured); acceptable for Enter-only search, revisit if search becomes search-as-you-type. `heading_path` is quadratic in headings (a 1 MiB document of `## a` lines holds the index write lock for minutes). `TextStore::apply` and `refresh_all` read and hash documents under the write lock; read first, then swap (keep entries replaced since the snapshot with `Arc::ptr_eq`). `PlanInputs::of` repeats the discovery `verify_text` already ran, so each validation walks every brief twice. `current_tree` clones the whole `ValidationCache` only to count errors.
- **Unbounded memory.** Turn pins keep `MAX_TURNS = 64` turns for the process life. `diff.rs` returns `after` and turn texts up to `MAX_DOC_BYTES` (8 MiB) per side while `doc_view` cuts at 1 MiB.
- **Locks.** `TextStore::end_turn` takes `&Project`, so callers hold the project read lock across a full-tree disk read; plan 7 should pass the path list or the context. `validate_all` and `revalidate` never check `ctx.is_stopping()`, so Ctrl-C during a long pass waits for the watcher thread. The hash check and rename in `save_document` are not serialised.
- **Stale cache.** A cached validation view depends on git commit state and artifact existence the `doc/` watcher cannot see; fixing it needs a decision (watch `.git/HEAD` or revalidate on open).
- **Save details.** `replace_no_follow` adds 22 bytes to the target name, so a name over 233 bytes fails every save with a generic 500. `fs/safe_replace.rs` uses raw libc `rename_at`/`unlink_at`; `safe_fs::safe_rename_in_workdir` could remove two `unsafe` blocks. `host_verify/store_fs.rs::write_atomic` is a second temp-then-rename helper with the same scheme (overlap, not a defect). `check_relpath_syntax` does not reject Unicode format characters (U+202E) and the tree and diff header do not mark them; `Untrusted` in `web/src/plan/chat/visible-controls.ts` is the marker helper, and the file-mode tree and diff header do not use it.
- **Smaller.** `DocChanged.hash` is `None` for deleted and unreadable files alike, so `useGone` can report "deleted" for a file that still exists. `is_markdown` is defined in `doc.rs`, `tree.rs` and `planning/project.rs`. `ValidationCache` is a bare `Mutex<HashMap>` extension key (wrap it in a newtype). `TextStore::load` never fails, so the `unwrap_or_else` fallback in `files/mod.rs` is unreachable. `commands/plan/verify/report.rs` and `checks.rs` import each other (move `build_levels_output` and `stage_type_label` into `checks.rs`). `plan/inputs.rs` compares porcelain paths (repo top level) with `ls-tree` paths (working directory) so `changed` never matches when the project root is a subdirectory, and `status` lacks `GIT_OPTIONAL_LOCKS=0`; `commands/run/plan_inputs.rs` calls `uncommitted_reason` per input (four git processes each) where `uncommitted_reasons` answers all in four. `git` helpers in `loom/tests/file_mode_contracts.rs` and `files/tests/diff.rs` do not disable `commit.gpgsign`. Untested: a `HEAD` blob over 1 MiB (413), `/api/diff/turn` with `..`, temp cleanup after a failed rename, a stop between two plans, a porcelain path outside the project root.
- **Nits.** `commands/plan/verify/tests.rs::verifies_a_plan_with_no_repository_root` ends with assertions on an unrelated `check_base_tree(&[], None)` call; `files/tree.rs` unwraps `strip_prefix` in a request path (guarded by a filter; use let-else); `wire/files_tests.rs` calls `SCHEMA_FILES_TS.to_owned()` in five tests for nothing; the file-mode plan's decision names `git show HEAD:<path>` while the code runs `rev-parse` plus `cat-file` (`diff.rs`).

## Page route and page model

`GET /api/concept/<key>` (`plan_server/concept/routes.rs`, `Role::Viewer`) answers one `ConceptPage` (`plan_server/wire/concept.rs`, mirrored by `web/src/plan/api/schema-concept.ts`). `PageKey::parse` (`concept/page.rs`) accepts `product`, `engineering` and `<scope>/<name>` where the name matches `[A-Za-z0-9._-]{1,128}` and is not `.` or `..`; anything else is 400 `bad_page`, an unknown document 404 `not_found`, a missing `ConceptState` 500. The page key is the URL path under `/product` and `/engineering` in the browser.

The server resolves, the browser renders. A page arrives with key chips (colour, label, per-chip `out_of_date`, `no_plan`), blocks of sentences with `marks`, `citations` (`Sentence { summary, id }` or `Source { path, anchor }`) and `rests_on` (the source sections a sentence rests on, reached through its cited level-1 sentences), `implements` / `implemented_by` links, an `empty` state, and `building` / `estimate`. The browser computes nothing from summary files, so the open-state rule runs on `rests_on` alone.

- Colours: `key.rs` assigns `index % 8 + 1` over plan 4's `store::scope` order (the vision table, then the metaplan's entries). A summary page takes its document's colour in its overview. The vision and the metaplan have no chip; a mark for a sentence citing them directly has colour `0`, drawn in `--muted-foreground` (`docColour` in `web/src/plan/concept/marks.tsx`).
- Empty states (`EmptyKind`): `no_vision`, `sections_no_vision`, `no_metaplan`, `plans_no_metaplan`, `never_built`, `building`. `never_built` needs a non-empty document list; a vision with zero sections and no overview file reads `building` with count `None`.
- `ImplementsView` is `not_stated` or `sections { links }`; `implemented_by` and `PlanLink` list only plans with a concept page (`links.rs`: a plan with no summary id, or whose page key `PageKey::parse` rejects, is left out), while `key.rs` computes `no_plan` from `project.implemented_by`, which still counts them. The two views can disagree for an unlisted archived plan.
- Enum names on the wire are `SummaryStateView`, `OutOfDateReason` (`source_changed`, `rebuilding`, `awaiting_approval`, `cannot_rebuild`, `failed`) and `EmptyKind`; `Option` fields serialize as `null` (no `skip_serializing_if`). `Block` and `Citation` carry a snake_case `kind` tag.
- `state::out_of_date_reason(id, state: SummaryState, ctx: &PageContext)` is `pub(crate)` and takes the state by value (`SummaryState` is `Copy`). `PageContext` holds `read_only: Option<String>`; `routes::page_context` fills it from the first read-only problem, with `#[allow(clippy::needless_update)]` on the `..Default::default()` tail so a later field compiles.
- `delta::page_keys(id, &Scope)` is `pub(crate)` and returns the page keys a summary shows on (its own page and its scope's overview); `ConceptState::latest()` returns `Arc<Evaluation>`.

Adding a `PlanMessage` variant (`ConceptChanged`) needs the `Eq` derive (`PlanMessage` derives it), an arm in `wire/tests_schema.rs::all_plan_messages`, and `concept_changed` in `web/src/plan/api/schema.ts` (`PLAN_MESSAGE_TYPES`, `conceptMessageSchemas`). `PageContext` and the plan 10 hooks: `progress(ctx)` in `page.rs` returns `(None, None)` until plan 10 fills `building` and `estimate`.

## Engine driver and ConceptState

`concept::install` (`concept/engine.rs`, called from `routes::install_all`) builds a `SummaryEngine` from the project root, the runtime directory and the shared `OwnWrites`, runs `engine.on_batch` once with `Batch { initial: true, .. }` (the watcher drops its initial batch because the project loads after that walk, so renames and deletions made while no server ran apply before the first request), stores `ConceptState` in `ctx.extensions()` and registers a `ctx.on_batch` callback. `install_with(ctx, runtime)` takes the runtime directory explicitly; route tests that make the engine write must use it, because `install` points the engine at the real `~/.loom/plan/<key>` runtime directory (`PlanContext::new` has no override).

`ConceptState { engine, runtime, latest, previous, listeners }`: `latest()` returns the evaluation after the last batch, `subscribe(Listener)` registers `Fn(&PlanContext, &EngineUpdate)` run in registration order after every successful engine update, `handle(ctx, batch)` runs one batch and broadcasts the delta.

- An engine error with readable claims prints one `lifecycle::line` (through `safe_error`), keeps the previous evaluation, and publishes the batch's `sources` alone so open passages refetch; the page names are unknown, so a title, plan-state or pressure change in that batch is never named.
- An engine error with unreadable claims (the engine's one failing step) evaluates the project without claims (`without_claims`) and publishes normally. Listeners are not called on that path, so plan 10's scheduler sees no invalidations from those batches.
- The summary scheduler reads `invalidated` from a `subscribe` listener (`summaries/mod.rs`), and its facade broadcasts `ConceptChanged` for the `delta::page_keys` of the evaluation's scope (`architecture/summary-store.md`, Rebuilds and Cost).

## The concept_changed delta

`delta.rs` keeps a `Snapshot { summaries: id -> (state, file hash), shown: page key -> Shown }` per batch and compares it with the next. `ConceptChanged { pages, out_of_date, sources }`:

- `pages` names every overview whose whole `ConceptPage` changed, every product section whose `implemented_by` links changed, every plan whose `implements_view` changed, the page of every summary whose state or file hash changed, and the page of every summary id a batch path maps to.
- Sibling pages: a change of an overview's key row (documents, colours, labels, `no_plan`; `out_of_date` is compared nowhere in it) names every summary page of that scope, because each page embeds the key chips and takes its colour from them. `key_row_pages` is redundant for the browser, which widens to the scope when it sees the overview, and keeps the delta complete for a consumer that does not.
- `out_of_date` names the summaries that became `stale`, `incomplete` or `rebuilding`; the browser dashes their marks and chips at once, with reason `source_changed`, before any refetch.
- `sources` lists every batch path under `doc/` outside the summary store; open passages refetch them.

The snapshot reads each summary file's hash after `evaluate`, and `page.rs::summary_file_hash` reads the file again per request, while blocks come from the last evaluation; a reseal between the reads can leave a hash describing a different build than the text ([concerns](../concerns/planning-document-model-followups.md#concept-mode-server-gaps)).

## Browser: routes, page state and view state

`web/src/plan/router.tsx` mounts under `PlanShell`: `/` (`HomeRoute`), `f/:feature` (`FeatureRoute`), `new` (`KickoffRoute`), and as `ConceptRoute` (`plan/concept/concept-route.tsx`) `f/:feature/{product,engineering}`, `f/:feature/{product,engineering}/:doc` and `plans/:doc` (a standalone plan's summary). The Product and Engineering entries in `plan/tabs.ts` omit `element` (`PlanTab.element` is optional) because the router owns those routes. `web/src/plan/api/page-key.ts` maps a pathname to the server's page key and back (`pageKeyOfPath`, `pageHref`, `parsePageKey`): `f/<feature>/<scope>` is `overview/<feature>/<scope>`, `f/<feature>/<scope>/<doc>` is `<feature>/<scope>/<doc>`, `plans/<doc>` is `plans/<doc>`, with `<scope>` `product` or `engineering`; a standalone plan's scope is engineering (`scopeOfKey`). `conceptPageLabel(pathname)` names the page for the eyebrow above an overview; plan 2's presence list never reads it.

`page-state.ts` holds one `conceptPageAtom(key)` per page key (`{ page, previous, error, status }`), validated through `isConceptPageKey` (the same rule as `PageKey::parse`) so an invalid URL fetches nothing. `loadConceptPages(store, keys)` fetches in one pass and applies every answer together, so an overview and the summary pages its runs cite change together under the open-state rule; a response overtaken by a later request for the same key (a per-key ticket) is dropped. A failed refetch keeps the loaded page and records the error, except 404 and 400 (`MISSING_STATUSES`), which drop it so the route and cited runs show the not-found state (`isMissing`; `run.tsx` reads "The <title> summary no longer exists").

- `subscribeConcept` follows `concept_changed` on the plan socket (`socket.subscribe(type, handler)` is a method on the `planSocketAtom` handle) and `onResync`. `applyConceptChanged` dashes `out_of_date` summaries at once (`markOutOfDate`), refetches the named pages that are loaded (an unloaded page is never fetched) plus every loaded page of a scope whose overview the delta names, and refetches each `sources` path in the passage cache (`refreshDocView`, `refreshAllDocViews` in `passages.ts`).
- No state is copied from one page to another: each page shows its own fresh response, ordered by its own ticket, because copying across keys has no order and an older response could overwrite a newer dash. A sibling summary page therefore keeps its dashed chip until the delta names the scope's overview or the page is refetched.
- `useConceptPage` refetches every cached page (`refetchAllLoaded(store, [key])`, one pass) on its first effect run, so a mount after time away catches missed deltas; later key changes load only the new key.

View state is `openRunsAtom(pageKey)` (`view-state.ts`): a jotai atom per page key mirrored to `sessionStorage` under `loom-plan:concept:<pageKey>`, parsed through a zod schema on read, every read and write in `try/catch` so a blocked store leaves the in-memory state usable. The URL carries only the page. `notesAtom(pageKey)` holds the fold notes in memory only. Open runs are `{ level 0|1|2, sentenceId, restsOn, parent }`.

## Open-state rule

`carryOpenState(prev, next, open, cited?, inFile?)` (`concept/open-state.ts`) carries the open runs of the previous page onto the rebuilt one, keyed to the source sections each run rests on (`rests_on`), and returns `{ open, notes }`. A run keeps its place when `next` has its sentence id with exactly the same anchor set (checked before the overlap and reading-order tie-break), otherwise it moves to the sentence with the best anchor overlap; a run whose anchors all vanished folds and leaves a `FoldNote` whose `paragraphOf` is the id of the next-page sentence the note follows (the run's restored parent), or `""` for the page start.

- Level-1 runs of an overview live on the cited summary pages; the optional `CitedLookup` (`page-state.ts::citedLookup(store, page)`) resolves a citation to that sentence so `rests_on` is available. Without it the run keeps its id while its parent still cites it. `restoreStoredRuns` (first load) rarely has the cited pages loaded, so nested level-1 runs restore through `carryStoredRuns` and `syntheticPrevious` from the stored anchors.
- Removed-section notes come from the carried level-0/1 run (anchors gone from its new sentence and from every sentence of `next`), deduplicated per paragraph and anchor against any hand-built level-2 entry; the level-2 branch stays for stored and hand-built runs. `inFile` (`passage-doc.ts::sectionInShownDoc`) picks "was removed" against "was rewritten" from the document a mounted passage last rendered.
- Fold notes name the anchor slug ("Section port-adapter was removed from section_02.md"), because `runFor` (`column-model.ts`) copies `sentence.rests_on`, which carries no titles, and `SourceAnchorRef.title` is filled only by hand-built runs.
- A replacement's first commit renders the new page with the pre-carry open runs; a per-commit judgement on open runs (`useFocusFollow`) must wait for the carry's commit whenever `carried.current` is set.

## Reading column, focus and keys

`reading-column.tsx` renders one column: paragraphs of `sentence.tsx` buttons, opened `run.tsx` runs, `passage.tsx` source passages, `fold-note.tsx` notes. Each run carries two `FoldCap` buttons (`fold-handle.tsx`): a chevron at its start and one at its end (`data-side="start"|"end"`); there is no gutter bracket. `reading-order.ts::columnOrder` lists the focus targets as `ColumnTarget[]` (`FocusTarget & { parent? }`), so a passage's focus key carries its run parent: reading-order ids can collide between an overview sentence and a cited sentence (both `s1`), hence keys `s|<parent>|<id>` and `p|<parent>|<sentenceId>|<anchor>` (`column-context.ts`).

- Focus is real DOM focus on the target (roving): the column has `tabIndex` 0 only while focus is outside it, and both `FoldCap`s of a run take `tabIndex` 0, so Tab walks through them. Keys (`column-keys.ts`, help rows in `plan/help/shortcuts.tsx`): `j`/`k` and the arrows move, `Enter`/`→`/Space open, `Esc` folds the innermost run around focus, else the run opened last, `Shift+Esc` folds every open run, `←` folds only the innermost run around focus. Outside the column, `useEscapeKeys` (`concept-route.tsx`) folds the run opened last on `Esc` (all on `Shift+Esc`) unless a dialog is open or the user is typing. `f` opens file mode at the first source section, `d` opens the first document's summary page, `a` attaches (summary arm for a sentence, source arm built from the `DocView` for a passage), `g p` and `g e` go to the overviews (`useGoKeys` in `concept-route.tsx`, active only on concept routes).

- An opened cited sentence takes its mark from the citing sentence (`doc.id == citation.summary`), else from its page (`marks.tsx` `citedMarks` / `pageMark`). The plan glyph lists the `plans` of the first sentence of the cited sentence's paragraph and never reads the cited page's `implemented_by` (`sentence.tsx::plansOf`).
- The passage header links to file mode with `?lines=START-END` before the hash (`passage.tsx::passageHref`); file mode has no other line-range convention. Passages come from `GET /api/doc?path=` once per file (`passages.ts::docViewAtom`), cut by `sections`.
- Presence: `PresenceEntry.reading` is a raw string the client sends with the `reading` message (`web/src/plan/api/schema.ts`); nothing in `web/src/plan` sends it, so concept pages do not appear in the presence list.

## Review Loop (Server)

`plan_server/review/` owns restore, suggestions, compare, built notes and open-question counts. `routes::routes()` registers `POST /api/restore` (`Role::Holder`, JSON) and Viewer GETs `/api/turn-sections`, `/api/hashes`, `/api/ref`, `/api/compare`, `/api/at-commit`, `/api/built`, `/api/open-questions` and `/api/implemented-by` (it reuses `concept::links::implemented_by`, so links, titles, state names and order match concept mode). `install` calls `setup::install`, which keeps one `Arc<ReviewState>` (`state.rs`: suggestion box, suggestion-to-sender map, last broadcast open-question counts) in the context extensions; context callbacks capture `Weak<PlanContext>`, so no reference cycle forms. A handler that spawns git copies what it needs out of `ctx.project()` and drops the read guard first, because the watcher waits on that lock. Error bodies carry fixed public messages, never a filesystem path or a cookie value.

**Restore goes through the save path with pinned text.** `restore::restore_file(path, pin, turn_running, force, save)` decides one file and never calls `save` on a refusal. A running turn is refused ("a turn is running"); a pin without the turn-start text or the turn-end hash (the turn created or deleted the file) is refused ("the turn created or deleted this file; ask in chat"). Otherwise the caller's `save` receives the turn-start text with the turn-end hash as the opened hash, so a file edited after the turn comes back as `Changed { current_text, current_hash, turn_start_text }` for the editor merge, and a plan that fails validation as `Invalid`. `turn_routes::restore_path` builds the pin from `TextStore::turn_pin` and `turn_end`, refuses a path outside `doc/` (`save_path_of`: `to_doc_rel` then `check_relpath_syntax`) and answers "not changed by this turn" for an ended turn with neither pin. `turn_running` is sampled per file, so a turn that starts mid-request is never written under. Paths of a completed turn come from `TextStore::end_turn`, called only after `turn_ended` succeeds: it returns the retained changes without rereading disk, so deleted paths survive and turns older than the bridge snapshot's current and previous sessions still work. `force` reaches `save` only for a complete pin on an idle chat. `turn_running()` is false during `Ending`, so a restore can race the closing turn's write ([concerns](../concerns/planning-session-sandbox-limits.md#planning-session-bridge-follow-ups)).

**Suggestions.** `suggest.rs` is the box: at most 20 cards in submission order, scoped to the current holder. `commands::suggest` checks the passage path (syntax, then discovery: a path discovery does not list is refused like a malformed one), reads the holder once under the box lock (`holder_snapshot`: the `BrowserId` that routes frames, the public reference, the name, away) and sends the card and the `sent` status before releasing the lock. A holder change therefore waits on the box, `dropped` always follows `sent`, and the card reaches only the holder named in `sent`. Authoring subscribers fire after the authoring state lock drops and the hub's delivery is `try_send`, so no lock-order cycle exists. `suggestion_answer` (holder only) sends `suggestion_status` to the answering holder's browser and, when different, to the sender; the holder's tabs remove a card only on that status. `setup`'s authoring listener (`follow_authoring`) drains the box when authoring changes hands and sends each `dropped` status to its sender and to the current holder (a holder that never had the card ignores it); a reconnecting holder gets its cards replayed. Never route through `PlanHub::send_to_holder(None, ..)`: it drops the frame, which is why `Authoring::holder_browser()` exists.

**Refs and compare.** Git sees only a validated ref or a 40-hex id. `compare::resolve_ref` rejects an empty ref, one over 256 bytes, one starting with `-`, or one holding a control character or whitespace (`RefError::Invalid`, route 400 `bad_ref`), then runs `git rev-parse --verify --quiet --end-of-options <ref>^{commit}` and accepts only a 40-lowercase-hex answer (`RefError::Unknown` otherwise). Every other call takes a `require_commit` id; paths follow `--` or sit in a `<commit>:<path>` object name after the request-path check. `changed_since(root, commit)` lists each discoverable `doc/` document that differs from the commit (`git diff --name-status -z --no-renames` plus untracked files; a rename is a removal plus an addition), sorted, a path git lists twice keeps its first entry, non-UTF-8 names skipped. `discoverable(rel)` applies discovery's rules to one path (`is_editor_temporary` on every component, outside the summary store): `at-commit` cannot use the current tree as its allowlist because a removed document must stay readable. `text_at` returns `None` for a path missing at the commit or naming a directory or submodule (`git cat-file` diagnostics under `LC_ALL=C`: `does not exist in '`, `exists on disk, but not in '`, `could not get object info`) and `BlobTooLarge` (413 `too_large`) for a blob over `files::doc::MAX_EDIT_BYTES` (1 MiB), checked by size before the read.

**Built notes and counts.** `built.rs` reports `BuiltNote::ChangedAfter { plan, built, .. }` when a product section changed after the plan implementing it was built, and a running note for a running plan; written and retired plans give nothing. The build date is the `**Generated:**` stamp of the run review (`parse_generated`), reported as RFC 3339 UTC seconds, not the raw stamp; the section's change date comes from git. `questions.rs` counts open questions per document and `setup` broadcasts counts only when a batch changes one. A `doc_changed` hash is null for a path with no held text (non-Markdown, outside `doc/`, deleted), and `/api/hashes` omits those paths too.

## Chat Panel and Review UI (Browser)

`web/src/plan/chat/` is the panel and `web/src/plan/review/` the review controls. `ChatRegistrations` (mounted by the dock) owns the work that must outlive the panel: the socket subscription (with its `connect` prop it also opens the socket and attention watcher on routes that mount no panel, such as `/`), queue refill (`useQueueRefill`, so texts returned by an ended chat reach the stored draft), the composer shortcut, `ChatAnnouncer` and the Send-to-author dialog root. The model (`model.ts`) keeps command registries per Jotai store, owns pending commands (senders subscribe to acknowledgements and disconnects only while awaiting a result and never mutate `draftAtom`), reconciles unconfirmed sends by message identity (`model-identity.ts`: text plus delivered quote), and keeps an interrupt intent until `queue_returned` because the server sends `result` first (`chat/dispatch.rs`). The ended transcript stays visible through cleared and new sessions until the new chat's first item.

**Socket and schemas.** `PlanMessage` and `ClientMessage` come from `socketMessageSchema` and `socketCommandSchema` (`api/schema.ts`): the union of `planMessageSchema` and the chat and review wire shapes, because chat and review frames each share one `type` tag. `planMessageSchema` stays the discriminated union the Rust tag-array tests (`wire/tests_schema.rs`, which exclude the chat and review tags) pin. Parse a tagged fixture with `planMessageSchema`: `helloSchema` is strict and rejects the `type` tag.

**Attachments and the formatter.** `format-attachments.ts` `formatMessage(text, attachments)` reproduces the Rust formatter byte for byte. Both sides run the shared fixtures `loom/tests/fixtures/plan_session/attachments/*.json` with the expected `*.txt` (`format-attachments.test.ts` asserts at least ten and compares with `toBe`), so a formatter change needs the fixture and both implementations in one change. Rules: a line-leading `<loom-attachments>` or `</loom-attachments>` in typed text gets a backslash; the block is `<loom-attachments>`, one `[n] source <path> <address>` header per attachment and `>` quote lines, `</loom-attachments>`; a quote is cut at 2,000 characters with `[…N more characters; read the source]`; the address is `stage:<id>`, else the anchor, else the summary sentence (`attachmentAddress`). The composer refuses a delivered message over 100,000 bytes (`CAP` in `composer.tsx`); a whole-file attachment is limited to 16 KiB (`MAX_ATTACHMENT_BYTES` in `attachments/add-to-chat.tsx`, imported by the suggestion cards and the turn footer). Trimming is a linear scan (`trimWhiteSpace`); a trailing-run regex is quadratic on every keystroke.

**Local storage and the checkpoint.** `storage.ts`: `safeStorage` wraps every read, write, remove and subscribe in try/catch and falls back to the initial value; `storageFullAtom` (always written to `getDefaultStore()`) is set only on a quota error (DOMException name, code 22 or 1014) and cleared by the next successful write; `validatedStorage(schema)` falls back unless a read or a storage event parses; `storageKey(projectKey, name)` is `loom-plan:<projectKey>:<name>`, the only way to build a key. Drafts persist per project (`drafts.ts`, zod-validated for both `AttachmentDraft` variants and storage events); before `serverInfo` loads the unqualified key is read as the draft and never migrated. The review checkpoint lives under `storageKey(project, "checkpoint")` (`review/checkpoint.ts`): `{ commit: string | null, hashes: Record<path, hash> }`, `null` when it fails the schema. `changedSince(cp, current)` returns added, changed and removed paths sorted; `markSeen(store, path, hash)` updates one path and does nothing before first-visit initialization, which the review UI owns; "Mark all seen" writes synchronously. `review/live.ts` subscribes to `doc_changed` and refetches `/api/hashes` serially (a burst of frames asks for exactly one more load) instead of patching, because the frame's hash is null for paths with no held text. The changed-since dialog renders checkpoint and ref comparisons with `DiffView`; checkpoint rows stay hash-based even when `getCompare` differs, and uncommitted links use `openDiff` (the file-mode diff router knows only `turn`, `open` and `head`).

**Review controls.** Restore (`restore.tsx`) excludes deleted files using the turn-diff texts and derives the turn-end hash as `planning::sections::normalized_hash` does (SHA-256 of the normalized pinned after-text) for `requestEdit`, because the response's `changed.current_hash` is the current text and would bypass the editor merge. Suggestion attachments use an empty selected hash when the suggested text is gone, so the server reports `changed_since_selected`, and publish the fetched current hash to `hashesAtom`. Send to author keeps its own React root (registration-owned, with the clicking store) because the selection secondary unmounts when the browser selection clears while sender statuses must survive. `EmptyOffer` keeps the `OfferButton` registry; an offer click that must end a chat open on this screen first waits for the ended snapshot (a session open on another screen refuses the offer locally). The start-race matcher covers both the bridge refusals and the authoring refusal "Another browser holds authoring" (named holder). A sent chip finds its session by turn timestamp, preferring the current turn collection, because turn ids repeat across the current and previous sessions. The turn footer takes row counts and deletion status from pinned turn diffs; `summaryLink` (`turn-footer-rebuilt.tsx`) is the single summary-id helper, and it strips leading slashes so a server id cannot become a `//host` link. Tool grouping folds only consecutive top-level tool rows; nested subagent rows are boundaries and pass through unchanged, and Edit/Write file counts use distinct `file_path` strings parsed from the tool input.

**Accessibility.** Server-supplied text renders through `<Untrusted>` (`visible-controls.ts`: a left-to-right isolated block with `unicode-bidi: isolate`, format characters shown visibly). `y` and `n` act only while the pending permission card has focus (the one card sits at the end of the transcript, `transcript.tsx` `PendingDecision`), and a card never takes composer focus. Answered permission rows are `role="group"`. `ChatAnnouncer` is always mounted by `ChatRegistrations` and is the only writer of the per-store `announcedAtom` and `noticeAtom`; the two live regions render inside the sheet's `Dialog.Content` while it is open, because `aria-hidden` (used by Radix modals) leaves existing `[aria-live]` elements visible and hides only those mounted after the modal opens. A repeated request for the same tool is made audible by emptying the region and rewriting it after 50 ms. Focus after "New chat" is read in a `useLayoutEffect` cleanup of the unmounting `ConcludedChat`, because a parent-level cleanup runs after the child DOM is gone and focus is already on `body`.

**Chat home.** A chat belongs to the screen of its feature or plan (`SessionView.feature`, `chat/session-home.ts`); a session owned by another screen shows a notice, not its transcript. ## Web Extension Slots

The extension slots in `web/src/plan/` and what fills them:

- `concept/page-header-extras.tsx` (open-question count and the "Changed after … was built" marker, limited to `product/section_<n>` pages), `concept/key-chip-extras.tsx` and `files/tree-entry-extras.tsx` (the "changed since you looked" mark), `header-extras.tsx` (`ChangedSinceControl`, `ChatSheetButton` when `compact`, and `SummaryStatus`, the rebuild popover with the panel, question and cost lines) and `empty-offer.tsx` (the offer is a button for the holder, or while nobody holds authoring, and runs the registered `OfferButton` handler; viewers and read-only mode see text).
- `concept/key-row-extras.tsx` (`<KeyRowExtras page />`, props exactly `{ page }`) renders `PendingApprovalNotice`, the above-budget notice with its approve button.
- The chat turn footer draws no per-summary cost: `summaries/state.ts` no longer subscribes to the `summary_turn_cost` frame (it stays in `api/schema-summaries.ts` only), and `turn-footer-rebuilt.tsx` lists the rebuilt summaries without a cost.
- Server: `PageContext` carries `read_only` and `rebuilds: Option<Arc<Rebuilds>>`; `state::out_of_date_reason` has the `awaiting_approval` and `failed` arms, `page::progress` the `building` and `estimate` values, and the scheduler subscribes through `ConceptState::subscribe`. A direct `Bridge::start_session` caller (plan 11) holds `ChatState::starting` or a lease from before it reserves.

Slots that still render `null` and are reserved for plan 11:

- `files/plan/plan-actions-extras.tsx` (`<PlanActionsExtras plan path />`, end of the plan header): "Pressure-test" for written plans and the done-plan actions. `header-extras.tsx` takes one more line from plan 11.
