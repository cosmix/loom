# Plan Server

> Plan server

## Module map

Bare `loom plan` runs `plan_server::run(&PlanServeArgs)` (`loom/src/plan_server/mod.rs`): `root::resolve_project` (a git repository, never a `loom/` stage worktree), `server_runtime_paths` (a set `LOOM_PLAN_STATE` is ignored with a warning), `create_runtime_dir`, `lock::acquire`, `start`, `lock.publish`, `announce`, `serve_until_stopped`. `start(ServerOptions)` binds (`web_server::listener::bind_listener`, `DEFAULT_PORT = 7272`, walking forward when no `--port` is given), mints the token (`web_server::token::mint`), builds `BindInfo` and `PlanContext`, runs `routes::install_all`, spawns the watcher and the 1 s tick (`watch.rs`), then the accept loop thread `loom-plan-accept` that calls `web_server::serve`. It touches neither the lock nor the runtime directory, so tests call it directly.

## Shared web_server layer

`loom/src/web_server/` is the transport both servers use. `serve(listener, Arc<dyn Router>, running, ServeConfig)` owns the accept loop, the per-connection timeouts, the head gate and the `Host` gate, then calls `Router::upgrade` (head only peeked: WebSocket handshakes, token bootstrap; return `None` when finished) and `Router::handle` (one consumed head plus body prefix). `ConnInfo` hands the router the connection's own `local` address, the `AccessPolicy`, the `Limits` and the `running` flag. `serve` fails closed before accepting when the policy is remote and carries no `Auth`, waits up to 3 s for connections on stop, and sleeps 50 ms after a failed `accept`. `AccessPolicy::new(local, Option<Auth>)` is infallible; each server builds its own `Auth` (`Auth::new(token, cookie_name)`; `Debug` is redacted). `ServeConfig.thread_name` names connection threads (`loom-plan-conn`). `http::write_response_with_headers` carries extra headers (the planning `Referrer-Policy`). The shared 503 bodies and log lines say "dashboard"; the planning server emits them verbatim.

## Gate order

`gate::admit` runs for every `/api/*` request and `/ws` upgrade, in this order: `Host` (403), exact `Origin` equal to `http://<Host>` on every POST and every WebSocket (403; the dashboard's loopback-alias leniency does not apply), the access cookie `loom_plan_<port>` (401), the browser identity, the body's `Content-Type` and `Content-Length` (415/413, before any body byte is read), then the route's `Role`. The browser cookie is `loom_plan_browser_<port>`; both cookies are `Path=/; HttpOnly; SameSite=Strict`. An HTTP request without a valid browser cookie gets a minted `BrowserId` and a `Set-Cookie`; a WebSocket without one is refused 401 (the app calls `GET /api/server` first). A minted id reaches only `Role::Viewer` routes: on `Holder`/`HolderOrTake` routes it is refused 401, and `Presence::name_of` does not record it, so the presence map is bounded by browsers that send their cookie back. `GET /?token=<token>` with the right token sets the access cookie, the browser cookie when absent, and redirects to `/`; a wrong token or a foreign `Origin` is 403. Planning responses carry `Referrer-Policy: no-referrer`. Bodies are read with `Read::take` bounded by the gate-checked `Content-Length` (`request::read_body`), not `web_server::http::read_body`.

## Route modules

A route module `plan_server/<name>/mod.rs` contributes `routes() -> Vec<RouteSpec>` with one line in `routes::all_routes()` and, if it needs state, `install(&Arc<PlanContext>)` with one line in `routes::install_all()`. `RouteSpec { method, path, body, role, handler }`: `path` is exact unless it ends in `/`, which makes it a prefix; `HEAD` is answered by `GET` routes; `Role` is `Viewer` (any holder of the access cookie), `Holder`, or `HolderOrTake` (any browser takes authoring when nobody holds it). `find()` returns the first match, so `routes.rs` tests `first_duplicate(&all_routes())` for a `(method, path)` collision. Later plans hang their own state on `ctx.extensions()` (one typed slot per type) and register `ctx.on_batch` hooks and `ctx.shutdown()` hooks. `install_hub_hooks` runs first so `hello` is the first frame every WebSocket receives.

## Wire model and parity

Wire types live in `plan_server/wire/` (`message.rs`, `server.rs`, `presence.rs`, `checklist.rs`) and mirror `web/src/plan/api/schema.ts`. `PlanMessage` (`type` tag, snake_case, `deny_unknown_fields`): `Hello(Box<Hello { you, server, checklist, presence, authoring }>)`, `Presence`, `Authoring`, `Checklist`, `ServerStopping`, `Refused`. `ClientMessage`: `SetName { name }`, `Reading { path }`. Two checks keep Rust and TypeScript equal: JSON fixtures in `web/src/plan/api/fixtures/` are round-tripped by Rust tests (`assert_fixture` in `message.rs`) and parsed by the web tests, and `wire/tests_schema.rs` reads `schema.ts` with `include_str!` and asserts every serialized enum value is a quoted entry of the matching exported array. A new wire enum variant, or a changed fixture, needs the schema array and fixture updated in the same change. The dashboard's equivalent is `commands/status/web/schema_parity.rs`; the two helpers differ and are not shared.

## WebSocket

`ws::run_connection` serves one admitted connection: 250 ms socket timeout, a protocol `Ping` every 10 s, `MAX_INBOUND_BYTES = 256 KiB`. The connection holds a `Lane::WebSocket` slot from `web_server::limits` (shared `MAX_WEBSOCKETS = 48`); past it the upgrade answers 503 `busy`. `PlanHub` (`ws/hub.rs`) is the planning server's own hub — it does not use `web_server::hub::Hub`, because it sends to single connections as well as broadcasting — with a 64-frame queue per connection and a slow connection dropped. A connection registers before its `on_open` hooks run, so a broadcast made by a hook (or concurrently) is queued behind the open frames, which are a snapshot at least as new as anything queued before them. `ws::dispatch::dispatch` runs on the connection's own thread between reads and must return quickly; a frame that does not parse as `ClientMessage` never reaches it and is answered `Refused { command: "frame" }`. The server sends only protocol pings, which browser JS cannot observe, so the client has no half-open watchdog until the server also sends a text heartbeat.

## Presence and authoring

`BrowserId` is the cookie value and never leaves the server; `PublicId` is what other tabs see. `Presence` records a browser only through `public_id`, `set_name` and `opened`; names are at most 32 characters (`presence.rs`, matched by `MAX_NAME_CHARS` in `web/src/plan/header/name-prompt.tsx`); the browser that set a name first keeps it and a later namer shows as "Viewer N". `Authoring` (`authoring.rs`) names the holder as a `BrowserId`, so every tab of the holding browser holds authoring. The holder is away once its last connection closes and frees after `GRACE` (600 s) unless a tab reconnects; `Authoring::tick` runs from the 1 s tick with the time passed in so tests drive it. `Take::HolderOnly` never takes authoring; `Take::TakeIfFree` takes it when nobody holds. Refusals: `NotHolder { holder }`, `NoHolder`, `ReadOnlyMode`, `Stopping` (the holder is refused too while stopping). `AuthoringEvent` (`Taken`, `Away`, `Back`, `Freed`) reaches subscribers after the internal lock drops, so two concurrent changes can arrive out of order: treat events as hints and re-read `holder()`. A browser that takes authoring over HTTP and never opens a WebSocket is never marked away, so authoring does not free until restart; no route takes authoring yet. `ReadOnly::detect()` (`prereq.rs`) lists missing tmux, Claude Code or its login, and the Linux sandbox prerequisite; any problem makes the server read-only and nobody takes authoring.

## Shutdown

`lifecycle::line` prints timestamped lines. The first stop signal calls `begin_shutdown`: `Shutdown::begin` first (it sets the stopping flag, so a racing `TakeIfFree` already sees the server as stopping, and drains every registered `ShutdownHook` concurrently, naming the ones still running), then a `ServerStopping` broadcast; the accept loop, WebSockets and routes stay up while hooks drain. The second signal exits at once (`std::process::exit`). `RunningServer::stop` clears the accept flag, stops the watcher and tick and joins them. The watcher and tick share threads with later plans' batch hooks and authoring subscribers, with no `catch_unwind`: a panicking hook silently freezes the project view or the grace timer.

## Runtime directory and lock

The runtime directory is `<loom user dir>/plan/<project key>` (`planning::runtime::server_runtime_paths`; `LOOM_PLAN_STATE` belongs to planning sessions and is ignored by the server). `create_runtime_dir` makes it mode 0700 through `safe_create_dir_all`/`safe_open_dirfd`, which open with `O_NOFOLLOW`: a symlinked `~/.loom` or `$LOOM_HOME` stops `loom plan` from starting. `lock::acquire` returns `Held(ServerLock)` or `Running(LockRecord { pid, url, token })`; the held lock publishes the base URL and token once the server is listening, so a second `loom plan` prints the running server's link through `startup::already_running_lines` (passed through `inline_safe`) and exits 1 with `AlreadyRunning`, or asks for a retry while the first is still starting. The lock opens by path (`lock.rs`), safe because its parents were just validated.

## Open points

Reviewer suggestions nobody implemented, each checked against the tree.

- **Token and hardening gaps.** `browser::open` passes the tokenized URL to `xdg-open` as argv, readable by another local user through `/proc/<pid>/cmdline` while the opener runs; section 02 mandates opening the URL, so closing it needs a spec decision (for example opening a 0600 redirect file in the runtime directory). Refusals written by the shared layer (Host 403, head errors, 503 at the cap) and tungstenite's handshake errors carry no `Referrer-Policy`; the bodies are plain text without links. `lock::acquire` opens the lock by path rather than relative to the directory fd, and no test plants a symlink inside the runtime path. `Auth` and `Admitted` have redacted `Debug`; keep it when adding fields.
- **Unbounded inputs.** No POST route exists yet, so `read_body` has a per-read bound but no total deadline; add a wall-clock bound with the first POST route. `Presence::public_id` records every distinct well-formed cookie for the life of the process, and `set_name`/`reading` broadcast to up to 48 connections with no per-connection rate limit; both need the access cookie.
- **Shared module carries dashboard wording and dashboard-only code.** The 503 bodies and logs in `web_server/unserved.rs`, `head.rs`, `ws.rs` and the accept-error log in `serve.rs` say "dashboard" and reach planning clients; the dashboard's tests pin those bodies, so neutral wording needs a name in `ServeConfig` and a test update. `token::cookie_name` hardcodes `loom_dashboard_<port>`, `auth::resolve_process_token` is dashboard-only, and `web_server/access_tests.rs` imports the dashboard's `ServeOptions`; moving `resolve_process_token` next to `AccessPolicy::resolve` in `commands/status/web/mod.rs` would remove the test dependency on `commands`.
- **Duplicated helpers.** `request.rs::read_body` repeats `web_server::http::read_body` except for the cap (give the shared one a `max` parameter); `ws/conn.rs` repeats `SOCKET_TIMEOUT`, `KEEPALIVE`, `send_pending` and the tungstenite config of `web_server/ws.rs`; random hex minting is hand-written in `web_server/token.rs`, `daemon/server/tokens.rs` and `csrf.rs` (a shared `random_hex(n) -> io::Result<String>` would also remove the `/dev/urandom` panic in `PublicId::mint`, `ids.rs:51`, which runs under the presence mutex); `router.rs` passes `ws::MAX_INBOUND_BYTES` while `mod.rs` builds `Limits::new` with it (read `conn.limits.max_inbound_bytes()`); `gate::check_role` re-derives the public id `router::call` already computed; `web_server/bootstrap.rs:46` drops the `write_redirect` result with `let _ =` while the planning router logs it; `ws/hub.rs::connections_of` is `pub` but test-only.
- **Hook failures freeze things silently.** `watch.rs` runs later plans' batch hooks and authoring subscribers on shared threads with no `catch_unwind`, and `RunningServer::stop` drops the join result. `PlanContext::project()` hands out a std `RwLock` read guard while the watcher takes the write lock: a second `ctx.project()` in one call stack can deadlock behind a waiting writer.
- **Authoring.** Events can arrive out of order (subscribers re-read `holder()`); a browser that takes authoring over HTTP without a WebSocket never goes away; `web/src/plan/state/atoms.ts::canAuthorAtom` lets the holder author while stopping although the server refuses every `TakeIfFree` then, and `authorBlockReasonAtom` is `null` while server state is unloaded. Revisit all three when the first `HolderOrTake` POST route lands.
- **Web shell gaps.** `web/src/plan/api/socket.ts` writes `lastMessageAt` and never reads it (a watchdog needs a server text heartbeat first); the checklist skeleton never resolves to an error when the socket cannot connect (the "Connection lost" banner belongs to the chat panel plan); `header/tabs.tsx` has no narrow-width strategy, so the header overflows at 390 px once plans register about 200 px of tabs; `header/popover.tsx` and `ui/dialog.tsx` use `data-open:`/`data-closed:` animation variants that never match Radix's `data-state`; `header/step-tracker.tsx` marks the current step with `bg-muted` on `bg-card` (low contrast); `header/share.tsx` copy state never returns to idle, so a repeat click announces nothing; `header/presence.tsx` renders a focusable list item with no action.
- **Tests.** `plan_server/tests/mod.rs::an_omitted_port_walks_past_a_busy_default` returns early when 7272 is taken and passes vacuously beside a running `loom plan`; `loom/tests/web_server_contracts.rs` has no loopback skip (failing loudly is defensible for contracts); the share-link test in `plan-shell.contracts.test.tsx` cannot detect a retained tokenized link (stub the third open's fetch as never-resolving and assert the URL is absent); the `wire/tests_schema.rs` helper overlaps the dashboard's and is not shared.
