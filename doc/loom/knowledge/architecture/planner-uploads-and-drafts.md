# Planner Uploads and Kickoff Drafts
>
> Uploads, drafts

Two stores outside the repository, both under the planner's runtime directory, with the commands and transcript rules that use them. Web side: [Planner Web Shell](planner-web-shell.md).

## Upload route

`POST /api/attachments` (`plan_server/uploads/`, installed by `routes::install_all`) takes a raw body and stores it under its content hash. Rules:

- **Role.** The holder, and any browser while nobody holds authoring (`HolderOrTake`): a fresh New work page attaches before its first message takes authoring, and a `Holder` rule would refuse that upload. Another browser's hold, read-only mode and `stopping` still refuse it.
- **Types.** `plan_session::attachments::stored::MEDIA_TYPES`: `image/png`, `image/jpeg`, `image/gif`, `image/webp`, `application/pdf`, `text/plain`, `text/markdown`. The gate refuses a wrong `Content-Type` (415) and an oversized `Content-Length` (413) before it reads the body; the handler then checks the bytes against the declared type (422): magic bytes for images and PDF, UTF-8 for text.
- **Caps.** 10 MiB a file (`MAX_UPLOAD_BYTES`); 256 MiB for the store (`MAX_STORE_BYTES`), past which the answer is 507 with a one-line reason; the whole body must arrive inside the request's 30 s budget (`request.rs` `BODY_TIME_LIMIT`).
- **Storage by content.** `<runtime>/attachments/<first 16 hex of sha256>.<ext>` plus a sidecar `<id>.json` (name, type, size, `stored_at`; read back up to 4 KiB). The same bytes uploaded twice are one file. The directory is 0700 and every write goes through `safe_fs` (temp name opened `O_CREAT|O_EXCL|O_NOFOLLOW`, renamed into place), ordered against the cap check, `touch` and the sweep by one process-wide lock. The runtime directory is not created by `start_with_routes` (only `run()` does), so the handler calls `create_runtime_dir` before the first write.
- **Names.** The display name is the `name` query parameter (percent-encoded, at most 1024 decoded bytes, `MAX_PARAM_BYTES`); the client cuts it to 120 code points before encoding (`attachments/upload.ts`). One `clean_name` in `attachments/stored.rs` strips control and format characters (`context/format_chars.rs`) for both the upload check and the resolver. A name is never used in a path.
- **Answer.** `{id, name, media_type, bytes}`. A chat command names the file by id (`AttachmentInput` kind `file {id, name}`); `plan_session::attachments::resolve_input(project, attachments_dir, input)` maps the id to the absolute path, and an unknown or malformed id is refused. `resolve(project, DocumentAttachmentInput)` keeps its signature for documents, so the document tests are unchanged. The client never sends a path and never receives one.
- **What the session sees.** The delivered block names the absolute path, media type, size and name, and the session reads the file with Read. The planning session sandbox has a read-only grant on `<runtime>/attachments` (`ensure_runtime_grants`, `plan_session/sandbox/mod.rs`, runs before every launch; contract `guard_allows_reads_of_attachments_and_denies_writes`). The transcript chip carries `{id, name, media_type, bytes}`; a Read or Grep tool row of a stored file is shown as `attachment <id>.<ext>` (`transcript/tools.rs` `display_path`), never the runtime path.
- **Expiry.** `uploads::install` sweeps files older than 30 days (`KEEP_SECONDS`) at every server start. Re-uploading a stored file refreshes its `stored_at` (`uploads::touch`), and so does every write of a draft that references the file, so an unfinished draft's attachments live as long as the draft. The sweep opens the store with `safe_open_dirfd` and removes through `safe_remove_in_workdir`; it does not follow a symlinked store directory.

## Kickoff drafts

A kickoff survives its session as `<runtime>/kickoffs/<session id>.json` (`plan_server/chat/drafts.rs`, commands in `draft_cmd.rs`). The session id must be a lowercase hyphenated uuid, because it becomes a file name.

- **Shape.** `Draft {session, started_at, updated_at, messages, shape, attachments, name_override, target, live}`: `messages` are the user's typed texts (at most 40, 4096 bytes each, cut at a character boundary with `[…]`; the first and the newest are kept); `shape` is the agent's last `KickoffShape` without the user's rename; `attachments` are the start command's inputs as the browser sent them (at most 10); `target` is the confirmed document's path, set by `confirm_kickoff`. A file over 256 KiB is not read and none is written larger; a file that fails to parse is skipped with a warning and left in place.
- **Writes.** At start, on every shape change, on every user send, on rename and on confirm, and again with `live: false` on `BridgeEvent::Ended`. Every read-modify-write holds `ChatState::drafts`, because the bridge listener, the dispatch thread and the `Ended` handler all write.
- **`live` is computed on read.** A view's `live` is the stored flag AND the bridge's current chat session being this one, so after a restart every draft reads `live: false`; the stored flag is never read alone.
- **Landed drafts disappear.** A draft whose `target` exists under the project root (any lifecycle prefix of a plan file included) has landed; the store deletes it on its next read or write (and publishes the change to open tabs) and never lists it. Discarding deletes it too. Ended drafts older than 30 days go at server start.
- **Wire.** `GET /api/kickoffs` answers `{drafts: [KickoffDraftView]}`, `KickoffDraftView {session, name, size, problem, started_at, updated_at, live}`; a `kickoff_drafts` socket message carries the same list (both schema arms and a fixture, as every `PlanMessage` variant needs).
- **Commands.** `rename_kickoff {name}` (holder, `is_feature_name`) stores `name_override` beside the tracker's current view, never inside it, so later agent blocks are still compared raw; the override wins in every `KickoffView` and draft view and the server tells the agent in one user message. A rename before any shape exists, and after `confirm_kickoff` armed the write target, is refused. `set_aside_kickoff` ends the running kickoff and keeps its draft. `continue_kickoff` starts a new kickoff whose opening carries the draft: the effective name (as the new draft's `name_override`), the size (`small` for a plan), the whole shape and the attachments that still resolve (one that no longer does is named in the opening as no longer available); the replacement draft is written before the old one is deleted, and a refused or failed start leaves the old draft as it was. `discard_kickoff` deletes an ended draft. Continue takes authoring like a start (`TakeIfFree`) and discard allows no holder, because an ended kickoff has already released the starter's authoring; both refuse another browser's hold.

## The opening in the transcript

The kickoff's first user record is one `<pasted_content>` item holding the generated guidance and the typed text (`guidance/provider.rs` joins them with a blank line). The bridge shows each once, and the seam is a file: when an offer opening is joined with typed text, the guidance provider writes the typed part to `SessionDir::opening_typed()` (`opening-typed.txt` in the session directory, 0600, `write_opening_typed` in `guidance/provider.rs`), and `Session::configure` reads it (`read_opening_typed`, `bridge/start.rs`; absent, unreadable or blank means one item) into `Opening.typed`, so the split never comes from searching the joined text. The opening is then sent as two items, the guidance (a collapsed origin item) and the typed text (a visible user item), and the one recorded prompt replaces both (`plan_session/transcript/opening.rs`). `isMeta` records, which Claude Code writes after a Skill tool result with the skill body as list content, are skipped before their text is used (`records.rs`); Skill tool rows never render. The `loom-kickoff` fence the assistant ends each reply with is for the server only, and `withoutKickoffFence` (`web/src/plan/chat/kickoff-fence.ts`) drops it from assistant text, streaming included ([the mistake](../mistakes/planner-review-fixes.md#a-structured-block-and-a-composite-opening-were-never-replayed-through-the-transcript)).

A sent item and its recorded prompt can arrive in either order: the `UserPromptSubmit` hook confirms delivery (`set_delivery` makes `s-N` Delivered) before the plain human record, so the mapper (`opening.rs`) matches a Delivered sent item as well as a pending one, or both would stay ([the mistake](../mistakes/planner-review-fixes.md#a-sent-item-and-its-record-arrived-in-the-opposite-order)). In the browser, one `commandPendingAtom` guards the Size control and the proposal against a double dispatch.
