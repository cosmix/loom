# Planner Web Shell and Screens

> Shell

The planner web app (`web/src/plan/`) follows `web/src/plan/ui/DESIGN.md`, the design record a designer worker set for the redesign; read it before touching layout, type or colour (`ui/design.css` holds its tokens and the button scale). The brief bundles `doc/plans/feat-planner/briefs/feat-planner-12-ui-repair/` and `feat-planner-13-planner-redesign/` hold the per-screen values each plan used. Product contract: `doc/product/feat-planner/section_05.md`, `section_06.md`, `section_08.md`, `section_09.md`. The feature screens (layout route, spine, offers, pages, wire) are in [Planner Feature Screens](planner-feature-screens.md).

## Header and dock

- **One app bar** (`header/header.tsx`, `header.css`): the logo, `Identity` from `header/feature-switcher.tsx`, the activity pill and responsive controls. The logo is a home link named "Loom planner home" (32/40/56px by width, frozen `activity-fixes` contract). The bar follows the dashboard header (`web/src/components/header.tsx`): 16px block padding and its card-to-background wash (`header.css`, a deliberate exception recorded in `ui/DESIGN.md` Surfaces). At widths of at least 1024px the controls are the Home and Files links with the registered views (`tabs.tsx`), presence, share, theme, Settings and Help; narrower layouts use `overflow.tsx`. There is no Product or Engineering tab, no step rail and no next-step card: a feature's progress lives in the spine. `HeaderExtras` (`web/src/plan/header-extras.tsx`, prop-less) renders `HandoffMounts` and, on every `hasChatPanel` route, `ChatSheetButton` (`chat/panel-collapse.tsx`), which from 1280px (`DESKTOP` in `chat/sheet-state.ts`) shows only while the side panel is collapsed and then expands it ([placement](#chat-home-and-the-chat-panel)); that width is not the header's own 1024px layout switch. Nothing sits under the app bar: a pressure run's progress is the activity popover's pressure row (`header/activity-rows.tsx`): plan file name and current step, round x of y, elapsed time and a determinate bar.
- **Switcher** (`feature-switcher.tsx`): one button holding the eyebrow over the title and a chevron, with one hover surface and the label as its accessible name. Its menu lists features only, by slug, the route's own with `aria-current` and a check; Home and New work are not entries (the logo goes home). `useIdentity` names what the bar shows: a feature route gives "Planning · feature" over the slug; `/new` gives "Planning · new work" over "Untitled", or, once a kickoff has a size, that size's eyebrow over the name so far (the rename included, from the live kickoff or the draft of `/new?session=`); files give "Planning · files" and everything else "Planning · project" over the project name. The eyebrow reads the shape's size but not the start offer, which `KickoffHead` also reads ([follow-up](../concerns/planner-ui-repair-followups.md#planner-review-fixes-unchecked-here-and-reviewer-suggestions)).
- **Footer** (`shell-footer.tsx`, drawn by `PlanShell` under the routed page and dock): `PlanFooter` draws the dashboard's `QuotaMeters` (`@/components/quota-meters`) from `summaryPanelAtom`, with no `quota_left`, and names a provider the panel reports nothing for ("Claude limits unavailable", "Codex limits unavailable"). It is empty until the summary feed has answered, so it never claims limits are unavailable before it knows. The footer is the only place the limits are drawn (Settings shows none). `.plan-footer` (`ui/design.css`) copies the dashboard footer's grid (`routes/shell.tsx`): from 1024px a `minmax(0, 1fr)` track holds the meters and an `auto` track the "unavailable" notes; under 1024px the tracks stack. `QuotaMeters` sets `container-type: inline-size` and picks its layout by container query, so it needs a track with a definite width ([the mistake](../mistakes/planner-polish.md#the-footer-meters-stacked-because-a-container-query-component-sat-in-a-flex-item)). `SummaryFeedHost` (mounted by the shell while signed in) runs `useSummaryFeed` into `panelLoadAtom`, so the footer, the pill and Settings share one feed.
- **Activity pill and popover** (`header/activity.tsx`, `activity-rows.tsx`, `use-activities.ts`, `activity.css`): `ActivityPill({ compact, sample })` reads the shell's feed (`panelLoadAtom`, `summaryReloadAtom`), so rebuild progress shows while the popover is closed; a summary question opens the popover without taking focus. `sample` omits the run, changed-since and summary footer (help scenes). The popover draws no quota meters and no token totals: the limits are in the footer and the totals in Settings. The pill's trigger is the planner's one roundel, the global activity sign; a rebuilding summary row shows the arrow spinner ([busy signs](#roundel-and-busy-text)).
  - *List.* `ActivityList` draws one row per thing in progress, in one anatomy (glyph tile, title, sub line, time). A running plan is one row, "Plan running" with the plan name and "M of N stages merged" (`stagesMerged`, `RunRow`); the run data has no document or run-start field, so a drafting row reads "Drafting <document>" with the session name and the run row carries no start time. A kickoff waiting for the user is a row titled by the session brief (`BriefTitledRow` fetches the brief only in the live list, because the Help sample pill shares `useActivities` and its test asserts no fetch) and links to that session's screen (`/new?session=<id>`). A running rebuild is one disclosure row (`SummaryRow`) that opens `StatusContent` (the question, a read-only note and `RebuildActivity`: queue, failures, start error); its accessible name is `summaryRowName` ("Summary rebuilds: <visible title>, <subtitle>", WCAG 2.5.3), and one `useSummaryExpansion` state lives in `LivePill` so the detail survives a rebuild starting or ending.
  - *Footer* (`.activity-foot`): the idle summary row (`SummaryStatusRow`) first, wrapped in `.activity-foot__scroll`; then `RunLine`, which draws a stopped run as one footer control line (and nothing while the run is listed above); then `ChangedSinceControl`, a `<button>` named "Changed since you looked · N" that navigates to `/changes` ([the page](#changed-since-and-seen-text)). The footer shrinks only when the scroll wrapper exists (`:has`), so the run and changed-since lines keep the bottom edge while `.activity-scroll` and the detail scroll. `SummaryPanel` (`summaries/summary-panel.tsx`, frozen `summaries/contracts.test.tsx`) is mounted by Settings' Summaries group (`settings-sections.tsx` `SummariesGroup`) and draws no `QuotaMeters`: its statistics are **Token totals** as two figure cards (`summaries/token-figures.tsx` `TokenCards`: a mono total, a stacked monochrome bar of `role=img` segments, a four-figure legend, and a daily-average tick on Today; the two periods are divided by one hairline, not boxed, and a container query on a child of `.sp-cards` sets two columns from 480px), then the last rebuild as one row (a tone dot and a fresh, cache-read and output `dl`), an Idle line while nothing runs and Retry on failed rows; the count-up animates only when `(prefers-reduced-motion: no-preference)` matches and `(prefers-reduced-motion: reduce)` does not. Styles are `summary-panel.css` (`.sp-*`), no Tailwind, and the group's hint names no provider limits. The reading face, size and preview sections live in `settings/reading-sections.tsx` with `reading.css`: the **specimen** (two preview lines in the chosen face and size, framed as a `figure` above the face and size choices) and **size tiles** (three radio tiles, each a page picture from `size-picture.tsx` over its label; the native radio group keeps the keys). The theme control is the shared `components/theme-picker.tsx`: Ledger, Walnut and Graphite ([themes](#themes)); `SummaryStatus` and `StatusTrigger` have no production importer and are mounted by `summary-status.test.tsx` and a frozen contract only ([follow-up](../concerns/planner-ui-repair-followups.md#planner-issue-fixes-reviewer-suggestions)).
  - The popover opens by itself on arrival when summaries are out of date, covers the reading column and swallows clicks; `web/scripts/plan-journeys-kit.mjs` dismisses it with Escape and prints a NOTE.
- **Share** (`header/share.tsx`): the dialog shows the URL with Copy and, on a remote bind, the plain-HTTP warning. `ShareLink` has no tunnel field; the dialog fetches the link on every open.
- **Dock** (`dock.tsx`): `hasChatPanel(pathname)` is false on `/`, so no `ChatPanel` mounts there. `ChatRegistrations` is always mounted; its `connect` prop (true when there is no panel and the path is not `/new`) opens the chat socket and attention watcher that `ChatPanel` owns wherever it is mounted ([the mistake](../mistakes/planner-ui-repair.md#hiding-chatpanel-on-the-home-route-dropped-the-socket-and-notifications)).
- **Help is a lazy chunk.** `shell.tsx` loads `PlannerHelpDialog` through `React.lazy` and `Suspense`: its topics and scenes would put `plan.js` at 514 kB, over vite's 500 kB chunk warning; lazy it is 476 kB. A `src/plan/help` `codeSplitting` group does not work, because groups pull their dependencies in recursively (1 MB), and an icons vendor group reaches only 499.3 kB. Tests await the dialog with `findByTestId`. Revisit if help must be available offline from the start.
- **Tokens.** `plan.css` defines `--plan-shadow` on `:root` and `.dark` (not under `[data-loom-plan]`, because the activity popover portals out of the shell) and `--popover-lift`, the popover's second drop, on `:root` only (the value is the same in both themes); `POPOVER_SHADOW` is `var(--plan-shadow), var(--popover-lift)`. Tailwind utilities outrank `@layer components` CSS, so a popover's size and surface go through `className` plus inline `boxShadow`, and Settings uses unlayered `settings/settings.css` (`.ps-*`) over the shared `theme-picker.tsx`. 390px must not scroll sideways.
- **Buttons.** One unlayered `.plan-button` rule set in `ui/design.css` keyed by `data-look` (`quiet`, `secondary`, `primary`) and the button's own `data-size` sets every look. `DisabledReason` (`ui/disabled-reason.tsx`) and `OfferButton` take an optional `look`, default `secondary`; a caller that wants the screen's primary fill passes `look="primary"`, and no caller restyles through `[&_button]:` wrappers. `INLINE_BASELINE` (exported from `disabled-reason.tsx`) is the shared inline class for `PLACEMENT.inline`, `ChipRow`, `RebuildButton` and both approval-notice wrappers. Tailwind utilities lose to the unlayered rules on a `.plan-button`, so a state such as the current item is expressed in an unlayered rule (`ui/doc-heading.css` `aria-current`).
- **Read-only server.** The banner alone carries the problem and the fix; a blocked control's reason is the single word "Read-only", the chat head draws no hazard and queue rows draw no blocked buttons.

## Home and kickoff

- **Home** (`home/`): the invitation is the first `li` of `ul.card-grid` (`FeatureCards` `lead`) and spans every track as a band (doodle, words, the screen's one primary), stacking under a 40rem container; on an empty repository it stands alone, upright and centred (`data-empty`). `.home` is `position: relative` so its sr-only text stays inside the shell's `main` scroller. `FeatureCards` orders features by `byAttention` (`attention.ts`): running plans, then open questions (sum of `sections[].open_questions`) or open findings (`candidates`), then work under way, then finished features with nothing open, which draw `data-quiet` (no card fill). A card's link is named by the feature slug and described by the step count and the `FeatureStatus` list ("Needs attention": plans running, open questions, open findings, not pressure-tested); `ProgressStrip` is a visible `ol` of six step marks with each word in `.sr-only`. Above the features sit the **Unfinished** shelf (`drafts-shelf.tsx`: one row per kickoff draft, newest first, titled by `draftTitle` — the name, else "Untitled · <date>" — with the problem's first line and a live or set-aside status; each row opens `/new?session=<id>`; nothing renders without drafts) and the move offers.
- **Standalone plans** (`standalone-shelf.tsx`, `standalone-table.tsx`, `move-into-feature.tsx`): a `section` named "Standalone plans" holding a `details` that starts closed (open when the list is empty, so its explanation shows; frozen `features.contracts.test.tsx` pins the closed start, a summary containing "<n> standalone plans" and plan links inside the details and outside the summary). The summary counts plans per state under the count. The body is a table of every plan, uncapped: a select box, the title (the link, covering the row; `shortTitle` drops a leading "Plan:") over its slug, the state as a glyph and a word, and Modified (`last_change` on `StandalonePlanView`, the plan file's mtime from `files::plan_view::last_change`, null when unreadable; relative within a week, else a short date, the full time as the `title`). Headers sort (`standalone-order.ts`), Modified descending by default, an unreadable time last in either direction. With two states or more, `StateFilter` (`state-filter.tsx`) offers All and one counted `aria-pressed` toggle per state the list holds; toggles combine, filtering runs states first, then the text, then the sort, and `useStateFilter` unselects a selected plan the state filter hides (also when the list changes under it), while the text filter keeps hidden selections. From `FILTER_FROM` plans a field narrows by title or slug; selection survives filtering and the header box acts on the plans shown. A selection bar on the filter's line offers Move to feature for all selected plans at once (`MoveIntoFeatureDialog`, one chat message naming every path, one per line; the wording names `doc/plans/<feature>/` when every path is a standalone plan, else the misplaced-document wording). Under 600px the table becomes blocks; explicit `role` attributes keep the table semantics that `display: block` drops in WebKit.
- **The threshold** (`/new` with no session, `empty-kickoff.tsx`, `threshold.css`; design record `ui/DESIGN.md`, New work). One centred 44rem column under a faint accent wash: the doodle drawing its thread over the heading in the reading face, then one round field holding the kind switch, the words, the attached documents and the foot, then the starter pills and a note. `KickoffRoute` renders `/new` as the threshold always; while a kickoff runs, `OpenDraftNotice` above the form reads "<name or Untitled> is still open" with Continue and Set it aside. The foot is Attach's glyph and Start; the reason or keys line is right-set before Start at every width and, under 480px, leaves the flow (clipped, still Start's aria description). After an attachment the attach button reads "Attach another" and the foot shows "Enter to send · Shift+Enter for a new line". Starters (`kickoff-starters.tsx`) are words alone: only a finding pill carries a glyph. In `threshold.css` a `:last-child` pseudo-class weighs as a class, so a reset of the foot's auto margin must name `:last-child` too ([the mistake](../mistakes/planner-follow-ups-delivery.md#a-css-reset-lost-to-a-last-child-rule-and-the-mockups-two-frames-disagreed)).
- **Kind of work.** `KindControl` (`kind-control.tsx`, `kind-control.css`) is three native radios in one pill track: Feature, Standalone plan (`KIND_WORD`, exported from `kickoff-head.tsx`) and Follow-up, each named by its label and described by a one-line hint through `aria-describedby`. Add plan preselects Standalone plan. Choosing Follow-up shows the **feature picker** (`feature-picker.tsx`, `feature-picker.css`, `follow-up-features.ts`): a floating listbox anchored to the track and listing the features that have a metaplan (done or not), each with a progress ring, `aria-activedescendant` on the listbox, the focus ring on the active option, closing on focus-out, and the sentence "No feature has a metaplan yet." when none. The picked feature shows as a chip beside the track; `followUp` preselects it from a link, applied once the features arrive. A follow-up is a feature chat, not a kickoff: `useKickoffStart` starts the Plan follow-ups offer for the picked feature (`PLAN_FOLLOW_UPS_ID`) with the typed words and documents, never sets `kickoffSessionAtom`, and `kickoff-route.tsx` then navigates to `/f/<feature>/metaplan`, where the chat panel carries the session.
- **Live kickoff and draft.** `/new?session=<id>` is the conversation while it runs, else `DraftView` (`draft-view.tsx`: problem, decisions, questions and the user's messages, with Continue this draft and Discard; it refetches when its `live` flag turns false). Its page grid, `.kickoff-page` in `kickoff.css`, is `1fr | 44rem text column | minmax(17rem, 1fr)` and applies only to the live conversation and the draft, so the head never moves when Taking shape appears. `KickoffHead` (`kickoff-head.tsx`) is the Hearth chat head over a hairline: the work's name as the one heading, else "New feature", "New standalone plan" or "New work", and under it the state in a few words with no eyebrow and no busy sign (the transcript's starting card or working turn carries the pane's one; the head draws its six state words itself, because mounting `chat/state-line.tsx` `StateLine` would add a second `role=status` region, [the mistake](../mistakes/planner-follow-ups-delivery.md#a-component-that-owns-a-live-region-was-mounted-a-second-time)). `kickoffSessionAtom` holds this tab's own start and is cleared when `/new` unmounts before the session arrives, so a later `/new` shows the threshold. Wire, storage and commands: [Planner Uploads and Kickoff Drafts](planner-uploads-and-drafts.md#kickoff-drafts).
- `useProposalActions` is exported from `proposal.tsx` for the Size control (`shape-size.tsx`); the Size control and the proposal share one `commandPendingAtom` that `useProposalActions` checks and sets before it sends, so one click on a shape choice sends one message ([the doubled send](planner-uploads-and-drafts.md#the-opening-in-the-transcript)). `TakingShape` (`taking-shape.tsx`) draws Problem, Decisions and Questions as rows (never the agent's JSON), a Name row that is editable until the work is confirmed (`rename-field.tsx`; the write button and notice appear when a shape exists), and the draft view reuses its row components. A kickoff attachment (`kickoff-attachments.tsx`) imports `chat-chips.css` itself.
- Server strings go through `SentenceText` raw: it escapes format characters itself after parsing, so pre-escaping with `visibleControls` changes the Markdown parse.

## Reading column

`concept/column-keys.ts`: `j`/`k` and the arrows step through DOM stops in document order (`step`): openable closed sentences (`[data-sentence-id][role=button]`) and `button.concept-run-cap`; plain sentences and passages are reached by clicking. A focused element holding stops (an opened run group, a passage) stands on its first stop. `foldAll` (Shift+Esc on a cap or the header path) moves focus to the outermost opener explicitly: Chromium blurs a focused element as it is removed, `onBlur` (`column-focus.ts`) clears `insideRef`, and `useFocusFollow` would never restore focus. jsdom does not blur on removal, so tests call `blurOnRemoval()` from `reading-column-harness.tsx`.

- **Colours** come from the server: `plan_server/concept/key.rs` gives each key chip `index % 8 + 1`, `body.rs` uses `colour_of(chips, doc.path)` with 0 for a document outside the key (the vision citations on a product overview). No client module assigns document hues; they stay `--doc-1..8`.
- **Document key** (`document-key.tsx`): a one-line lede (`keyLede`: "Key: the N sections of this feature" on a document page, "Sources: the … this overview summarizes" on an overview), then a link per document showing its glyph, its short label and its title on a fixed-width track, the first four plus a "… n more" chip (`Ellipsis` icon, sr-only text), and the mark legend; no "Fold all". The title (`chipTitle` drops a leading "<n> — ") is drawn whole in the DOM and cut to the chip's width by CSS alone (`.concept-key-title`), so the link's accessible name keeps all of it; a Radix tooltip repeats it above the out-of-date or implements note, never a native `title`, which would show a second tooltip. A document that changed since the reader looked gets the word "changed" after its chip (`key-chip-extras.tsx`, `role="img"` named "changed since you looked", the name the file tree's marker uses; a frozen review test pins both), not a dot. Per-page expansion state lives inside the component, keyed by page: a React `key` on the component would drop focus and reset `PendingApprovalNotice`.
- **Cited pages.** `concept/cited-pages.ts` prefetches the summaries the page's own document links name (key chips and marks), not raw citations, so a plan deleted since the overview was committed fetches nothing. An opened run reads Loading until every cited page has arrived, because `loadConceptPages` commits through `Promise.all` (`page-state.ts`).
- **Headers.** `ui/doc-heading.tsx` is a grid of blocks (`doc-heading.css`): breadcrumb, title row (mark and title only), the toolbar bar, the status card, the facts line, then the caller's children. The bar (`.doc-heading-toolbar`, bordered) holds the view switch and the caller's `actions`, each wrapped in `ToolbarGroup` (`.doc-heading-group`, divided by rules, collapsed by `:empty` when nothing renders inside); `concept/page-heading.tsx` passes two groups, the settle control and Edit / Discuss / Open all. `HeadingChip.kind` splits the chips: `status` (default) rows go to `StatusCard` (`ui/doc-heading-parts.tsx`, `ul.doc-heading-status.plan-surface`, named "Status"), `fact` pairs to `FactsLine` (`dl.doc-heading-facts`). A status row (`li.doc-heading-row`) holds the chip (a link, a pressable button or a span carrying `data-chip`, `data-tone` and the tooltip, with its glyph span always drawn, empty without an icon, then `.doc-heading-chip__label`), then `chip.detail` in `.doc-heading-row__detail` and `chip.action` in `.doc-heading-row__action`; the row carries `data-action` when it has one. The file-mode tests (the `doc-heading-view` tests under `files/`) read `data-tone` and the glyph from the interactive element itself, so the chip element, not the row, carries them. `page-heading.tsx` orders the summary status first, then open questions, then the plan state and pressure, and marks Implements and Built by as facts. The heading is a size container (`container-type: inline-size`); the bar stacks under 40rem and a row's action drops under its words under 30rem through `@container`, which jsdom ignores: tests pin the rules in the sheet text (`doc-heading.css?raw`). The "Built by" chip derives from `ConceptPage.implemented_by`; a locked Edit gets its title per `LockKind` (`LOCK_TITLES`); a summary page drops the path row and offers Open all only; `files/plan/plan-actions-extras.tsx` renders done-plan follow-ups. `passage.tsx` takes optional `leading`/`trailing` so a run's caps sit on the first chip line and after the last body. `markdown/render.tsx` suppresses a body H1 equal to the document title after `normalizeTitle` strips backticks, so a title holding a code span is not drawn twice.
- **Heading anatomy.** The heading's side inset is `--doc-heading-inset` (default `--space-5`, the source view's `px-6`); `.concept-page-column` (`concept-route.tsx`) sets it to 0 so header, key and text share left and right edges. A summary page's Rebuild is the `action` slot of the status `HeadingChip` (`SummaryAction` in `concept/page-header-extras.tsx`: `ApprovalAnswer` while a rebuild waits for approval, else `RebuildButton`, both `look="quiet"`) and the pending rebuild's sentence is its `detail` slot (`SummaryDetail`, drawing `ApprovalSentence`); `summaries/approval-notice.tsx` keeps `ApprovalNotice` and `PendingApprovalNotice` (button and sentence on one line) for the overview head, and the three share `useAnswerApproval`. Every test that mocks `./page-header-extras` must export `SummaryDetail` too. `PageHeaderExtras` renders `.doc-heading-extras` (run actions, then the build marker in `.doc-heading-extras__marker`, both hidden by `:empty`). The shell's `<main>` scroller (`shell.tsx`) is `relative`, so the key chips' and chips' sr-only descriptions take it as their containing block instead of the body and never lengthen the page; a page whose summary state is null shows no chip and so no Rebuild (the server sets a state for every expected id, `evaluate.rs`, so this lasts only while a cached evaluation predates a new document). An overview has no `PageHeading`: its Open all / Fold all is `OpenAllButton` (exported from `page-heading.tsx`) rendered by `OverviewHead` in `concept-route.tsx`. `design.css` is unlayered, so a Tailwind utility cannot override `.plan-page-title`; a two-class selector in a component stylesheet does (`ui/doc-heading.css` `.doc-heading-title-row .plan-page-title`).
- **Run hairline.** A level-1 run's hairline sits on `.concept-run > .concept-sentence-wrap` (`concept/concept-runs.css`). It cannot hang on the run's span: a member opened to passages splits that span into several inline boxes, and a `:has(> .concept-passages:first-child)` rule then hides the whole run's border, so later members read as closed level-0 prose.
- Open runs fall back to an `unkeyed` `storageKey` segment before `hello`, so view state survives a reload in a store with no `serverInfoAtom`.
- **Fragments.** A fragment is a run of consecutive sentences that open to the same content (`concept/fragments.ts`, `openKeys`: one key per cited sentence, else one per source section). `mergeFragments` builds the column's view of a page once, caching it per `ConceptPage` in a `WeakMap`, and turns each fragment into one merged sentence (the lead's id, the members' texts joined by a space, the unions of marks and citations through `citationKey`), so open runs, reading order, carry, Open all and the keys need no other change; two adjacent sentences citing one table render as one fragment and open the table once. Grouping is on the client because the server cannot know adjacency inside an opened run, where cited sentences from several summaries stand side by side. A sentence with no citation is not a button and never joins a fragment. `anchorKey` and `CitedLookup` live in `cited-lookup.ts` (re-exported by `open-state.ts`), because `carryNested` calls `fragments.runSentences` and importing them from `open-state.ts` would close a cycle. `sentence.tsx` draws each member in its own span.
- **The at-rest marker.** A merged sentence (`.concept-sentence-wrap[data-fragment]`, `concept-runs.css`) shows a 1px inset `box-shadow` bottom edge at 35% of `--sentence-colour`, on the property the hover edge (2px at 85%) also sets and at lower specificity, so hover replaces it without stacking and adds no transition. 35% measures at least 1.60:1 on Ledger and 1.96:1 in Walnut and Graphite across the eight document hues; a 6% tint is under 1.1:1 and would not read.
- **Same passage.** A passage opened under two citers is shown under each (`PassageBlock` takes its `parent`, and the focus key includes it); a repeat inside one view collapses to `SamePassageLine`, a `p` reading "Same passage as above" that scrolls to the first showing. It is a block `p`, so chip, reference and end cap sit on separate lines.
- **Fold caps and focus.** The fold cap keeps a 1.5em round padding box (min 24px) around the 1.1em chevron with no background, so the line box keeps the old footprint and the focus ring is a circle (999px radius); the chevron rests at 0.85 opacity so every theme passes 3:1. Roving focus (`column-focus.ts` `useRovingFocus`): `move(key)` always sets `want` and `setFocusKey(key)` and bumps a `useReducer` counter, so one commit follows and the layout effect focuses the post-commit element; a direct `focus()` would hit the run group or sentence that `foldRun` or `openSentence` removes in the same handler (a second focus event and a scroll to the departing element). Pinned by `fold-caps.test.tsx` "a cap click focuses the folded sentence once and never the departing run".
- **Plan summaries read in levels.** A sealed plan summary opens its opening sentences, then the detail sentences they cite, then the source passage with its link (`plan-page-opens-two-levels-then-source`). **Add to chat** is a pill beside the selection; its hairline rule is drawn only when the primary and a secondary action are both present.

## Chat home and the chat panel

A chat belongs to a screen. `SessionView.feature` (`plan_session/model/mod.rs`) is persisted in `SessionRecord` (`session.json`, `bridge/registry.rs`) and read by `Session::view`, so a recovered closing session keeps its home; `set_owner` (`bridge/owner.rs`) names it for a kickoff that confirms later. `chat/session-home.ts` resolves the home: `session.feature` for a chat, the plan's feature or (standalone) `PressureRunView.plan` for a pressure run, and none for a kickoff, a move-into-feature or New chat on `/files`, which show on every screen. A session whose home is another screen shows the "elsewhere" notice (`ElsewhereBody`), not its transcript.

- With an open session on another screen, an offer or New chat refuses locally ("Finish the session in <feature slug or plan title> first.", `chat/offer-flow.ts`): no confirm, no end, no composer. No code path re-fires an offer on navigation or after Cancel (`confirmEndFirst` runs only from clicks). A kickoff start on `/new` refuses too (`new/kickoff-route.tsx`). ## Changed since and seen text

`review/changes-page.tsx` is the routed page `/changes`, full width so a side-by-side diff has room (the list column sits beside the diff from 1024px, `SIDE_BY_SIDE`); `review/changed-since.tsx` holds `ComparisonList`, `ChangedSinceControl` (the popover's footer row) and `changesFrom`; the rest is `changed-since-data.ts`, `seen-text.ts` and `checkpoint.ts`. The checkpoint is the commit the browser last acknowledged; a document's diff starts from the text the viewer last saw, not only from that commit.

- **The page.** Arriving puts focus on the heading, so a screen reader starts at the title. The popover row is a `<button>` that navigates to `/changes` with `state.from` (the page it was opened from, kept across reopening) and closes the popover by focus-outside: the page focuses its H1, which dismisses the non-modal Radix popover, and Radix skips the trigger refocus after an outside interaction (pinned by `changed-since.test` "opening the page from the popover closes it without returning focus to its trigger"; a `PopoverClose` would throw outside a popover, where tests render the control). `ChangedSinceControl` renders nothing outside a router (`useInRouterContext`), because the frozen `ActivityPill` contract tests mount the pill with no Router. An empty list reads "Nothing changed since you looked" with the way back (`from`, else Home) and takes the focus Mark all seen's button held. `changesFrom` takes only a same-origin path: it rejects a non-string, a leading `//` and a leading `/\`, which browsers read as `//`.
- **Seen text.** `seenTextsAtom` (`projectPref`, key from `storageKey`, name `seen-text`) stores the text a viewer read per path, so a diff stays computable when the checkpoint commit is gone from the repository (contract "seen text outlives a missing checkpoint commit"). Read it reactively through the atom: the contract remounts through the kit's `mount()`, which names a fresh `project_key` per call, and a store captured at mount would miss the same-page reload. `DOC_LIMIT` is 256 KiB per document, `TOTAL_LIMIT` 2 MiB per origin. The total is enforced across every project's `loom-plan:<key>:seen-text` key, because the browser's quota is per origin and every repository's planner serves on port 7272: the current project's entries come from its atom, the others from `localStorage` (`otherStores` walks `length`/`key` directly inside a try/catch, not through `safeStorage`), the least recently seen go first, and size is the JSON length times 2. `storageFullAtom` raises the storage-full banner when a write still fails.
- **Opening a diff marks it seen.** The open document stays listed (status "seen", `aria-current`) after its diff acknowledges it, and a click on the already-open row does nothing, so a "Show diff" re-click during a live refresh cannot race a row that left the list. A row is two lines at every width (path full width; status and since-commit left, action right) because the list column (about 44%, minimum 420px) cannot hold all three on one line.
- **Mark all seen** (`useMarkAllSeen`) reads each listed document through a `READ_CONCURRENCY` (4) pool and stops once the bytes read pass `TOTAL_LIMIT`. A read that succeeds at a hash other than the checkpoint's is skipped and deletes the entry that no longer matches. A generation guards stale diff responses: `checkpointGenerationAtom` sits beside the checkpoint atom and every `checkpointAtom` write bumps it; `markSeen` writes through an internal atom that does not bump, so a mark-all during a diff fetch keeps the newer baseline. The counter is not part of the stored `Checkpoint` object, which five `toEqual` assertions pin and which gains nothing, since an in-flight fetch never survives a reload.
- **Test kit.** `changed-since-test-kit.tsx` answers `/api/compare` for `c1` only: a test that opens a diff after Mark all seen with checkpoint commit `c2` and no seen text sets `replies['/api/compare?commit=c2']`, or the row hides its Show diff button.

## Roundel and busy text

Busy and state signs follow five rules (`ui/DESIGN.md`, Status):

1. **Roundel** (`BusyRoundel`, aurora-ui): only the header activity pill's trigger (`header/activity.tsx` `PillGlyph`), the global sign that something is happening. When the most urgent activity is a your-turn kind (permission, waiting) the trigger shows that kind's bell or LED instead.
2. **A state word** ("Running", "Drafting", "Rebuilding", "Working", sending, restoring, uploading, loading a brief): the two-arrow `ArrowSpinner` (`ui/spinner.tsx`, lucide `RefreshCw`), static under `prefers-reduced-motion`. `BusyText` (`ui/busy-text.tsx`) leads its words with it; `SUMMARY_STATE_GLYPHS.rebuilding`, `PLAN_STATE_WORD_GLYPHS.running`, `StateMark` and `ActivityTile` for state-word kinds are it.
3. **The item or action itself** (a plan, a document, a pressure test, a Codex review, a chat): the LED status dot. `ActivityGlyph` (`ui/activity-glyphs.tsx`) draws it for every kind but permission, green and pulsing when live, gray and still when paused; `PLAN_STATE_GLYPHS.running` is `LiveDot`. Pick by what follows the mark: a plan row led by its name has the dot, the "Running" chip the arrows. In the pressure chat a running step (Codex, `/pressure`, `/address`) is rule 2's `ArrowSpinner`, one per running step even side by side (`chat/pressure/pressure-timeline.tsx` `StepGlyph`); the Codex card tile and the run head rest (`Search`, `FlaskConical`). A dot always has a word beside it.
4. **Block states**: `LoadState` (`ui/load-state.tsx`, `load-state.css`) is the one loading, empty, not-found and error state, centred on both axes in its container (`flex: 1 1 auto`, and `min-height: 100%` as an only child), `size="page" | "compact"`. Loading draws `Spinner` (a 20px ring) under `role="status"` and fades in after 160ms; the others a quiet lucide icon, only the error one toned. Its container needs a definite height or the state sits at the top.
5. **Counted work**: a progress bar (the pressure strip).

`DisabledReason`'s `reason` is a `string | null` rendered through `Untrusted`, so busy strings passed to it stay plain text. For an "every X uses Y" change, `rg` every other implementation across `web/src/plan` before calling it done ([the mistake](../mistakes/planner-polish.md#an-every-x-uses-y-issue-was-judged-fixed-from-one-surface)).

## Themes

Four themes, in `web/src/aurora-ui/shared/styles/tokens.css` (the shared base) and `web/src/index.css` (the planner's overrides); the dashboard and the planner share them, so a change reaches both. **Ledger** is light with the amber `--primary` `oklch(0.84 0.155 80)`; **Walnut** is a dark theme (`.dark`, hue 55, background `oklch(0.19 0.014 55)`) and **Graphite** a neutral dark charcoal at hue 270 (`.dark[data-dark-theme="gray"]`, id `gray`). **Aubergine** is a dark purple at hue 325 (`.dark[data-dark-theme="aubergine"]`). Walnut and Graphite take an orange `--primary` and `--ring` `oklch(0.74 0.15 55)`. Their warning tones (`--tone-warning`, `--hazard-warning`) are amber at hue 80, 25 degrees off the accent so a warning never reads as the accent; Ledger's warning stays orange beside its amber accent. The atoms default to `ledger`/`aubergine` (`aurora-ui/shared/atoms/theme.ts`), so the dashboard's default dark is Aubergine and `ThemeProvider` always sets `data-dark-theme`; the planner seeds Graphite for an empty key (`plan/theme-default.ts`); the dashboard picker offers all four; the planner's offers Ledger, Walnut and Graphite through `ThemePicker`'s `themes` prop. The light `gray` and `cool` variants (`tokens.css`) have no picker ([follow-up](../concerns/planner-follow-ups-followups.md#themes-and-contrast)).

`--accent-ink` (`--ring` on Ledger, `--primary` in the dark themes, pinned by `themes.contracts.test.tsx`) colours lines and glyphs at 3:1; `--accent-text` (`index.css`: `oklch(0.5 0.11 80)` on Ledger, `--primary` in the dark themes) colours accent text runs at 4.5:1. The rules, the contrast floor and the other tokens are in `web/src/plan/ui/DESIGN.md`. The contract helper `value()` in `themes.contracts` resolves a bare `var(--x)` declaration through the same theme chain and accepts an OKLCH `/ alpha`, so a palette that aliases a token passes.
