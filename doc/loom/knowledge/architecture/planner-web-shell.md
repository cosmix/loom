# Planner Web Shell and Screens

> Shell and screens

The planner web app (`web/src/plan/`) follows `web/src/plan/ui/DESIGN.md`, the design record a designer worker set for the redesign; read it before touching layout, type or colour (`ui/design.css` holds its tokens and the button scale). The brief bundles `doc/plans/feat-planner/briefs/feat-planner-12-ui-repair/` and `feat-planner-13-planner-redesign/` hold the per-screen values each plan used. Product contract: `doc/product/feat-planner/section_05.md`, `section_06.md`, `section_08.md`, `section_09.md`. The feature screens (layout route, spine, offers, pages, wire) are in [Planner Feature Screens](planner-feature-screens.md).

## Header and dock

- **One app bar** (`header/header.tsx`, `header.css`): the logo, `Identity` from `header/feature-switcher.tsx`, the activity pill and responsive controls. The logo is a home link named "Loom planner home" (32/40/56px by width, frozen `activity-fixes` contract). The bar follows the dashboard header (`web/src/components/header.tsx`): 16px block padding and its card-to-background wash (`header.css`, a deliberate exception recorded in `ui/DESIGN.md` Surfaces). At widths of at least 1024px the controls are the Home and Files links with the registered views (`tabs.tsx`), presence, share, theme, Settings and Help; narrower layouts use `overflow.tsx`. There is no Product or Engineering tab, no step rail and no next-step card: a feature's progress lives in the spine. `HeaderExtras` (`web/src/plan/header-extras.tsx`) renders `HandoffMounts` and, in compact layouts only, `ChatSheetButton`. `PressureStrip` follows the app bar unless `sample` is set.
- **Switcher** (`feature-switcher.tsx`): one button holding the eyebrow over the title and a chevron, with one hover surface and the label as its accessible name. Its menu lists features only, by slug, the route's own with `aria-current` and a check; Home and New work are not entries (the logo goes home). `useIdentity` names what the bar shows: a feature route gives "Planning · feature" over the slug; `/new` gives "Planning · new work" over "Untitled", or, once a kickoff has a size, that size's eyebrow over the name so far (the rename included, from the live kickoff or the draft of `/new?session=`); files give "Planning · files" and everything else "Planning · project" over the project name. The eyebrow reads the shape's size but not the start offer, which `KickoffHead` also reads ([follow-up](../concerns/planner-ui-repair-followups.md#planner-review-fixes-unchecked-here-and-reviewer-suggestions)).
- **Footer** (`shell-footer.tsx`, drawn by `PlanShell` under the routed page and dock): `PlanFooter` draws the dashboard's `QuotaMeters` (`@/components/quota-meters`) from `summaryPanelAtom`, with no `quota_left`, and names a provider the panel reports nothing for ("Claude limits unavailable", "Codex limits unavailable"). It is empty until the summary feed has answered, so it never claims limits are unavailable before it knows. `SummaryFeedHost` (mounted by the shell while signed in) runs `useSummaryFeed` into `panelLoadAtom`, so the footer, the pill and Settings share one feed.
- **Activity pill and popover** (`header/activity.tsx`, `activity-rows.tsx`, `use-activities.ts`, `activity.css`): `ActivityPill({ compact, sample })` reads the shell's feed (`panelLoadAtom`, `summaryReloadAtom`), so rebuild progress shows while the popover is closed; a summary question opens the popover without taking focus. `sample` omits the run, changed-since and summary footer (help scenes). The popover draws no quota meters and no token totals: those are in the footer and in Settings.
  - *List.* `ActivityList` draws one row per thing in progress, in one anatomy (glyph tile, title, sub line, time). A running plan is one row, "Plan running" with the plan name and "M of N stages merged" (`stagesMerged`, `RunRow`); the run data has no document or run-start field, so a drafting row reads "Drafting <document>" with the session name and the run row carries no start time. A kickoff waiting for the user is a row titled by the session brief (`BriefTitledRow` fetches the brief only in the live list, because the Help sample pill shares `useActivities` and its test asserts no fetch) and links to that session's screen (`/new?session=<id>`). A running rebuild is one disclosure row (`SummaryRow`) that opens `StatusContent` (the question, a read-only note and `RebuildActivity`: queue, failures, start error); its accessible name is `summaryRowName` ("Summary rebuilds: <visible title>, <subtitle>", WCAG 2.5.3), and one `useSummaryExpansion` state lives in `LivePill` so the detail survives a rebuild starting or ending.
  - *Footer* (`.activity-foot`): the idle summary row (`SummaryStatusRow`) first, wrapped in `.activity-foot__scroll`; then `RunLine`, which draws a stopped run as one footer control line (and nothing while the run is listed above); then `ChangedSinceControl`, a `<button>` named "Changed since you looked · N" that navigates to `/changes` ([the page](#changed-since-and-seen-text)). The footer shrinks only when the scroll wrapper exists (`:has`), so the run and changed-since lines keep the bottom edge while `.activity-scroll` and the detail scroll. `SummaryPanel` (token totals and quota meters, frozen `summaries/contracts.test.tsx`) is whole in Settings' Summaries group (`settings-sections.tsx` `SummariesGroup`, with Last rebuild and Token totals); `SummaryStatus` and `StatusTrigger` have no production importer and are mounted by `summary-status.test.tsx` and a frozen contract only ([follow-up](../concerns/planner-ui-repair-followups.md#planner-issue-fixes-reviewer-suggestions)).
  - The popover opens by itself on arrival when summaries are out of date, covers the reading column and swallows clicks; `web/scripts/plan-journeys-kit.mjs` dismisses it with Escape and prints a NOTE.
- **Share** (`header/share.tsx`): the dialog shows the URL with Copy and, on a remote bind, the plain-HTTP warning. `ShareLink` has no tunnel field; the dialog fetches the link on every open.
- **Dock** (`dock.tsx`): `hasChatPanel(pathname)` is false on `/`, so no `ChatPanel` mounts there. `ChatRegistrations` is always mounted; its `connect` prop (true when there is no panel and the path is not `/new`) opens the chat socket and attention watcher that `ChatPanel` owns wherever it is mounted ([the mistake](../mistakes/planner-ui-repair.md#hiding-chatpanel-on-the-home-route-dropped-the-socket-and-notifications)).
- **Help is a lazy chunk.** `shell.tsx` loads `PlannerHelpDialog` through `React.lazy` and `Suspense`: its topics and scenes would put `plan.js` at 514 kB, over vite's 500 kB chunk warning; lazy it is 476 kB. A `src/plan/help` `codeSplitting` group does not work, because groups pull their dependencies in recursively (1 MB), and an icons vendor group reaches only 499.3 kB. Tests await the dialog with `findByTestId`. Revisit if help must be available offline from the start.
- **Tokens.** `plan.css` defines `--plan-shadow` on `:root` and `.dark` (not under `[data-loom-plan]`, because the activity popover portals out of the shell) and `--popover-lift`, the popover's second drop, on `:root` only (the value is the same in both themes); `POPOVER_SHADOW` is `var(--plan-shadow), var(--popover-lift)`. Tailwind utilities outrank `@layer components` CSS, so a popover's size and surface go through `className` plus inline `boxShadow`, and Settings uses unlayered `settings/settings.css` (`.ps-*`) over the shared `theme-picker.tsx`. 390px must not scroll sideways.
- **Buttons.** One unlayered `.plan-button` rule set in `ui/design.css` keyed by `data-look` (`quiet`, `secondary`, `primary`) and the button's own `data-size` sets every look. `DisabledReason` (`ui/disabled-reason.tsx`) and `OfferButton` take an optional `look`, default `secondary`; a caller that wants the screen's primary fill passes `look="primary"`, and no caller restyles through `[&_button]:` wrappers. `INLINE_BASELINE` (exported from `disabled-reason.tsx`) is the shared inline class for `PLACEMENT.inline`, `ChipRow`, `RebuildButton` and both approval-notice wrappers. Tailwind utilities lose to the unlayered rules on a `.plan-button`, so a state such as the current item is expressed in an unlayered rule (`ui/doc-heading.css` `aria-current`).
- **Read-only server.** The banner alone carries the problem and the fix; a blocked control's reason is the single word "Read-only", the chat head draws no hazard and queue rows draw no blocked buttons.

## Home and kickoff

- **Home** (`home/`): the invitation is the first `li` of `ul.card-grid` (`FeatureCards` `lead`), a subgrid shared with the feature cards; it spans two columns by a container query at 594px (two 290px columns plus the gap), not a viewport query. A card's link is named by the feature slug; `ProgressStrip` is an sr-only `ol` and the card draws the step count as `.plan-fine` text. Above the features sit the **Unfinished** shelf (`drafts-shelf.tsx`: one row per kickoff draft, newest first, titled by `draftTitle` — the name, else "Untitled · <date>" — with the problem's first line and a live or set-aside status; each row opens `/new?session=<id>`; nothing renders without drafts) and the move offers.
- **Standalone plans** (`standalone-shelf.tsx`, `standalone-table.tsx`, `move-into-feature.tsx`): a `section` named "Standalone plans" holding a `details` that starts closed (open when the list is empty, so its explanation shows; frozen `features.contracts.test.tsx` pins the closed start, a summary containing "<n> standalone plans" and plan links inside the details and outside the summary). The body is a table of every plan, uncapped: a select box, the title (the link) over its slug, and the state as a glyph and a word. Headers sort; from `FILTER_FROM` plans a field narrows by title or slug; selection survives filtering and the header box acts on the plans shown. A selection bar on the filter's line offers Move to feature for all selected plans at once (`MoveIntoFeatureDialog`, one chat message naming every path, one per line; the wording names `doc/plans/<feature>/` when every path is a standalone plan, else the misplaced-document wording). Under 600px the table becomes blocks; explicit `role` attributes keep the table semantics that `display: block` drops in WebKit.
- **Kickoff** (`new/`, one `.kickoff-page` grid, `kickoff.css`): `1fr | 44rem text column | minmax(17rem, 1fr)`, shared by the empty form, the live conversation and an ended draft, so the head never moves when Taking shape appears (the empty form's doodle holds the column Taking shape later takes). `KickoffRoute` renders `/new` as the empty form (`empty-kickoff.tsx`) always; while a kickoff runs, `OpenDraftNotice` above the form reads "<name or Untitled> is still open" with Continue and Set it aside. `/new?session=<id>` is that kickoff: its conversation while it runs, else `DraftView` (`draft-view.tsx`: problem, decisions, questions and the user's messages, with Continue this draft and Discard; it refetches when its `live` flag turns false). `kickoffSessionAtom` holds this tab's own start and is cleared when `/new` unmounts before the session arrives, so a later `/new` shows the empty form. Wire, storage and commands: [Planner Uploads and Kickoff Drafts](planner-uploads-and-drafts.md#kickoff-drafts).
- **Kind of work.** `KindControl` (`kind-control.tsx`) is a two-radio group, "Feature" or "Standalone plan" (`KIND_WORD`, exported from `kickoff-head.tsx`), each with a one-line hint; Add plan preselects Standalone plan, and `KickoffHead` names the kind in the page head. `useProposalActions` is exported from `proposal.tsx` for the Size control (`shape-size.tsx`); the Size control and the proposal share one `commandPendingAtom` that `useProposalActions` checks and sets before it sends, so one click on a shape choice sends one message ([the doubled send](planner-uploads-and-drafts.md#the-opening-in-the-transcript)). `TakingShape` (`taking-shape.tsx`) draws Problem, Decisions and Questions as rows (never the agent's JSON), a Name row that is editable until the work is confirmed (`rename-field.tsx`; the write button and notice appear when a shape exists), and the draft view reuses its row components.
- Server strings go through `SentenceText` raw: it escapes format characters itself after parsing, so pre-escaping with `visibleControls` changes the Markdown parse.

## Reading column

`concept/column-keys.ts`: `j`/`k` and the arrows step through DOM stops in document order (`step`): openable closed sentences (`[data-sentence-id][role=button]`) and `button.concept-run-cap`; plain sentences and passages are reached by clicking. A focused element holding stops (an opened run group, a passage) stands on its first stop. `foldAll` (Shift+Esc on a cap or the header path) moves focus to the outermost opener explicitly: Chromium blurs a focused element as it is removed, `onBlur` (`column-focus.ts`) clears `insideRef`, and `useFocusFollow` would never restore focus. jsdom does not blur on removal, so tests call `blurOnRemoval()` from `reading-column-harness.tsx`.

- **Colours** come from the server: `plan_server/concept/key.rs` gives each key chip `index % 8 + 1`, `body.rs` uses `colour_of(chips, doc.path)` with 0 for a document outside the key (the vision citations on a product overview). No client module assigns document hues; they stay `--doc-1..8`.
- **Document key** (`document-key.tsx`): a one-line lede (`keyLede`: "Key: the N sections of this feature" on a document page, "Sources: the … this overview summarizes" on an overview), then a link per document showing its glyph, its short label and its title on a fixed-width track, the first four plus a "… n more" chip (`Ellipsis` icon, sr-only text), and the mark legend; no "Fold all". The title (`chipTitle` drops a leading "<n> — ") is drawn whole in the DOM and cut to the chip's width by CSS alone (`.concept-key-title`), so the link's accessible name keeps all of it; a Radix tooltip repeats it above the out-of-date or implements note, never a native `title`, which would show a second tooltip. A document that changed since the reader looked gets the word "changed" after its chip (`key-chip-extras.tsx`, `role="img"` named "changed since you looked", the name the file tree's marker uses; a frozen review test pins both), not a dot. Per-page expansion state lives inside the component, keyed by page: a React `key` on the component would drop focus and reset `PendingApprovalNotice`.
- **Cited pages.** `concept/cited-pages.ts` prefetches the summaries the page's own document links name (key chips and marks), not raw citations, so a plan deleted since the overview was committed fetches nothing. An opened run reads Loading until every cited page has arrived, because `loadConceptPages` commits through `Promise.all` (`page-state.ts`).
- **Headers.** `ui/doc-heading.tsx` keeps a flex-wrap title row (the actions wrap under the title when the column cannot hold both). The "Built by" chip derives from `ConceptPage.implemented_by`; a locked Edit gets its title per `LockKind` (`LOCK_TITLES`); a summary page drops the path row and offers Open all only; `files/plan/plan-actions-extras.tsx` renders done-plan follow-ups. `passage.tsx` takes optional `leading`/`trailing` so a run's caps sit on the first chip line and after the last body. `markdown/render.tsx` suppresses a body H1 equal to the document title after `normalizeTitle` strips backticks, so a title holding a code span is not drawn twice.
- **Heading anatomy.** The heading's side inset is `--doc-heading-inset` (default `--space-5`, the source view's `px-6`); `.concept-page-column` (`concept-route.tsx`) sets it to 0 so header, key and text share left and right edges. A summary page's Rebuild is the `after` slot of the status `HeadingChip` (`SummaryAction` in `concept/page-header-extras.tsx`), so status and action share one baseline; a page whose summary state is null shows no chip and so no Rebuild (the server sets a state for every expected id, `evaluate.rs`, so this lasts only while a cached evaluation predates a new document). An overview has no `PageHeading`: its Open all / Fold all is `OpenAllButton` (exported from `page-heading.tsx`) rendered by `OverviewHead` in `concept-route.tsx`. `design.css` is unlayered, so a Tailwind utility cannot override `.plan-page-title`; a two-class selector in a component stylesheet does (`ui/doc-heading.css` `.doc-heading-title-row .plan-page-title`).
- **Run hairline.** A level-1 run's hairline sits on `.concept-run > .concept-sentence-wrap` (`concept/concept-runs.css`). It cannot hang on the run's span: a member opened to passages splits that span into several inline boxes, and a `:has(> .concept-passages:first-child)` rule then hides the whole run's border, so later members read as closed level-0 prose.
- Open runs fall back to an `unkeyed` `storageKey` segment before `hello`, so view state survives a reload in a store with no `serverInfoAtom`.

## Chat home and the chat panel

A chat belongs to a screen. `SessionView.feature` (`plan_session/model/mod.rs`) is persisted in `SessionRecord` (`session.json`, `bridge/registry.rs`) and read by `Session::view`, so a recovered closing session keeps its home; `set_owner` (`bridge/owner.rs`) names it for a kickoff that confirms later. `chat/session-home.ts` resolves the home: `session.feature` for a chat, the plan's feature or (standalone) `PressureRunView.plan` for a pressure run, and none for a kickoff, a move-into-feature or New chat on `/files`, which show on every screen. A session whose home is another screen shows the "elsewhere" notice (`ElsewhereBody`), not its transcript.

- With an open session on another screen, an offer or New chat refuses locally ("Finish the session in <feature slug or plan title> first.", `chat/offer-flow.ts`): no confirm, no end, no composer. No code path re-fires an offer on navigation or after Cancel (`confirmEndFirst` runs only from clicks). A kickoff start on `/new` refuses too (`new/kickoff-route.tsx`). A move starts owned by its destination only when that feature exists (`validate_feature` refuses an unknown one at start); the send fallback start keeps the ended chat's owner only while the project still has it. `validate_plan` runs in `chat/dispatch.rs`'s guidance closure with the same refusal path as `validate_feature`.
- **Surface.** The panel is one continuous surface: hierarchy comes from type, space and a single hairline, with no nested boxes. Assistant prose is 15px/1.55 in `--font-reading` (Source Serif 4 reads smaller than Inter at 14px); a user turn is 14px/500 Inter with a 2px `--border` left rule, full width; tool activity is a quiet folding run of lines; no transcript, table or panel text is below 13px except a chip's source and a file's size at `--type-fine` (12px), a recorded exception. The permission card is the one emphasised element and keeps the `y`/`n` keys and `DenyNoteForm`. The composer is one bordered box (`.chat-composer-box`, the exact selector the frozen contract "the composer has a visible border" reads) holding the context chip, the pending chips, the borderless textarea (`.chat-composer-field`) and the drop cover; while a file is dragged over, the box edge dashes with `--foreground` and nothing shifts. A notice is a plain `.chat-notice[data-tone]` element (`state-line.tsx`), not `HazardPanel`. New CSS goes in `chat/chat-surface.css`, because `panel-a11y.test` pins that `chat.css` holds no `box-shadow`, `opacity` or `--tone-`. Transcript sizes live only in `chat-transcript.css`: a `[role=log]` rule in `chat.css` would win on specificity over `.chat-transcript` and make the kickoff screen differ from the panel. Chat-wide tokens (`--chat-gutter`) are scoped on `.chat-panel`, `.chat-transcript` and `.chat-composer` together: `Transcript` and `ComposerArea` also mount outside `.chat-panel` (`new/kickoff-route.tsx`, `help/chat-scene.tsx`), where a token defined on the panel alone collapses the padding to 0. `--font-reading` is defined only on `[data-loom-plan]`, so the 390px chat sheet (a Radix portal) carries `data-loom-plan`, `data-reading-face` and `data-reading-size` on its `Dialog.Content`, or its prose falls to sans.
- **Head** (`chat/panel-head.tsx`): title, state pill, menu and collapse. The menu exists only while a chat is live and holds End chat alone (`EndChatMenuItem`); New chat is never drawn beside a live chat. It shows as the head button when there is no session (`NewChatButton`) and in the composer area after a chat concluded (`composer.tsx`, Ended and Failed). The title is the session brief's label (`useSessionBrief`), `Chat` until it loads; `session.name` is a tmux label ("loom plan: chat"), used only when it starts with an uppercase letter. `StateLine` stays mounted for its live region. `ChatGlyph` (`chat/chat-state-glyph.tsx`) draws the `MessageSquare` icon for an idle chat or none, `ActivityGlyph` (the rotating arrows of the activity popover) for starting and drafting, and a mark for permission, ended and failed; `BusyRoundel` (aurora-ui) appears only inside a live chat (`tool-row.tsx`, `state-line.tsx`). The collapsed rail (`CollapsedRail` in `panel.tsx`) is one tall tab, the whole strip a button: the glyph over the word "Chat" set vertically, the state word under it, the permission badge; its focus ring is inset (-2px) because an outward ring is clipped against the viewport edge. The phone Chat button uses `ChatGlyph` too.
- **Opening item.** An origin item (the guidance prompt that opens a chat) draws the session brief's label, or "Opening message" until the brief loads (`items.tsx` `OpeningLabel`), with a Show control and no prompt text in the DOM until Show is pressed; a test that reads an origin item's text clicks Show first. The prompt reaches the transcript wrapped in `<pasted_content id=X>` tags; the mapper unwraps it ([the wrapper](planning-session-bridge.md#delivery), [the mistake](../mistakes/planner-ui-repair.md#claude-code-wrapped-delivered-prompts-and-every-text-match-broke-silently-2026-11-03)). A kickoff opening with typed text is two items, the collapsed guidance and the user's own text shown once and always visible ([the split](planner-uploads-and-drafts.md#the-opening-in-the-transcript)); `isMeta` skill bodies and Skill tool rows never render, and `kickoff-fence.ts` hides the `loom-kickoff` block from assistant text.
- **Tool rows.** `groupToolRows` (`chat/tool-group.ts`) folds every run of one or more plain tool rows into one quiet line, while the turn runs and after it ends, labelled "Used <n> tools · edited <m> files" (frozen `chat.contracts.test.tsx`; the folded rows stay in the `<details>` DOM). Errors, denials, subagent rows and permission cards stay outside the fold, and Skill rows are dropped.
- **Context.** What the user is viewing is a quiet chip inside the composer box (`ContextLine`, `chat/context-line.tsx`): "About <name>", or "Now viewing <name>" while a chat runs, with a Dismiss context button. Its group's accessible name is "Viewing <name>", which the visible words do not repeat; it follows the route, is not a live region, and stays dismissed until the user moves to another document. The panel top holds no context line. The viewed document maps `/files/<rel>` and `/f/<f>/source/<rel>` alike (`chat/viewed-document.ts`). `lastAttachedAtom {path, session}` (`chat/context-attach.ts`) dedups an attachment per session and is bound to the session id by a store subscription in `ScreenSync`, because a start's session id is unknown when its result arrives; a record left with a null session binds to the next chat. An attached document that exceeds the quote limit (`attachments/doc-attachment.ts`) is cut at a line boundary with a visible marker, never silently. The send guard is a per-store `WeakSet` (`composer-hooks.ts`), so two hook instances cannot send twice; `useSendDraft` stays synchronous when nothing is fetched.
- **Chips.** A selection's chip reads as the quoted start of the selection (48 characters, whitespace collapsed, an ellipsis when cut; `chat/chip-label.ts`, `QUOTE_CHARS`) with the source (file, passage, lines) as secondary text, so two selections of one page read differently; a whole document keeps its file name, an overview reads "Product overview" or "Engineering overview". Add to chat opens the panel, or the sheet on narrow screens.
- **File attachments.** The paperclip, a drop on the composer and a paste of files (`composer-hooks.ts`; a paste that carries text/plain stays a text paste) upload through `attachments/intake.ts` (`attachFiles`, `upload.ts`) to the [upload route](planner-uploads-and-drafts.md#upload-route) and add a file chip (`chat/file-chip.tsx`). File chips are `FileDraft` in a `ChatAttachment` union beside `AttachmentDraft` (`attachments/types.ts`), so documents and quotes keep their type; a send carries the file by id. Image thumbnails are object URLs held per id in `attachments/previews.ts`: `rememberPreview` takes a hold per upload, `forgetPreview` releases one, the URL is revoked at zero, and a dropped duplicate releases its hold (`addAttachmentAtom`). A chip's file size comes from `ui/format-bytes.ts`. New work's document starter (`new/document-starter.tsx`) has its own file picker beside the chat's.
- **Concluded chat.** The view swaps on the user's intent (the session they chose to write after), never on the draft text, which the user edits ([the mistake](../mistakes/planner-redesign.md#a-view-was-derived-from-data-the-user-edits)).
- **Permission card.** One card sits at the end of the transcript (`transcript.tsx` `PendingDecision`); the composer area renders none.
- **Pressure dialog and run.** Node tiles tint `--doc-8` (Review), `--doc-3` (Second review) and `--doc-5` (Address); queued timeline rows are plain divs. The done head lives in `pressure/done-head.tsx` (a test mocks `./pressure-done` with only `PressureDone`). `LiveElapsed` is shared from `pressure/elapsed.tsx`. The dialog offers quick-pick rounds only.

## Help

One scene per pressure and reading topic; shortcuts have two groups (While reading, Anywhere). Pins (`help/pin-placement.ts`) try four sides clear of targets, placed pins and measured text and controls (occupied boxes through `Range.getClientRects`, guarded for jsdom), then a canvas-margin gutter level with the target centre, then an inside corner; bars try above, below, left, right. Measurement divides out ancestor scale because the dialog zoom-in scales the canvas. Scenes build their sample session with `sessionViewSchema.parse` at module load, so a new required `SessionView` key throws on import of `help/topics.ts` and fails every suite that imports the help footer. The stage shadow is a local `color-mix` on the foreground. On phones the dialog shows the topic list, then the article, and scrolls.

## Changed since and seen text

`review/changes-page.tsx` is the routed page `/changes`, full width so a side-by-side diff has room (the list column sits beside the diff from 1024px, `SIDE_BY_SIDE`); `review/changed-since.tsx` holds `ComparisonList`, `ChangedSinceControl` (the popover's footer row) and `changesFrom`; the rest is `changed-since-data.ts`, `seen-text.ts` and `checkpoint.ts`. The checkpoint is the commit the browser last acknowledged; a document's diff starts from the text the viewer last saw, not only from that commit.

- **The page.** Arriving puts focus on the heading, so a screen reader starts at the title. The popover row is a `<button>` that navigates to `/changes` with `state.from` (the page it was opened from, kept across reopening) and closes the popover by focus-outside: the page focuses its H1, which dismisses the non-modal Radix popover, and Radix skips the trigger refocus after an outside interaction (pinned by `changed-since.test` "opening the page from the popover closes it without returning focus to its trigger"; a `PopoverClose` would throw outside a popover, where tests render the control). `ChangedSinceControl` renders nothing outside a router (`useInRouterContext`), because the frozen `ActivityPill` contract tests mount the pill with no Router. An empty list reads "Nothing changed since you looked" with the way back (`from`, else Home) and takes the focus Mark all seen's button held. `changesFrom` takes only a same-origin path: it rejects a non-string, a leading `//` and a leading `/\`, which browsers read as `//`.
- **Seen text.** `seenTextsAtom` (`projectPref`, key from `storageKey`, name `seen-text`) stores the text a viewer read per path, so a diff stays computable when the checkpoint commit is gone from the repository (contract "seen text outlives a missing checkpoint commit"). Read it reactively through the atom: the contract remounts through the kit's `mount()`, which names a fresh `project_key` per call, and a store captured at mount would miss the same-page reload. `DOC_LIMIT` is 256 KiB per document, `TOTAL_LIMIT` 2 MiB per origin. The total is enforced across every project's `loom-plan:<key>:seen-text` key, because the browser's quota is per origin and every repository's planner serves on port 7272: the current project's entries come from its atom, the others from `localStorage` (`otherStores` walks `length`/`key` directly inside a try/catch, not through `safeStorage`), the least recently seen go first, and size is the JSON length times 2. `storageFullAtom` raises the storage-full banner when a write still fails.
- **Opening a diff marks it seen.** The open document stays listed (status "seen", `aria-current`) after its diff acknowledges it, and a click on the already-open row does nothing, so a "Show diff" re-click during a live refresh cannot race a row that left the list. A row is two lines at every width (path full width; status and since-commit left, action right) because the list column (about 44%, minimum 420px) cannot hold all three on one line.
- **Mark all seen** (`useMarkAllSeen`) reads each listed document through a `READ_CONCURRENCY` (4) pool and stops once the bytes read pass `TOTAL_LIMIT`. A read that succeeds at a hash other than the checkpoint's is skipped and deletes the entry that no longer matches. A generation guards stale diff responses: `checkpointGenerationAtom` sits beside the checkpoint atom and every `checkpointAtom` write bumps it; `markSeen` writes through an internal atom that does not bump, so a mark-all during a diff fetch keeps the newer baseline. The counter is not part of the stored `Checkpoint` object, which five `toEqual` assertions pin and which gains nothing, since an in-flight fetch never survives a reload.
- **Test kit.** `changed-since-test-kit.tsx` answers `/api/compare` for `c1` only: a test that opens a diff after Mark all seen with checkpoint commit `c2` and no seen text sets `replies['/api/compare?commit=c2']`, or the row hides its Show diff button.
