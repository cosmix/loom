# Planner Web Shell and Screens

> Shell and screens

The planner web app (`web/src/plan/`) follows one locked mockup; its structure, CSS values and copy live in the brief bundle `doc/plans/feat-planner/briefs/feat-planner-12-ui-repair/` (`common.md`, then `shell.md`, `features.md`, `reading.md`, `chat-help.md`, `card-payload.md`, `summary-engine.md`). Product contract: `doc/product/feat-planner/section_05.md`, `section_06.md`, `section_09.md`.

## Header, rail and dock

- **One app bar** (`header/header.tsx`, `header.css`): logo, feature switcher (`feature-switcher.tsx`), the step rail, next-step card, activity pill, presence, pressure strip, Settings and Help (`header-buttons.tsx`), an overflow menu (`overflow.tsx`) below 1024px (`WIDE_QUERY`), and the chat button (`HeaderExtras`, `header-extras.tsx`, renders `ChatSheetButton` only when compact). The header holds no run strip, changed-since control or summary status: they live in the activity popover. jsdom answers `matchMedia` false, so a test that mounts a full route goes through `renderAt` (`concept/concept-route-support.tsx`), which stubs the wide layout and clears `localStorage`, or Settings and the view tabs are missing.
- **Rail.** `StepTracker` (`step-tracker.tsx`) draws seven counter cells; each links to `?step=n` on `/f/<feature>`. `StepGlyph` and `STEP_MARKS` live in `rail-popover.tsx` (no import cycle with the tracker). Live step 7 reads `runStripAtom.daemon_running`, while home and the step nav show running from plan state, so the surfaces differ when no daemon runs.
- **Next-step card** (`next-step.tsx`): `NextStepCard` takes `compact` (offer button only, for the narrow second row). A button label that equals the card title is dropped (a guard test pins this for `write_section` and `write_plan`).
- **Activity pill** (`activity.tsx`, `use-activities.ts`): `ActivityPill({ compact, sample })` owns the summary feed (`useSummaryFeed`) and the auto-open of a summary question, so the feed runs while the popover is closed; `sample` omits the run, changed-since and summary footer (help scenes). `RunStrip` and `ChangedSinceControl` keep only their row variants; `SummaryStatus` stays because a frozen contract mounts it. The run data has no document or run-start field, so rows read "Drafting <document>" with the session name and "Plan running" carries no start time.
- **Dock** (`dock.tsx`): `hasChatPanel(pathname)` is false on `/`, so no `ChatPanel` mounts there. `ChatRegistrations` is always mounted; its `connect` prop (true when there is no panel and the path is not `/new`) opens the chat socket and attention watcher that only `ChatPanel` used to own ([the mistake](../mistakes/planner-ui-repair.md#hiding-chatpanel-on-the-home-route-dropped-the-socket-and-notifications)).
- **Tokens.** `plan.css` defines `--plan-shadow` on `:root` and `.dark` (not under `[data-loom-plan]`, because the activity popover portals out of the shell). Tailwind utilities outrank `@layer components` CSS, so a popover's size and surface go through `className` plus inline `boxShadow`, and Settings uses unlayered `settings/settings.css` (`.ps-*`) over the shared `theme-picker.tsx`. The app bar keeps the stated 34px logo and 14px 20px 16px padding down to 480px and the 28px compact values only below it (390px must not scroll sideways; the header measures 121px against the 160px cap).
- `DisabledReason` (`ui/disabled-reason.tsx`) fixes the button look; it applies the primary measures (30px, `0 12px`, 8px, 13px/600) only when no `size` prop is passed, and callers restyle it through a wrapper (`[&_button]:` classes, `.kickoff-ghost`).

## Card payload and the feature screens

`wire/checklist_card.rs::card_facts` adds `title`, `has_product`, `sections`, plan counts, `untested` and a counter and label per step to each feature's checklist. The title is the vision H1 with its suffix stripped, else the metaplan heading; the pitch skips a `Status:` paragraph. Both counts of step 2 come from the same listed vision rows (`sections_listed`), never from every written file. The web schema and fixtures (`checklist`, `checklist-message`, `hello`, hand-written JSON checked by `cargo test --lib plan_server::wire`) mirror it.

- **Home** (`home/`): the invitation is the first `li` of `ul.card-grid` (`FeatureCards` `lead`), a subgrid shared with the feature cards; it spans two columns by a container query at 594px (two 290px columns plus the gap), not a viewport query. The standalone shelf's `details` opens by default only when there are no standalone plans; move offers render above it.
- **Feature screen** (`feature/`): `/f/<feature>` is the step flow, `?step=n` selects (`steps.ts` validates against `STEP_COUNT`). Queue rows take plan names from `item.path` (`PLAN-<slug>.md`), not the gap sentence; a row carries its item's `OfferButton` and `StepItems` lists only the items no row shows. Server strings go through `SentenceText` raw: it escapes format characters itself after parsing, so pre-escaping with `visibleControls` changes the Markdown parse.
- **Kickoff** (`new/`): `useProposalActions` is exported from `proposal.tsx` for the Size control; `TakingShape` renders the write button and notice when a shape exists.

## Reading column

`concept/column-keys.ts`: `j`/`k` and the arrows step through DOM stops in document order (`step`): openable closed sentences (`[data-sentence-id][role=button]`) and `button.concept-run-cap`; plain sentences and passages are reached by clicking. A focused element holding stops (an opened run group, a passage) stands on its first stop. `foldAll` (Shift+Esc on a cap or the header path) moves focus to the outermost opener explicitly: Chromium blurs a focused element as it is removed, `onBlur` (`column-focus.ts`) clears `insideRef`, and `useFocusFollow` would never restore focus. jsdom does not blur on removal, so tests call `blurOnRemoval()` from `reading-column-harness.tsx`.

- **Colours** come from the server: `plan_server/concept/key.rs` gives each key chip `index % 8 + 1`, `body.rs` uses `colour_of(chips, doc.path)` with 0 for a document outside the key (the vision citations on a product overview). No client module assigns document hues; they stay `--doc-1..8`.
- **Document key** (`document-key.tsx`): four chips plus a "… n more" chip (`Ellipsis` icon, sr-only text); no "Fold all". Per-page expansion state lives inside the component, keyed by page: a React `key` on the component would drop focus and reset `PendingApprovalNotice`.
- **Headers.** `ui/doc-heading.tsx` keeps a flex-wrap title row (the actions wrap under the title when the column cannot hold both) instead of the brief's grid. The "Built by" chip derives from `ConceptPage.implemented_by`; a locked Edit gets its title per `LockKind` (`LOCK_TITLES`); a summary page drops the path row and offers Open all only; `files/plan/plan-actions-extras.tsx` renders done-plan offers. `passage.tsx` takes optional `leading`/`trailing` so a run's caps sit on the first chip line and after the last body.
- Open runs fall back to an `unkeyed` `storageKey` segment before `hello`, so view state survives a reload in a store with no `serverInfoAtom`.

## Chat home and the chat panel

A chat belongs to a screen. `SessionView.feature` (`plan_session/model/mod.rs`) is persisted in `SessionRecord` (`session.json`, `bridge/registry.rs`) and read by `Session::view`, so a recovered closing session keeps its home; `set_owner` (`bridge/owner.rs`) names it for a kickoff that confirms later. `chat/session-home.ts` resolves the home: `session.feature` for a chat, the plan's feature or (standalone) `PressureRunView.plan` for a pressure run, and none for a kickoff, a move-into-feature or New chat on `/files`, which show on every screen. A session whose home is another screen shows the "elsewhere" notice (`ElsewhereBody`), not its transcript.

- With an open session on another screen, an offer or New chat refuses locally ("Finish the session in <title> first.", `chat/offer-flow.ts`): no confirm, no end, no composer. No code path re-fires an offer on navigation or after Cancel (`confirmEndFirst` runs only from clicks). A kickoff start on `/new` refuses too (`new/kickoff-route.tsx`). A move starts owned by its destination only when that feature exists (`validate_feature` refuses an unknown one at start); the send fallback start keeps the ended chat's owner only while the project still has it. `validate_plan` runs in `chat/dispatch.rs`'s guidance closure with the same refusal path as `validate_feature`.
- **Head** (`chat/panel-head.tsx`): title, state pill, menu and collapse; New chat beside a live session moves into the menu. The title is the session brief's label (`useSessionBrief`), `Chat` until it loads; `session.name` is a tmux label ("loom plan: chat"), used only when it starts with an uppercase letter. `StateLine` stays mounted for its live region. New CSS goes in `chat/chat-surface.css`, because `panel-a11y.test` pins that `chat.css` holds no `box-shadow`, `opacity` or `--tone-`. The no-session glyph is the muted `.chat-led`; the quartered roundel (aurora-ui `BusyRoundel`) draws only starting and ending.
- **Permission card.** One card sits at the end of the transcript (`transcript.tsx` `PendingDecision`); the composer area renders none.
- **Pressure dialog and run.** Node tiles tint `--doc-8` (Review), `--doc-3` (Second review) and `--doc-5` (Address); queued timeline rows are plain divs. The done head lives in `pressure/done-head.tsx` (a test mocks `./pressure-done` with only `PressureDone`). `LiveElapsed` is shared from `pressure/elapsed.tsx`. The dialog offers quick-pick rounds only.

## Help

One scene per pressure and reading topic; shortcuts have two groups (While reading, Anywhere). Pins (`help/pin-placement.ts`) try four sides clear of targets, placed pins and measured text and controls (occupied boxes through `Range.getClientRects`, guarded for jsdom), then a canvas-margin gutter level with the target centre, then an inside corner; bars try above, below, left, right. Measurement divides out ancestor scale because the dialog zoom-in scales the canvas. Scenes build their sample session with `sessionViewSchema.parse` at module load, so a new required `SessionView` key throws on import of `help/topics.ts` and fails every suite that imports the help footer. The stage shadow is a local `color-mix` on the foreground. On phones the dialog shows the topic list, then the article, and scrolls.
