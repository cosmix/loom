# Planner Web Shell and Screens

> Shell and screens

The planner web app (`web/src/plan/`) follows `web/src/plan/ui/DESIGN.md`, the design record a designer worker set for the redesign; read it before touching layout, type or colour (`ui/design.css` holds its tokens and the button scale). The brief bundles `doc/plans/feat-planner/briefs/feat-planner-12-ui-repair/` and `feat-planner-13-planner-redesign/` hold the per-screen values each plan used. Product contract: `doc/product/feat-planner/section_05.md`, `section_06.md`, `section_08.md`, `section_09.md`. The feature screens (layout route, spine, offers, pages, wire) are in [Planner Feature Screens](planner-feature-screens.md).

## Header and dock

- **One app bar** (`header/header.tsx`, `header.css`): logo, `Identity` from `header/feature-switcher.tsx` (the feature's slug, never a document title), activity pill and responsive controls. At widths of at least 1024px the controls are the Home and Files links with the registered views (`tabs.tsx`), presence, share, theme, Settings and Help; narrower layouts use `overflow.tsx`. There is no Product or Engineering tab, no step rail and no next-step card: a feature's progress lives in the spine. `HeaderExtras` (`header-extras.tsx`) renders the chat sheet button only in compact layouts on a route with a mounted chat panel. `PressureStrip` follows the app bar unless `sample` is set.
- **Activity pill** (`activity.tsx`, `use-activities.ts`): `ActivityPill({ compact, sample })` owns the summary feed (`useSummaryFeed`) and the auto-open of a summary question, so the feed runs while the popover is closed; `sample` omits the run, changed-since and summary footer (help scenes). `RunStrip` and `ChangedSinceControl` keep only their row variants; `SummaryStatus` stays because a frozen contract mounts it. The run data has no document or run-start field, so rows read "Drafting <document>" with the session name and "Plan running" carries no start time. The popover opens by itself on arrival when summaries are out of date, covers the reading column and swallows clicks; `web/scripts/plan-journeys-kit.mjs` dismisses it with Escape.
- **Dock** (`dock.tsx`): `hasChatPanel(pathname)` is false on `/`, so no `ChatPanel` mounts there. `ChatRegistrations` is always mounted; its `connect` prop (true when there is no panel and the path is not `/new`) opens the chat socket and attention watcher that only `ChatPanel` used to own ([the mistake](../mistakes/planner-ui-repair.md#hiding-chatpanel-on-the-home-route-dropped-the-socket-and-notifications)).
- **Tokens.** `plan.css` defines `--plan-shadow` on `:root` and `.dark` (not under `[data-loom-plan]`, because the activity popover portals out of the shell). Tailwind utilities outrank `@layer components` CSS, so a popover's size and surface go through `className` plus inline `boxShadow`, and Settings uses unlayered `settings/settings.css` (`.ps-*`) over the shared `theme-picker.tsx`. 390px must not scroll sideways.
- **Buttons.** One unlayered `.plan-button` rule set in `ui/design.css` keyed by `data-look` (`quiet`, `secondary`, `primary`) and the button's own `data-size` sets every look. `DisabledReason` (`ui/disabled-reason.tsx`) and `OfferButton` take an optional `look`, default `secondary`; a caller that wants the screen's primary fill passes `look="primary"`, and no caller restyles through `[&_button]:` wrappers. Tailwind utilities lose to the unlayered rules on a `.plan-button`, so a state such as the current item is expressed in an unlayered rule (`ui/doc-heading.css` `aria-current`).
- **Read-only server.** The banner alone carries the problem and the fix; a blocked control's reason is the single word "Read-only", the chat head draws no hazard and queue rows draw no blocked buttons.

## Home and kickoff

- **Home** (`home/`): the invitation is the first `li` of `ul.card-grid` (`FeatureCards` `lead`), a subgrid shared with the feature cards; it spans two columns by a container query at 594px (two 290px columns plus the gap), not a viewport query. A card's link is named by the feature slug; `ProgressStrip` is an sr-only `ol` and the card draws the step count as `.plan-fine` text. The standalone shelf's `details` opens by default only when there are no standalone plans; move offers render above it.
- **Kickoff** (`new/`): `useProposalActions` is exported from `proposal.tsx` for the Size control; `TakingShape` renders the write button and notice when a shape exists.
- Server strings go through `SentenceText` raw: it escapes format characters itself after parsing, so pre-escaping with `visibleControls` changes the Markdown parse.

## Reading column

`concept/column-keys.ts`: `j`/`k` and the arrows step through DOM stops in document order (`step`): openable closed sentences (`[data-sentence-id][role=button]`) and `button.concept-run-cap`; plain sentences and passages are reached by clicking. A focused element holding stops (an opened run group, a passage) stands on its first stop. `foldAll` (Shift+Esc on a cap or the header path) moves focus to the outermost opener explicitly: Chromium blurs a focused element as it is removed, `onBlur` (`column-focus.ts`) clears `insideRef`, and `useFocusFollow` would never restore focus. jsdom does not blur on removal, so tests call `blurOnRemoval()` from `reading-column-harness.tsx`.

- **Colours** come from the server: `plan_server/concept/key.rs` gives each key chip `index % 8 + 1`, `body.rs` uses `colour_of(chips, doc.path)` with 0 for a document outside the key (the vision citations on a product overview). No client module assigns document hues; they stay `--doc-1..8`.
- **Document key** (`document-key.tsx`): four chips plus a "… n more" chip (`Ellipsis` icon, sr-only text), and the mark legend; no "Fold all". Per-page expansion state lives inside the component, keyed by page: a React `key` on the component would drop focus and reset `PendingApprovalNotice`.
- **Cited pages.** `concept/cited-pages.ts` prefetches the summaries the page's own document links name (key chips and marks), not raw citations, so a plan deleted since the overview was committed fetches nothing. An opened run reads Loading until every cited page has arrived, because `loadConceptPages` commits through `Promise.all` (`page-state.ts`).
- **Headers.** `ui/doc-heading.tsx` keeps a flex-wrap title row (the actions wrap under the title when the column cannot hold both). The "Built by" chip derives from `ConceptPage.implemented_by`; a locked Edit gets its title per `LockKind` (`LOCK_TITLES`); a summary page drops the path row and offers Open all only; `files/plan/plan-actions-extras.tsx` renders done-plan follow-ups. `passage.tsx` takes optional `leading`/`trailing` so a run's caps sit on the first chip line and after the last body. `markdown/render.tsx` suppresses a body H1 equal to the document title after `normalizeTitle` strips backticks, so a title holding a code span is not drawn twice.
- Open runs fall back to an `unkeyed` `storageKey` segment before `hello`, so view state survives a reload in a store with no `serverInfoAtom`.

## Chat home and the chat panel

A chat belongs to a screen. `SessionView.feature` (`plan_session/model/mod.rs`) is persisted in `SessionRecord` (`session.json`, `bridge/registry.rs`) and read by `Session::view`, so a recovered closing session keeps its home; `set_owner` (`bridge/owner.rs`) names it for a kickoff that confirms later. `chat/session-home.ts` resolves the home: `session.feature` for a chat, the plan's feature or (standalone) `PressureRunView.plan` for a pressure run, and none for a kickoff, a move-into-feature or New chat on `/files`, which show on every screen. A session whose home is another screen shows the "elsewhere" notice (`ElsewhereBody`), not its transcript.

- With an open session on another screen, an offer or New chat refuses locally ("Finish the session in <feature slug or plan title> first.", `chat/offer-flow.ts`): no confirm, no end, no composer. No code path re-fires an offer on navigation or after Cancel (`confirmEndFirst` runs only from clicks). A kickoff start on `/new` refuses too (`new/kickoff-route.tsx`). A move starts owned by its destination only when that feature exists (`validate_feature` refuses an unknown one at start); the send fallback start keeps the ended chat's owner only while the project still has it. `validate_plan` runs in `chat/dispatch.rs`'s guidance closure with the same refusal path as `validate_feature`.
- **Surface.** The panel is one continuous surface: hierarchy comes from type, space and a single hairline, with no nested boxes. Assistant prose is 15px/1.55 in `--font-reading` (Source Serif 4 reads smaller than Inter at 14px); a user turn is 14px/500 Inter with a 2px `--border` left rule, full width; tool activity is a quiet folding run of lines; the permission card is the one emphasised element and keeps the `y`/`n` keys and `DenyNoteForm`; the composer is part of the panel. A notice is a plain `.chat-notice[data-tone]` element (`state-line.tsx`), not `HazardPanel`. New CSS goes in `chat/chat-surface.css`, because `panel-a11y.test` pins that `chat.css` holds no `box-shadow`, `opacity` or `--tone-`. Chat-wide tokens (`--chat-gutter`) are scoped on `.chat-panel`, `.chat-transcript` and `.chat-composer` together: `Transcript` and `ComposerArea` also mount outside `.chat-panel` (`new/kickoff-route.tsx`, `help/chat-scene.tsx`), where a token defined on the panel alone collapses the padding to 0.
- **Head** (`chat/panel-head.tsx`): title, state pill, menu and collapse; New chat beside a live session moves into the menu. The title is the session brief's label (`useSessionBrief`), `Chat` until it loads; `session.name` is a tmux label ("loom plan: chat"), used only when it starts with an uppercase letter. `StateLine` stays mounted for its live region. The no-session glyph is the muted `.chat-led`; the quartered roundel (aurora-ui `BusyRoundel`) draws only starting and ending.
- **Context.** The composer names what the user is viewing in a line with the accessible name "Viewing <name>" and can attach the document. `lastAttachedAtom {path, session}` (`chat/context-attach.ts`) dedups an attachment per session and is bound to the session id by a store subscription in `ScreenSync`, because a start's session id is unknown when its result arrives; a record left with a null session binds to the next chat. An attached document that exceeds the quote limit (`attachments/doc-attachment.ts`) is cut at a line boundary with a visible marker, never silently. The send guard is a per-store `WeakSet` (`composer-hooks.ts`), so two hook instances cannot send twice; `useSendDraft` stays synchronous when nothing is fetched.
- **Concluded chat.** The view swaps on the user's intent (the session they chose to write after), never on the draft text, which the user edits ([the mistake](../mistakes/planner-redesign.md#a-view-was-derived-from-data-the-user-edits)).
- **Permission card.** One card sits at the end of the transcript (`transcript.tsx` `PendingDecision`); the composer area renders none.
- **Pressure dialog and run.** Node tiles tint `--doc-8` (Review), `--doc-3` (Second review) and `--doc-5` (Address); queued timeline rows are plain divs. The done head lives in `pressure/done-head.tsx` (a test mocks `./pressure-done` with only `PressureDone`). `LiveElapsed` is shared from `pressure/elapsed.tsx`. The dialog offers quick-pick rounds only.

## Help

One scene per pressure and reading topic; shortcuts have two groups (While reading, Anywhere). Pins (`help/pin-placement.ts`) try four sides clear of targets, placed pins and measured text and controls (occupied boxes through `Range.getClientRects`, guarded for jsdom), then a canvas-margin gutter level with the target centre, then an inside corner; bars try above, below, left, right. Measurement divides out ancestor scale because the dialog zoom-in scales the canvas. Scenes build their sample session with `sessionViewSchema.parse` at module load, so a new required `SessionView` key throws on import of `help/topics.ts` and fails every suite that imports the help footer. The stage shadow is a local `color-mix` on the foreground. On phones the dialog shows the topic list, then the article, and scrolls.
