# Web Dashboard

> Web

## Server

Hand-rolled HTTP/1.1 + WebSocket server, no framework. The transport is the shared `loom/src/web_server/` module, also used by the planning server ([plan-server.md](plan-server.md#shared-web_server-layer)); the dashboard supplies its own `Router`. Dashboard files: `loom/src/commands/status/web/mod.rs` (entry, `WorkDir::new(".")?.load()?` — needs `.loom/work` in the CWD or it exits before binding; `AccessPolicy::resolve(local, &ServeOptions)` is an inherent impl here; `MAX_INBOUND_BYTES = 64 KiB`), `router.rs` (`DashboardRouter`: `upgrade` runs the cookie bootstrap, then `/ws/terminal/*`, then `/ws`), `connection.rs` (`dispatch`/`Route`: API and SPA routes after the shared gates), `startup.rs` (printed URLs and the remote warning), `broadcast.rs` (daemon-fed publish/subscribe), `feed.rs` and `feed_split.rs` (the `/ws` message stream), `model.rs` (wire types, pinned by `model_tests.rs`), `config_api*` and `terminal/`.

The shared layer owns everything per-connection: `web_server::serve` runs the accept loop and, ahead of any router, the head and `Host` gates (no cookie check); `connection.rs` holds `WRITE_TIMEOUT = 5s` for whole-bundle HTTP writes against the WebSocket lane's 250ms and `DRAIN_DEADLINE = 300ms` on `drain_pending`; `limits.rs` holds `MAX_CONNECTIONS = 64`, the `MAX_WEBSOCKETS = 48` sub-cap and `MAX_TERMINALS = 8` behind an RAII `Slot`; `listener.rs` binds (`bind_listener`, `bind_first_available_port`, host-parametric); `access.rs` is `AccessPolicy`, `auth.rs` is `Auth`, `bootstrap.rs` is the token-to-cookie exchange, `ws.rs` sends and receives frames, `http.rs` has the CSP and security headers.

Port selection is atomic at the bind call, on whichever host `--host` resolves to (`127.0.0.1` by default). Bare `loom status --web` tries `DEFAULT_PORT` (7373) and advances only on `AddrInUse`, so concurrent dashboards in separate repositories settle on different ports. `loom status --web PORT` binds that port exactly and preserves the contextual bind error; explicit `0` asks the OS for an ephemeral port. The printed URL always contains the listener's actual port.

It reuses existing TUI/status code rather than reimplementing it: `render::attention_entries`, `render::failure_label`, `scheduling_report::alerts`, `tick::read`, `data::collect_status_data`, `daemon_client::{connect,subscribe,is_socket_disconnected}`, `DaemonServer::check_status`.

**A second write surface: `--terminals`.** With that flag, `/ws/terminal/<stage>/<view|control>` upgrades to a keystroke channel into a live stage's tmux session, gated by a startup-minted, port-scoped cookie token independent of `/api/config`'s CSRF token. Full detail — admission order, the close-code contract, the poll-based bridge loop, and the frontend emulator — is [architecture/web-terminal.md](web-terminal.md). Apart from that lane and `/api/config`'s writes, every route stays GET/HEAD only; a non-loopback `--host` bind leaves every viewing route open (SPA, assets, `/api/status`, `/ws`, `GET /api/config`) and requires the dashboard cookie only for `POST /api/config` and the terminal lane (below).

## Remote access (`--host`)

`AccessPolicy::resolve` (dashboard, `commands/status/web/mod.rs`) runs once, from `listener.local_addr()` and `ServeOptions`, before any connection thread spawns, and builds the policy with the infallible `AccessPolicy::new(local, Option<Auth>)`; every accepted connection shares the one resolved policy plus its own `local_addr` (a wildcard bind's accepted address varies per client, the listener's bind address never does). `remote = !local_addr.ip().is_loopback()`, so a wildcard bind (`0.0.0.0`/`::`) is remote even for a client that happens to connect over loopback. A remote listener with no `Auth` fails closed in `web_server::serve` (it returns `Err` before accepting) rather than serving with no auth.

`ServeOptions.dashboard_token` / `.terminal_token` must be equal when both are set (`web_server::auth::resolve_process_token`); `--terminals` still governs only whether `Broadcaster`/the terminal lane are enabled at all — a remote bind's token never implies terminal capability on its own.

Per connection, `AccessPolicy::host_allowed` checks `Host` against `local`, the accepted socket's own `local_addr()` — not the listener's bind address — so DNS names, wrong ports, and a proxy rewriting `Host` to a DNS name all fail; `localhost:<port>` passes only when `local` is itself loopback. `origin_allowed` requires an exact `http://<authority>` match against the same `local` whenever `Origin` is supplied, and requires it outright on writes and both WebSocket lanes. `AccessPolicy::authenticated` checks the `loom_dashboard_<port>` cookie (`web_server::token::cookie_name`) against `Auth::cookie_matches`; always `true` in loopback posture, since that mode authenticates nothing beyond `Host`/`Origin`. Its only caller is the config write gate (`config_api/request.rs`); the terminal lane checks the same cookie itself in `terminal/upgrade.rs::admit`. Viewing is open to anyone who reaches a remote listener, over plain HTTP: `GET /api/config` hands out the CSRF token without a cookie, which is safe only because a remote write also needs the cookie. `startup.rs` (`remote_warning_lines`) says so at startup.

The only way to obtain the cookie is `GET`/`HEAD /?token=<token>` (`web_server::bootstrap::bootstrap_cookie`, called from `DashboardRouter::upgrade`), which 302-redirects to `/` with the cookie set on a match and 403s on a mismatch; a token in the query of any other path does nothing.

Limits: plain HTTP, no TLS; no reverse-proxy support (a proxy rewriting `Host` to a DNS name is refused); `--host` takes only IP literals and the exact alias `localhost`, never a DNS name; no config key for the bind host, CLI flag only; the token is per process, so restarting the dashboard invalidates every existing cookie.

## Broadcaster fallback

Daemon lane first; a `Response::Error` degrades to the file-poll lane (`FILE_POLL_INTERVAL` 2s) with the message carried into the snapshot's `notice`. A received frame resets the failure counter so a healthy daemon never falls back. After `FILE_POLL_COUNT` polls the loop retries the daemon (~10s reconnect cycle). The daemon itself rebuilds the whole `StatusData` every 1000ms (`STATUS_BROADCAST_INTERVAL_MS`) with no change detection.

**`/ws` carries tagged messages, not whole snapshots.** `Broadcaster::publish` hands each collected `WebSnapshot` to `Feed` (`web/feed.rs`), which emits JSON text frames tagged `t`:

- `full`: `{"t":"full","snapshot":<the bare WebSnapshot, byte-identical to /api/status>}`. Sent as a new subscriber's first message, then every `FULL_INTERVAL` (30s), and at once when the stage id sequence, any immutable stage key, or `terminals`/`version` changes.
- `tick`: sent on every collect, so it is also the liveness signal. Carries `at`, `tick_age` and, for each stage whose clock values moved, the numeric `elapsed`/`exec`/`stale`/`judge`/`contract` entries.
- `state`: sent when a non-clock value changed. Carries each changed stage's whole dynamic part (every key except the immutable ones), the changed `status` blocks (`merge`, `progress`, `plan_name`, `quota`, `activity`) and the changed top-level `attention`, `alerts`, `daemon`, `source`, `notice` (`null` clears it).
- `tokens`: the whole tokens block (`null` when absent), sent only when it changed (the tracker writes `flow.json` about every 5s).

`web/feed_split.rs` owns the classification: `IMMUTABLE_STAGE_KEYS` (`id`, `name`, `description`, `summary`, `stage_type`, `dependencies`, `max_retries`) travel only in `full`; every other stage key is dynamic by default, so a new `StageSummary` field is delivered without a code change. Clock values (`elapsed_secs`, `execution_secs`, `staleness_secs`, `judge_heartbeat_secs`, `contract_testing.running_secs`, `attention[].judge_heartbeat_secs`) are masked in the diff, so a number moving to another number is not a `state`, while null to number is. A key that is neither classified nor a stage key forces a `full`; `feed_split_tests.rs` pins every `WebSnapshot` and `StatusData` key to a class. `web/frames.ts` (strict zod, `stageDynamicSchema` is `stageSummarySchema.omit(...)`) and `schema_parity.rs` pin the Rust and TypeScript key lists to each other.

Lock order is `feed -> hub.subscribers`: `publish` and `subscribe` both hold `feed` across their hub call, so a subscriber's `full` primer is built from the snapshot every later delta is relative to. A subscriber whose queue (`SUBSCRIBER_QUEUE_DEPTH`, 32) fills is dropped and recovers by reconnecting, which yields a fresh `full`; there are no sequence numbers. `Broadcaster::latest()` returns the bare snapshot JSON that `/api/status` serves. `web_server/ws.rs` has no keepalive of its own.

Client: `web/src/api/ws.ts` parses each message with `parseFrame` (`frames.ts`), drops any non-`full` message before the socket's first `full`, and applies it through `applyFrame` (`state/apply.ts`) and `state/merge.ts` (`mergeState`, `mergeTick`, `mergeTokens`, all pure). It does not fetch `/api/status`. The 30s watchdog reconnects when no message of any kind arrives, which a stalled daemon collect now causes.

## Fixture contract

`loom/src/commands/status/web/model_tests.rs` pins the Rust model's exact serde output against `web/src/api/fixtures/statuses.json`, which the TS `zod` schema (`web/src/api/schema.ts`) and tests consume. Changing the wire model means updating the fixture and schema in the same change, or the TS tests and the zod parse both fail. The one gap: the fixture test hardcodes the 13 `StageStatus` variants instead of deriving them from an exhaustive match, so a 14th variant compiles Rust-side and only fails at runtime on the TS side (zod rejects the whole snapshot, page renders blank).

A second, independent check, `loom/src/commands/status/web/schema_parity.rs`, closes a related gap for the enums it covers (`SessionType`, `StageStatus`, `StageType`, `FailureType`, `SessionExitReason`): each opens with an exhaustive `match` with no wildcard arm, so adding a variant fails that match to compile until its hand-maintained list is updated, and the test then asserts every serialized wire value is a quoted literal somewhere in `schema.ts`. It was added after `SessionType::Contract` shipped without a `schema.ts` update and rejected every frame (mistakes/web-dashboard-server.md).

## zod and the CSP

The CSP in `web_server/http.rs` (`CONTENT_SECURITY_POLICY`) sets no `script-src`, so `default-src 'self'` forbids `new Function`. zod 4 probes for eval support with `new Function("")` the first time an object schema is built. It catches the throw, but Chrome still logs a CSP violation on every page load. `web/src/api/zod.ts` calls `z.config({ jitless: true })`, which skips the probe, and re-exports `z`. Every schema module must import `z` from `@/api/zod`, because schemas are built when the module loads and a `z.config` call in `main.tsx` would run after them. `web/.oxlintrc.json` enforces this with `no-restricted-imports` on `"zod"`, and `web/src/api/zod.test.ts` wraps `globalThis.Function` in a counting proxy before a dynamic import of `@/api/schema`, then asserts zero calls. The Vite dev server sends no CSP, so the violation only shows under `loom status --web` or a `vite preview` given the same header.

## Committed dist + build.rs embedding

`web/dist` is a committed build output, embedded via `include_bytes!` at compile time: `loom/build/assets.rs`'s `generate_web_assets` (called from `loom/build.rs`) walks `web/dist` and writes a generated Rust source file under Cargo's `OUT_DIR` (not checked in) that the crate `include!`s. It compares generated content before writing (`write_if_changed`) — writing unconditionally would make the file's fresh mtime trigger a full crate rebuild on every `cargo build`. Rebuild and commit `dist/` with every change to `web/src/` (`cd web && bun install && bun run build`).

## CI/scripts

Any script invoking `loom status --web` needs its own `.loom/work` in the CWD — `WorkDir::new(".")` bails before binding otherwise, and a clean CI checkout never has one since `.loom/work` is gitignored (`scripts/smoke-web-dashboard.sh` creates a scratch workspace for this reason).

## Config read/write surface (`/api/config`)

The dashboard's only write route, and the first one it ever had: `loom/src/commands/status/web/config_api.rs` plus `config_api/{wire,workspace,entries,apply,csrf,request}.rs`. `GET` returns every `user_config::keys::KEYS` entry projected over both config scopes; `POST` writes or clears one key at one scope. The React side is `web/src/api/config.ts` and `web/src/components/settings-*`, opened from the header via `useOpenSettings()` (`settings-dialog.tsx`), which takes no argument and sets `?settings=1` — the param's value is never read, it only gates whether the dialog is open.

**Two scopes, one per-key project tier.** User scope is `~/.loom/config.toml` (the typed `KEYS` registry); project scope is `<repo>/.loom/work/config.toml`. `workspace.rs::resolve` is the ONE place naming which keys the project tier backs, and `backs()` asks `resolve` rather than keeping a second list beside it. Every project-backed key resolves per key (operator decision 2026-09-13, which removed the old SECTION-level tier for `[terminal]`/`[context]`): `Workspace::shadows` is true only when the project file supplies the key, and `Workspace::value_of` for an unsupplied key is the user tier's value (the built-in when the user file is silent), so the project lane shows what it inherits. `terminal.backend` and `context.ceiling_tokens` match by exact name and parse through the same functions as the runtime readers — `TerminalConfig::backend_from_section` (`fs/work_dir/config_sections/terminal_config.rs`) and `ContextConfig::resolve_with_user_ceiling` (`fs/work_dir/context_config.rs`) — so a malformed section fails both; a project `model_window_tokens` counts as supplying `context.ceiling_tokens`. `[pressure]`/`[models]` keys go through `section_key`, matched on `spec.section`, so a key added to either section needs no edit to `resolve`. A `[context]` kept alive by a sibling key (`subagent_ceiling_tokens`, `prompt_cache_split`) does not shadow the user ceiling, and the API reports the fallthrough. `remove_key` (`fs/work_dir/config_sections.rs`) still drops a section its removal empties, as tidiness. `insert_key` exists because `write_section`/`merge_section` serialize a whole struct, which would freeze the derived `subagent_ceiling_tokens` into the file and drop `prompt_cache_split`, which no struct owns; `loom init` uses it to write only the ceiling keys a plan sets.

**Write gates, all required** (`config_api/request.rs`, `web_server/http.rs`). `Host` is applied to every request ahead of routing, unchanged — now policy-driven (`AccessPolicy::host_allowed`), so it is the DNS-rebinding check in loopback posture and the exact-socket-identity check in remote posture. Then `AccessPolicy::origin_allowed(.., OriginRequirement::Required)` — this replaces an earlier plain `origin_allowed_strict` call: loopback posture still requires `Origin` PRESENT and loopback via `http::origin_allowed_strict`, and remote posture requires `Origin` to match the connection's own address exactly, unlike the lenient `origin_allowed` that GET keeps because a browser sends no `Origin` on a same-origin GET. On a remote bind only, the `loom_dashboard_<port>` cookie (`AccessPolicy::authenticated`), answering 401 with a JSON error that names the tokenized URL. Then a per-process double-submit CSRF token (`csrf.rs`, CSPRNG, constant-time compare) handed out only in the `GET /api/config` body and required in `X-Loom-Csrf`. The mechanism rests entirely on serving NO CORS headers: a cross-site page can send the request but cannot read the token, and cannot set the custom header (or `Content-Type: application/json`, deliberately required for the same reason) without a preflight that fails. **Adding any `Access-Control-Allow-*` header hands both halves back to the attacker.** Bodies need a digits-only `Content-Length` within `MAX_BODY_BYTES` (8 KiB); nothing past the cap is ever read.

**`default` on the wire.** Each entry carries the built-in it resolves to when neither scope sets it, sourced from `UserConfig::default().value_of(spec)` — never a second table of defaults. It is not recoverable from the rest of the entry: `user.value` is the RESOLVED user value, so it stops being the built-in the moment `user.set` turns true.

**Frontend: three-lane layout, not a scope switch.** The dialog renders the three tiers (built-in, user, project) as columns of one table (`settings-lanes.tsx`, `settings-lanes-cells.tsx`) or, below 700px via `useMediaQuery("(max-width: 699px)")`, as one card per row (`settings-cards.tsx`); both read from `sectionRows()`/`filterSections()` in `settings-model.ts`, which pairs `<prefix>_model`/`<prefix>_effort` keys into one row. Each user/project cell is a `LaneSlot` (`settings-control.tsx`) with its own clear button; the built-in column renders read-only via `BuiltinValue`, showing the wire's `default`. There is no scope-switch control, no "reset to built-in" button and no provenance rail (`railStops`/`RailStop`).

**Fixture.** `web/src/api/fixtures/config.json` is pinned by `the_config_fixture_matches_a_real_payload` and covers all three `effective.source` values, plus `scopes: [user, project]` on every `pressure.*`/`models.*` entry, not just `terminal`/`context`. It now pins the `default` values and the enum variant lists too, so moving ANY built-in — not just `CLAUDE_MODELS`/`CODEX_MODELS` — fails that test until the fixture is regenerated. The recipe is in the test's doc comment.

## Stage Summary and Review Notes on the Wire

The stage dialog and stage page show the plan-authored `summary` (`StageDefinition.summary` -> `Stage.summary` -> status `StageSummary.summary`), never `description`, which is the agent's task brief and stays off the dashboard; a stage without a summary shows only its name. `loom plan verify` and `loom init` warn per stage without one (`plan/schema/structural_checks.rs::check_missing_summaries`, reached through `check_file_ownership` so `validate_structural_preflight` keeps its pinned length).

`StageSummary` carries the review reason twice: `review_reason` is flattened to one line of at most 200 chars by `inline_safe`, because the terminal renderers (`ui/tui/ledger/panels.rs`, `render/graph.rs`, `render/attention.rs`) print it; `review_notes` is the same text through `context/untrusted.rs::multiline_safe` (newlines kept, the same control/bidi/backtick rules, 16,000-char cap). The web shows `review_notes` in place of the cut reason while the attention entry has a `review_reason` (`reviewNotesFor` in `components/attention-panel.tsx`). Failure evidence, acceptance criteria, failing-criteria commands and diagnostics, and dispute fields reach the wire whole: neutralized per character (`status/data/sanitize.rs::neutralize`, `flatten_char`), with no 200-char cut and no evidence line cap. Never render `review_notes` or `summary` in a terminal surface unflattened.

The dialog and the stage page render one shared `StageReport` (`components/stage-report.tsx`), four cards in this order:

- `NowCard` (`stage-now.tsx`): the state legend as one sentence, then `AttentionBody` with the evidence, reason, note and numbered steps. The only place that says what to do.
- `HistoryCard` (`stage-history.tsx`, `stage-history-model.ts`): the live attention entry marked CURRENT, then `status.stages[i].history` newest first, six shown until "Show all"; each ended issue's mark comes from the prefix of its `ended_by`. Ruled disputes are not summarized on the attention card: the history card's adjudication rounds carry them.
- `StageDetails` (`stage-details.tsx`): a folded disclosure over `StageSectionGrid`, open by default on the page and closed in the dialog.
- `StageTokens` (`stage-tokens.tsx`): the token panel, outside the disclosure because the token contract tests require it visible.

The sidebar attention card shows only the current entry plus an "N earlier issues" link to `?stage=<id>#history`, which scrolls the history card into view. Long text sits in `text-box.tsx` boxes that scroll past 288px; no surface truncates. The web never shows the CLI's `less -R` line.

## Header layout

The header (`web/src/components/header.tsx`, rows in `header-lines.tsx`, styles in `web/src/header.css`, imported by `index.css` after `graph.css`) is one CSS grid with two arrangements. Below `lg`: the logo and the controls share the top row, then the daemon pill (centred), the plan name, and the progress plus rails each run full width. From `lg`: `grid-cols-[auto_1fr_auto_auto]`, the logo spans the left column and the name, daemon pill and controls share the first row.

The stage counts and merge counts are two `StatRail`s ("stages", "merge") of ruled cells: glyph, count, label. Zero counts are muted; an alarm cell (attention, unmerged, conflicts) with a non-zero count takes a tone wash (`.stat-cell-raised`). Merge glyphs are ◆ merged, ◇ unmerged and the ⚡ merge-conflict state glyph; hovering a merge count lists its stage ids. A third rail, "tokens" (`TokenLine` in `header-lines.tsx`, rendered only while the snapshot carries a token flow), sits beside them with two cells in one row: the plan total and the cache hit. Fresh tokens per minute appears with its chart in the sidebar token-flow panel. It draws no sparkline. The token flow's other web surfaces are listed in [token-flow-sources.md](token-flow-sources.md#surfaces). On phones a rail is a full-width grid of equal columns (`--cells`); from `sm` each cell sizes to its content.

Touch sizing lives in one media query, `(max-width: 639.98px), (pointer: coarse)`: header buttons and view tabs get a 40px minimum and the warp strip grows to 14px. It sets `min-height`/`min-width` because the vendored `ThemeToggle` takes no `className` and its `size-8` utility would outrank a components-layer `height`.

## Graph view and vendored aurora-ui

The overview route `/` draws the plan as a dependency graph with React Flow (`@xyflow/react`) laid out top-to-bottom by `@dagrejs/dagre` in `web/src/lib/graph.ts` (pure: layout, thread styling per source state, lineage). Cards are `web/src/components/graph/stage-node.tsx` (a head, then a tray holding the activity line, the context meter and, when the stage has a flow, the `NodeTokens` trace of `graph/node-tokens.tsx`), edges `web/src/components/graph/thread-edge.tsx`; click traces a stage's thread, double-click / Enter / the corner button opens the stage dialog. The dialog and its detail sections live one level up, NOT under `graph/`: `web/src/components/stage-modal.tsx` (opened from any route by `?stage=<id>`, so the back button closes it; `useOpenStage` sets the param, the footer links to the full page at `/stages/<id>` via `stage-href.ts`) and `web/src/components/stage-sections.tsx` (shared by the dialog and `web/src/routes/stage.tsx`). `/ledger` keeps the table. The detail sections are built as rows with a hover hint per field and drop absent or inapplicable fields (`web/src/components/stage-detail.tsx`); the five-cell context meter lights a cell at its midpoint (`Math.round(ratio * 5)`), which differs from the TUI's floor. The activity panel renders the server's durable stage event log, newest first at each event's recorded timestamp (`web/src/lib/activity.ts`, `loom/src/fs/stage_events.rs`). It includes history from before the page connected; the claim that it only logs transitions observed by the page is incorrect. Every node `buildNodes` emits declares `measured` alongside `width`/`height`: React Flow discards a node's handle bounds when a rebuilt node object arrives without it, and then draws no edges at all — the frontend rebuilds that array on every frame ([mistakes/web-dashboard-server.md](../mistakes/web-dashboard-server.md)).

`StageSummary` (`web/src/api/schema.ts`, the whole `stageSummarySchema`) already carries `session_alive`, `session_type` and `session_backend` (`native` | `tmux`), so a client can tell whether a stage has a live tmux session without a wire-model change. Cite the whole schema rather than a narrow line range: it shifts on every wire-model addition.

Styling: aurora-ui (`~/src/aurora-ui`, a copy-paste kit) is vendored under `web/src/aurora-ui/` (`shared/`, `feedback/`, `theme/`), excluded from oxfmt/oxlint, with one local adapter (`shared/ui/button.tsx` re-exports the shadcn Button so `@base-ui/react` is not needed). Its `tokens.css` is the palette; dark mode is the `.dark` class set by the kit's `ThemeProvider`/`ThemeToggle` (jotai atoms persisted under `loom:*`), not `prefers-color-scheme` media queries, so new CSS must use `.dark` selectors. Loom's `--tone-*` state tokens stay in `index.css`. jsdom tests need the `matchMedia`, `ResizeObserver` and `DOMMatrixReadOnly` stubs in `web/src/test/setup.ts`; React Flow draws edges only after measuring nodes, which jsdom never reports, so edge counts are asserted on the pure layout, not the DOM.

## Dashboard-local settings: themes and notifications

The settings dialog holds a second kind of setting, browser-local rather than synced to `~/.loom/config.toml` or `.loom/work/config.toml`: `SettingsWebui` (`web/src/components/settings-webui.tsx`), rendered by `Body` (`settings-dialog.tsx`) above `LoadNotice` and outside the `load.phase === "ready"` guard, so it shows even when `/api/config` is unreachable. Both preferences persist to `localStorage` via jotai's `atomWithStorage`, the mechanism the three theme atoms (`web/src/aurora-ui/shared/atoms/theme.ts`) already use under `loom:theme`, `loom:light-variant` and `loom:dark-variant`; the new notification preference follows the same `loom:` prefix as `NOTIFICATIONS_STORAGE_KEY = "loom:notifications"` (`web/src/state/notifications.ts`).

**Theme picker.** `web/src/components/theme-picker.tsx` offers three themes (Ledger, Walnut, Graphite) as `<button aria-pressed>` controls -- never `role="radio"`, which `settings-dialog.test.tsx` asserts is absent anywhere in the dialog. Each swatch draws a miniature of loom's own stage graph (a header strip over five stage cards on two ranks) in literal `oklch(...)` colours, not `var(--...)`, because a swatch must show a theme the viewer is not currently in and CSS variables would resolve against the active theme instead.

**Notifications derive from a snapshot diff, sharing its shape with `appendTransitions`.** The dashboard derives events from its merged snapshot, not from discrete server events (`snapshotSchema`, `web/src/api/schema.ts`, validates the `/ws` `full` message and the `/api/status` GET; `state` messages merge into the same snapshot, see [Broadcaster fallback](#broadcaster-fallback)). Notifications run on `full` and `state` messages only, never on `tick` or `tokens`. `notifiableEvents` (`web/src/lib/notify.ts`) diffs the previous snapshot against the next -- the same precedent `appendTransitions` already established, and both now share the exported `statusesById` helper from `activity.ts` rather than keeping a second copy. Three rules: (1) a new `${id}:${label}` entry in `attention`, skipping the purely informational `COMPLETION PENDING` label; (2) a stage transitioning to `needs-handoff`; (3) the whole run settling (every stage `skipped` or `completed` with `merged: true`, no `merge.conflicts`) -- `merge.pending` emptying is NOT that signal, since it empties after every individual merge. Events are capped at five per frame for rules 1-2; the run-finished event (rule 3) is delivered after the cap and never dropped. `watchNotificationPreference(store)` (`state/notifications.ts`) holds a `store.sub` on the preference atom for the app's lifetime (called once from `main.tsx`), because `atomWithStorage` only listens for the cross-tab `storage` event while mounted, and the dialog's own `useAtom` would leave a tab with the dialog closed still notifying after the user opted out in another tab.

**Notifications need a secure context.** `notificationSupport()` (`state/notifications.ts`) returns `"insecure"` when `window.isSecureContext !== true`; `loom status --web --host <lan-ip>` serves plain HTTP off loopback on purpose, and the Notifications API requires `https`, `localhost`, or a loopback address. The switch disables itself and explains why in that state, and turns itself back off on mount if permission was revoked or reset after the user opted in, so the UI never shows an "on" switch that delivers nothing.

**A filter matching only the dashboard section suppresses the server table's "nothing matches" line.** `onlyDashboardMatches` in `Body` (`settings-dialog.tsx`) skips `SettingsCards`/`SettingsLanes` when the query is non-empty, no server section matches, and `webuiMatches(query)` does -- otherwise a query like `theme` would render `nothing matches "theme"` (`settings-cards.tsx`, `settings-lanes.tsx`) beside a visible theme picker that does match.

## Seeing a Web Change Rendered From Inside the Sandbox

Run `vite` and Playwright's `chrome-headless-shell` (`~/.cache/ms-playwright/chromium_headless_shell-*/`) in ONE Bash command: a background `vite` dies when its command ends, and `google-chrome` fails on its process-singleton socket. Pass `--no-sandbox --no-proxy-server` and a `--user-data-dir` under `TMPDIR`, and write the PNG inside the worktree in a gitignored `*.local` directory, since the Read tool blocks paths outside the worktree.

## Stage node duration

Completed stage nodes, ledger rows, and stage headings use the shared `timeText` formatter in `web/src/lib/format.ts`. For completed states it prefers `elapsed_secs` (first start through completion, including contract writing and intervening waits), falling back to `execution_secs` for snapshots without elapsed time. Active states retain their execution-time display. This keeps completed duration aligned across dashboard surfaces.

## Contract and implementation activity entries

The dashboard activity list renders persisted `StageEvent` records. `update_stage` records status changes and changes to a nonempty session while Executing, so contract-to-implementation handoffs emit an event even without a status transition. Events capture `session_type` from the saved session record. The shared formatter renders `contract writing started` for contract sessions and `execution started` for stage sessions at their event timestamps. Rewriting the same session does not duplicate starts. Older events lacking a session type retain the generic `started` label; historical phase boundaries cannot be reconstructed from those records.
