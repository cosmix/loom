# Web Dashboard

> loom status --web: server, SPA, streaming

## Server

Hand-rolled HTTP/1.1 + WebSocket server, no framework: `loom/src/commands/status/web/mod.rs` (entry, `WorkDir::new(".")?.load()?` — needs `.loom/work` in the CWD or it exits before binding), `loom/src/commands/status/web/listener.rs` (bind: `bind_listener`/`bind_first_available_port`, host-parametric), `loom/src/commands/status/web/access.rs` (`AccessPolicy`, resolved once per server), `loom/src/commands/status/web/auth.rs` (dashboard-wide token/cookie, `Auth`), `loom/src/commands/status/web/bootstrap.rs` (WS-upgrade routing plus `bootstrap_terminal_token`), `loom/src/commands/status/web/connection.rs` (`gate`: Host, bootstrap, cookie check ahead of routing; CSP/security headers, `WRITE_TIMEOUT=5s` for whole-bundle HTTP writes vs the WebSocket lane's 250ms, `MAX_CONNECTIONS=64`/`MAX_WEBSOCKETS=48` sub-cap with an RAII slot guard and `DRAIN_DEADLINE=300ms` wall-clock bound on `drain_pending` for the accept loop), `loom/src/commands/status/web/broadcast.rs` (daemon-fed publish/subscribe), `loom/src/commands/status/web/ws.rs` (frame send/receive), `loom/src/commands/status/web/model.rs` (wire types, pinned by `loom/src/commands/status/web/model_tests.rs`).

Port selection is atomic at the bind call, on whichever host `--host` resolves to (`127.0.0.1` by default). Bare `loom status --web` tries `DEFAULT_PORT` (7373) and advances only on `AddrInUse`, so concurrent dashboards in separate repositories settle on different ports. `loom status --web PORT` binds that port exactly and preserves the contextual bind error; explicit `0` asks the OS for an ephemeral port. The printed URL always contains the listener's actual port.

It reuses existing TUI/status code rather than reimplementing it: `render::attention_entries`, `render::failure_label`, `scheduling_report::alerts`, `tick::read`, `data::collect_status_data`, `daemon_client::{connect,subscribe,is_socket_disconnected}`, `DaemonServer::check_status`.

**A second write surface: `--terminals`.** With that flag, `/ws/terminal/<stage>/<view|control>` upgrades to a keystroke channel into a live stage's tmux session, gated by a startup-minted, port-scoped cookie token independent of `/api/config`'s CSRF token. Full detail — admission order, the close-code contract, the poll-based bridge loop, and the frontend emulator — is [architecture/web-terminal.md](web-terminal.md). Apart from that lane and `/api/config`'s writes, every route stays GET/HEAD only; a non-loopback `--host` bind additionally authenticates all of them (below), which is a widening of who must authenticate, not of what any route does.

## Remote access (`--host`)

`AccessPolicy::resolve` (`access.rs:44-62`) runs once, from `listener.local_addr()` and `ServeOptions`, before any connection thread spawns; every accepted connection shares the one resolved policy plus its own `local_addr` (a wildcard bind's accepted address varies per client, the listener's bind address never does). `remote = !local_addr.ip().is_loopback()`, so a wildcard bind (`0.0.0.0`/`::`) is remote even for a client that happens to connect over loopback. A remote listener with no valid process token fails closed (`resolve` returns `Err`) rather than serving with no auth.

`ServeOptions.dashboard_token` / `.terminal_token` (`mod.rs:108-114`) must be equal when both are set (`auth::resolve_process_token`, `auth.rs:72-91`); `--terminals` still governs only whether `Broadcaster`/the terminal lane are enabled at all — a remote bind's token never implies terminal capability on its own.

Per connection, `AccessPolicy::host_allowed` (`access.rs:84-94`) checks `Host` against `local`, the accepted socket's own `local_addr()` — not the listener's bind address — so DNS names, wrong ports, and a proxy rewriting `Host` to a DNS name all fail; `localhost:<port>` passes only when `local` is itself loopback. `origin_allowed` (`access.rs:98-117`) requires an exact `http://<authority>` match against the same `local` whenever `Origin` is supplied, and requires it outright on writes and both WebSocket lanes. `AccessPolicy::authenticated` (`access.rs:75-80`) checks the `loom_dashboard_<port>` cookie against `Auth::cookie_matches`; always `true` in loopback posture, since that mode still authenticates nothing beyond `Host`/`Origin`.

The only way to obtain the cookie is `GET`/`HEAD /?token=<token>` (`bootstrap.rs::bootstrap_terminal_token`, :55-82), which 302-redirects to `/` with the cookie set on a match and 403s on a mismatch; a token in the query of any other path does nothing.

Limits: plain HTTP, no TLS; no reverse-proxy support (a proxy rewriting `Host` to a DNS name is refused); `--host` takes only IP literals and the exact alias `localhost`, never a DNS name; no config key for the bind host, CLI flag only; the token is per process, so restarting the dashboard invalidates every existing cookie.

## Broadcaster fallback

Daemon lane first; a `Response::Error` degrades to the file-poll lane with the message carried into `snapshot.notice`. A received frame resets the failure counter so a healthy daemon never falls back. After `FILE_POLL_COUNT` polls the loop retries the daemon (~10s reconnect cycle). Lock order is `last_body -> subscribers -> latest` in `publish`, and `subscribe` takes `subscribers` before reading `latest` (a suffix of that order), so no deadlock; dedup compares the body ignoring only `generated_at`, so a daemon-to-files handover always publishes once.

## Fixture contract

`loom/src/commands/status/web/model_tests.rs` pins the Rust model's exact serde output against `web/src/api/fixtures/statuses.json`, which the TS `zod` schema (`web/src/api/schema.ts`) and tests consume. Changing the wire model means updating the fixture and schema in the same change, or the TS tests and the zod parse both fail. The one gap: the fixture test hardcodes the 13 `StageStatus` variants instead of deriving them from an exhaustive match, so a 14th variant compiles Rust-side and only fails at runtime on the TS side (zod rejects the whole snapshot, page renders blank).

## zod and the CSP

The CSP in `http.rs` (`CONTENT_SECURITY_POLICY`) sets no `script-src`, so `default-src 'self'` forbids `new Function`. zod 4 probes for eval support with `new Function("")` the first time an object schema is built. It catches the throw, but Chrome still logs a CSP violation on every page load. `web/src/api/zod.ts` calls `z.config({ jitless: true })`, which skips the probe, and re-exports `z`. Every schema module must import `z` from `@/api/zod`, because schemas are built when the module loads and a `z.config` call in `main.tsx` would run after them. `web/.oxlintrc.json` enforces this with `no-restricted-imports` on `"zod"`, and `web/src/api/zod.test.ts` wraps `globalThis.Function` in a counting proxy before a dynamic import of `@/api/schema`, then asserts zero calls. The Vite dev server sends no CSP, so the violation only shows under `loom status --web` or a `vite preview` given the same header.

## Committed dist + build.rs embedding

`web/dist` is a committed build output, embedded via `include_bytes!` at compile time: `loom/build/assets.rs`'s `generate_web_assets` (called from `loom/build.rs`) walks `web/dist` and writes a generated Rust source file under Cargo's `OUT_DIR` (not checked in) that the crate `include!`s. It compares generated content before writing (`write_if_changed`) — writing unconditionally would make the file's fresh mtime trigger a full crate rebuild on every `cargo build`. Rebuild and commit `dist/` with every change to `web/src/` (`cd web && bun install && bun run build`).

## CI/scripts

Any script invoking `loom status --web` needs its own `.loom/work` in the CWD — `WorkDir::new(".")` bails before binding otherwise, and a clean CI checkout never has one since `.loom/work` is gitignored (`scripts/smoke-web-dashboard.sh` creates a scratch workspace for this reason).

## Graph view and vendored aurora-ui (2026-09-05)

The overview route `/` draws the plan as a dependency graph with React Flow (`@xyflow/react`) laid out top-to-bottom by `@dagrejs/dagre` in `web/src/lib/graph.ts` (pure: layout, thread styling per source state, lineage). Cards are `web/src/components/graph/stage-node.tsx`, edges `web/src/components/graph/thread-edge.tsx`; click traces a stage's thread, double-click / Enter / the corner button opens the stage dialog. The dialog and its detail sections live one level up, NOT under `graph/`: `web/src/components/stage-modal.tsx` (opened from any route by `?stage=<id>`, so the back button closes it; `useOpenStage` sets the param, the footer links to the full page at `/stages/<id>` via `stage-href.ts`) and `web/src/components/stage-sections.tsx` (shared by the dialog and `web/src/routes/stage.tsx`). `/ledger` keeps the table. The detail sections are built as rows with a hover hint per field and drop absent or inapplicable fields (`web/src/components/stage-detail.tsx`); the five-cell context meter lights a cell at its midpoint (`Math.round(ratio * 5)`), which differs from the TUI's floor. The activity panel treats the first frame as a baseline and logs only transitions the page observes (`web/src/lib/activity.ts`), unlike the TUI's `TuiActivityLog::update`, which logs every stage on its first frame stamped with the load time. Every node `buildNodes` emits declares `measured` alongside `width`/`height`: React Flow discards a node's handle bounds when a rebuilt node object arrives without it, and then draws no edges at all — the frontend rebuilds that array on every frame ([mistakes/web-dashboard-server.md](../mistakes/web-dashboard-server.md)).

`StageSummary` (`web/src/api/schema.ts:79-86`) already carries `session_alive`, `session_type` and `session_backend` (`native` | `tmux`), so a client can tell whether a stage has a live tmux session without a wire-model change.

Styling: aurora-ui (`~/src/aurora-ui`, a copy-paste kit) is vendored under `web/src/aurora-ui/` (`shared/`, `feedback/`, `theme/`), excluded from oxfmt/oxlint, with one local adapter (`shared/ui/button.tsx` re-exports the shadcn Button so `@base-ui/react` is not needed). Its `tokens.css` is the palette; dark mode is the `.dark` class set by the kit's `ThemeProvider`/`ThemeToggle` (jotai atoms persisted under `loom:*`), no longer `prefers-color-scheme` media queries, so new CSS must use `.dark` selectors. Loom's `--tone-*` state tokens stay in `index.css`. jsdom tests need the `matchMedia`, `ResizeObserver` and `DOMMatrixReadOnly` stubs in `web/src/test/setup.ts`; React Flow draws edges only after measuring nodes, which jsdom never reports, so edge counts are asserted on the pure layout, not the DOM.

## Config read/write surface (`/api/config`)

The dashboard's only write route, and the first one it ever had: `loom/src/commands/status/web/config_api.rs` plus `config_api/{wire,workspace,entries,apply,csrf,request}.rs`. `GET` returns every `user_config::keys::KEYS` entry projected over both config scopes; `POST` writes or clears one key at one scope. The React side is `web/src/api/config.ts` and `web/src/components/settings-*`, opened from the header via `useOpenSettings()` (`settings-dialog.tsx`), which takes no argument and sets `?settings=1` — the param's value is never read, it only gates whether the dialog is open.

**Two scopes, one per-key project tier.** User scope is `~/.loom/config.toml` (the typed `KEYS` registry); project scope is `<repo>/.loom/work/config.toml`. `workspace.rs::resolve` is the ONE place naming which keys the project tier backs, and `backs()` asks `resolve` rather than keeping a second list beside it. Every project-backed key resolves per key (operator decision 2026-09-13, which removed the old SECTION-level tier for `[terminal]`/`[context]`): `Workspace::shadows` is true only when the project file supplies the key, and `Workspace::value_of` for an unsupplied key is the user tier's value (the built-in when the user file is silent), so the project lane shows what it inherits. `terminal.backend` and `context.ceiling_tokens` match by exact name and parse through the same functions as the runtime readers — `TerminalConfig::backend_from_section` (`fs/work_dir/config_sections/terminal_config.rs`) and `ContextConfig::resolve_with_user_ceiling` (`fs/work_dir/context_config.rs`) — so a malformed section fails both; a project `model_window_tokens` counts as supplying `context.ceiling_tokens`. `[pressure]`/`[models]` keys go through `section_key`, matched on `spec.section`, so a key added to either section needs no edit to `resolve`. A `[context]` kept alive by a sibling key (`subagent_ceiling_tokens`, `prompt_cache_split`) no longer shadows the user ceiling, and the API reports the fallthrough. `remove_key` (`fs/work_dir/config_sections.rs`) still drops a section its removal empties, as tidiness. `insert_key` exists because `write_section`/`merge_section` serialize a whole struct, which would freeze the derived `subagent_ceiling_tokens` into the file and drop `prompt_cache_split`, which no struct owns; `loom init` uses it to write only the ceiling keys a plan sets.

**Three write gates, all required** (`config_api/request.rs`, `http.rs`). `Host` is applied to every request ahead of routing, unchanged — now policy-driven (`AccessPolicy::host_allowed`), so it is the DNS-rebinding check in loopback posture and the exact-socket-identity check in remote posture. Then `AccessPolicy::origin_allowed(.., OriginRequirement::Required)` (`config_api/request.rs:101`) — this replaces an earlier plain `origin_allowed_strict` call: loopback posture still requires `Origin` PRESENT and loopback via `http::origin_allowed_strict`, and remote posture requires `Origin` to match the connection's own address exactly, unlike the lenient `origin_allowed` that GET keeps because a browser sends no `Origin` on a same-origin GET. Then a per-process double-submit CSRF token (`csrf.rs`, CSPRNG, constant-time compare) handed out only in the `GET /api/config` body and required in `X-Loom-Csrf`. The mechanism rests entirely on serving NO CORS headers: a cross-site page can send the request but cannot read the token, and cannot set the custom header (or `Content-Type: application/json`, deliberately required for the same reason) without a preflight that fails. **Adding any `Access-Control-Allow-*` header hands both halves back to the attacker.** Bodies need a digits-only `Content-Length` within `MAX_BODY_BYTES` (8 KiB); nothing past the cap is ever read.

**`default` on the wire.** Each entry carries the built-in it resolves to when neither scope sets it, sourced from `UserConfig::default().value_of(spec)` — never a second table of defaults. It is not recoverable from the rest of the entry: `user.value` is the RESOLVED user value, so it stops being the built-in the moment `user.set` turns true.

**Frontend: three-lane layout, not a scope switch.** The dialog renders the three tiers (built-in, user, project) as columns of one table (`settings-lanes.tsx`, `settings-lanes-cells.tsx`) or, below 700px via `useMediaQuery("(max-width: 699px)")`, as one card per row (`settings-cards.tsx`); both read from `sectionRows()`/`filterSections()` in `settings-model.ts`, which pairs `<prefix>_model`/`<prefix>_effort` keys into one row. Each user/project cell is a `LaneSlot` (`settings-control.tsx`) with its own clear button; the built-in column renders read-only via `BuiltinValue`, showing the wire's `default`. There is no scope-switch control and no "reset to built-in" button any more: an earlier version of this component, the provenance rail with a scope switch and reset button, does not exist — it was deleted along with its `railStops`/`RailStop` helpers.

**Fixture.** `web/src/api/fixtures/config.json` is pinned by `the_config_fixture_matches_a_real_payload` and covers all three `effective.source` values, plus `scopes: [user, project]` on every `pressure.*`/`models.*` entry, not just `terminal`/`context`. It now pins the `default` values and the enum variant lists too, so moving ANY built-in — not just `CLAUDE_MODELS`/`CODEX_MODELS` — fails that test until the fixture is regenerated. The recipe is in the test's doc comment.
