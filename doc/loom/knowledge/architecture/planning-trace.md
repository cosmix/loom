# Planning Trace

>

## Not the Source Graph

The planning trace links the planning documents of a feature: vision rows, product sections and their headings, metaplan entries, plans and stages, briefs and findings. It is not the `loom map` source graph ([Source Graph](source-graph.md)): no code symbol is a node, nothing in it reads or writes `.loom/` graph state, and code, wire, routes and UI say `trace`, never `graph`. Code: `loom/src/planning/trace/` (model, `tokens`, `settle`, `build/`), `loom/src/planning/findings/` (ledger), `loom/src/plan_server/trace/` (routes), `loom/src/plan_server/wire/trace.rs` (wire), `web/src/plan/trace/` (browser).

## Edge Lines and Tokens

Edges are plain lines in the documents, so a reader without `loom plan` follows them; no sidecar file holds edges or settle state. Each starts at column 0, outside fenced code, before the first `<!-- loom METADATA` line:

| Line | Where | Meaning |
| --- | --- | --- |
| `Covers: <tokens>` | in a metaplan entry, under its `##` heading | the entry's plan delivers these spec nodes (`MetaplanEntry.covers`, `bad_covers`) |
| `Implements: <tokens>` | the plan's declaration (`planning/implements.rs`) | the plan delivers these sections or headings |
| `Implements (stage:<id>): <tokens>` | anywhere in a plan's prose | one stage delivers these headings; the stage id lives in the YAML, so the plan schema is unchanged |
| `About: <tokens>` | in a findings ledger entry | the nodes a finding concerns |

`planning::trace::tokens` parses the tokens: `section_NN[.md]`, `section_NN#<anchor>`, `vision[#anchor]`, `metaplan[#anchor]`, `PLAN-<slug>.md` (any lifecycle prefix), `PLAN-<slug>.md#stage:<id>` or `#<anchor>`, and `[label](<target>)`. An anchor is `sections::github_slug`; a malformed token is kept as written (`bad_tokens`) and a well-formed token naming nothing resolves to `Unresolved`; both reach `loom plan check` (codes in [Planning Document Model](planning-document-model.md#project-view-and-checklist)). `section_refs(value) -> (Vec<SectionRef>, Vec<String>)` is shared by `Covers:`, stage lines and `Implements:`; `is_plan_token` (built on `tokens()`) validates a `planned` finding detail. A brief's link to its stage is derived from its bundle path `briefs/<slug>/<stage-id>/...`; there is no `Serves:` line.

## Settled Line

`Settled: <body> [stub <stub>] [upstream <upstream>]` (`planning/trace/settle.rs`; each hash is the first 12 lowercase hex digits of a SHA-256). The line is the document's own record that a reader settled it; the name avoids `Status:`, which prose already uses. Placement: its own paragraph directly after the first `#` heading, or after an `Implements:` anchor line that follows the heading; text glued under an `Implements:` line makes it no anchor and the mark goes under the heading, and a document with no level-1 heading gets the line at the top. `mark` replaces in place and returns the text unchanged for the same line; `clear` removes every `Settled:` line with the blank line before each.

- **Body hash**: `normalized_hash` of the text without its Settled lines (`settle::unsettled`, which returns the text borrowed when it holds none; `clear` and `body_hash` both go through it). Summary hashes strip the same lines through the same function (`planning/summary/hashes.rs` `SourceHashes`, [Summary Store](summary-store.md#states)), so settling or unsettling a document changes no summary's recorded hash and queues no rebuild. For a plan the body also covers the brief bundle (`briefs::bundle_files`), each brief's path and text in path order; a brief without Markdown text is hashed by `Project::fingerprint`.
- **Stub hash**: a product section's vision table row; a plan's metaplan entry span. The vision, the metaplan and a plan with no entry have none.
- **Upstream hash** (plans only): the spans of every implemented heading plus, for a section implemented whole, `settle::body_hash` of its text. It is not the section's `file_hash`, which includes the section's own Settled line: settling a section would flip every plan implementing it to `upstream_changed`.
- **States**, in this order: `draft` (no line or an unparsable one, plan problem `settled-bad`; a second line is `settled-duplicate`), `revised` (body differs), `stub_changed`, `upstream_changed`, `settled`.
- **Writers**: only the settle route, at the reader's request. Sessions never write or edit a Settled line; a session that edits a settled document says so, and the document reads `revised` until settled again. A locked document (`IN_PROGRESS-`, `DONE-`, `RETIRED-`, archive) keeps the line it had and cannot be settled.
- **Unresolved points**: a document holding `(My call` markers (case-insensitive) or open questions needs `confirm=1`; without it the route answers 409 `unresolved` with the counts.
- **Settled version**: `GET /api/settled-version` finds the newest commit whose version of the file holds the current line (`git log -S<line> -1`); a line never committed (a settle whose commit was skipped, refused or not yet finished) answers `commit: null` and the page shows no diff.

## The Trace Model

`build_trace` (`planning/trace/build.rs`, `build/docs.rs`, `claims.rs`, `gaps.rs`, `ledger.rs`) runs for every feature at the end of `Project::derive`, after every feature's documents are in place (a trace reads other features' plans), reads only the loaded project and is kept on `Feature.trace`. `Trace` holds `documents` (vision, sections listed or written, metaplan, plans written or only named by an entry), `headings` (level-2 headings of written sections, except the anchors `open-questions`, `out-of-scope` and `out-of-scope-for-this-section`, which the section skill mandates), `entries`, `findings`, `gaps`, `frontier` and `problems` (`TraceProblem` is `planning::problems::Problem`).

- **`TraceDoc`**: `role` (`Vision`, `Section`, `Metaplan`, `Plan`), `progress` (`Stub`, `Written`, `Planned`, `Built`, `Running`, `Done`), `settle`, `settleable`, `stub`, `bundle`, `my_calls`, `open_questions` and `current`, the line settling now would write. `settleable` is true for a written, unlocked document except the vision and metaplan of a feature whose plans are all done; done work is final, so it carries no settle state, gap or control, while product sections stay open to follow-up plans.
- **Coverage**: a heading is covered by an entry whose `Covers:` names it or its section, a plan whose `Implements:` names it (or its section with no anchor), or a stage line naming it. Coverage re-reads the `Implements:` line with `section_refs`, because `ImplementsLine.anchors` merges `section_04#a, section_04` and loses that the section was named whole. A stage line naming a section whole covers all its headings. A heading nothing covers is an `Uncovered` gap.
- **Gaps** (`GapKind` order): `Revised`, `StubChanged`, `UpstreamChanged`, `Revisit`, `Settle`, `Uncovered`, `Triage`. The first four exist only for written, unlocked documents. `Revisit` marks a metaplan entry whose plan has not started running (the node is the written plan, else `metaplan#entry`) and carries the ids of findings folded into it and of open findings whose About names a heading the entry covers or its plan implements; this is how a finding from wave 1 reaches plan 4 before it runs.
- **Frontier**: the first five gaps, one per document, in gap order; `Uncovered` counts only headings of settled sections; one `Triage` gap carries the open-finding count. A hint is a short link; the frontier starts no session (next actions stay offers).
- **Stub drift** is a session duty plus a recorded state. Whether a body outgrew its stub cannot be decided from hashes, so the skills tell sessions to update the stub in the same turn (or ask) and a stub that changes after settling reads `stub_changed`; no agent judges drift in the background.

## Findings Ledger

`doc/plans/<f>/findings.md` is one file per feature, plain Markdown (`DocKind::Other`): `# Findings`, then entries `## F-<n> <title>` with `About:`, optional `Source:` and `Status:` lines and one text paragraph. `Status:` is `open`, `planned PLAN-<slug>.md`, `folded metaplan#<anchor>` or `dismissed: <reason>`; a missing or unknown value reads open and raises `findings-bad-status`. Run reviews stay the immutable evidence; the ledger holds triage state.

- **Import**: `findings::import_review(root, plan_rel, review_text)` appends one entry per item of the run review's `## Open Findings` and `## Open Questions` (`run_review::review_items`) not already present, keyed by `Source: REVIEW-<stem>.md#<section anchor> (<stage id>, <12-hex hash of the item text>)`, with About `PLAN-<slug>.md#stage:<id>` followed by the plan's `Implements:` tokens, and returns the count; a standalone plan imports nothing. It runs in `fs::plan_lifecycle::mark_plan_done_if_all_merged` right after `plan_review::generate`, in the daemon's host job against the main checkout, so the ledger is an uncommitted change there. A failure keeps the plan retryable, and a repeat run adds nothing.
- **Untrusted text**: item text is agent-written. The title is the first 80 characters cut on a char boundary with newlines as spaces; the paragraph is one line, and text that starts with a heading `#`, a code fence (`` ` `` or `~`), a metadata key or a backslash gets a leading backslash so a finding never changes the ledger's structure (`findings/text.rs` `paragraph`, `unescape`). A dismissal reason is one line, control characters removed (whitespace controls become spaces), trimmed, at most 200 characters (`REASON_MAX`), never empty. The browser draws every ledger string as text, never as HTML or Markdown.
- **Writes**: import runs under `fs::locking::lock_plan` and writes with `replace_no_follow` or `restore_no_follow`, refusing a symlinked ledger file or directory above it; never `locking::locked_write`, which opens the parent following symlinks. The status route writes through `files::save::save_document`.
- **Folding**: a finding `folded metaplan#<anchor>` points at an entry whose plan has not started running; that entry reads "revisit before writing" or "revisit before running". `Status` lines are set by the metaplan skill after it writes or edits the entry.

## Routes and trace_changed

`plan_server/trace/mod.rs` `routes()` registers four routes with one line in `routes::all_routes`; the write routes build the new text and call `files::save::save_document`, so authoring, the lock, the opened-hash check, locked documents and symlinks follow the save route. `path` is relative to `doc/` as in `/api/save`.

| Route | Role | Effect |
| --- | --- | --- |
| `GET /api/trace/<feature>` | Viewer | the `TraceView` (`wire/trace.rs`); 404 `not_found` for an unknown feature |
| `POST /api/settle?path=&hash=[&confirm=1][&clear=1]` | HolderOrTake | writes or removes the Settled line and answers at once with `commit` pending or not committed ([Settle Commits](#settle-commits)); 409 on a stale hash, 409 `unresolved`, 409 `stale` while the loaded project trails the file, 422 for a plan with validation errors, 403 `locked`, 400 for a path with no trace document or a role that cannot be settled |
| `POST /api/findings/status` | HolderOrTake | JSON `{ feature, id, hash, status: { kind, detail } }`; 409 when the ledger hash no longer matches, before the new text is built; 400 for an unknown id, an empty detail, a `planned` detail that is no plan token or a `folded` detail naming no metaplan entry |
| `GET /api/settled-version?path=` | Viewer | `{ commit }` |

`TraceView` mirrors `Trace` with repository-relative `/` paths, snake_case enums, `null` options and `deny_unknown_fields`; a finding's status is `{ kind, detail }`. `wire/fixtures/trace.json` is written by a writer test from a fixed project (`LOOM_WRITE_FIXTURES=1`) and checked byte for byte; `web/src/plan/api/fixtures/trace.json` holds the same bytes and a web schema test parses it (`schema-trace.ts`). `PlanMessage::TraceChanged { feature }` goes out after a watcher batch for each feature whose `TraceView` differs (`trace/changed.rs`, compared as the checklist views are); the browser refetches that feature's trace. A socket test waits for a specific frame with an explicit deadline over `socket.read()`, because the server keeps sending other frames ([the hang](../mistakes/planner-follow-ups-delivery.md#a-socket-test-waited-on-a-frame-that-never-came)).

## Settle Commits

Settling writes the line at once and commits it afterwards, off the request path. Loom writes the line once; the commit either holds what was written or the reader is told to settle again.

### Request and queue

`POST /api/settle` (`plan_server/trace/settle_route.rs`) writes the Settled line through `save_document`, records what the line covers in a `SettleJob`, queues the job and answers at once `{result: "saved", hash, validation, commit}`. `commit` is `{state: "pending", job}` or `{state: "not_committed", reason}` when the queue cannot take the job (`SettleCommitStart`, `wire/trace.rs`). A job id is a string `<8-hex server token>-<n>`, so a browser that reconnects to another server never takes that server's job for its own. The job carries the browser, the document, the plan's briefs, `written` (the hash of the text the settle wrote) and `seen`, one `BriefSeen` per brief (`settle_job.rs`): `Text` holds the normalized hash of the project's cached text of the brief, which the line's body hash covered; `Bytes` holds a hash of the file's bytes taken when the line was written, for a brief the project holds no text for (not Markdown, or unreadable).

`trace/settle_queue.rs` runs jobs FIFO on one worker thread (`loom-plan-settle`) per server, started with the first push and ended when the queue is empty, registered through `PlanContext::own_worker`. The shutdown step "settle commits" stops new jobs: a settle during shutdown answers `not_committed` with "loom plan is stopping". Queued jobs end as `not_committed` ("loom plan stopped before the commit ran; settle again") while the sockets are still up, and the commit in flight runs to its end (a server stop never cuts git or the user's hooks short), the drain printing "waiting for a settle commit's hooks to finish". A second Ctrl-C stops the wait and leaves the commit running. Lines of dropped jobs stay written and uncommitted. A panic in a job ends it `not_committed` ("the commit failed unexpectedly; settle again"); the job and its announcement both run inside `catch_unwind`, so a panic in either ends that job alone and the worker goes on to `next`, which clears `running` before the worker ends and the drain never waits on a worker that is gone.

Each job's end sends `PlanMessage::SettleCommit` `{type: "settle_commit", job, path, state, commit, reason}` (`SettleCommitView`): `state` is `committed`, `unchanged` (the paths already matched HEAD) or `not_committed`; `commit` is the settle's own commit, set for `committed` only and null there when HEAD does not show it as the settle's. The message has no document hash. A reason that carries git's or a hook's output goes only to the settling browser (`PlanHub::send_to_browser`, `ws/hub.rs`); every other browser (`send_to_others`) reads "the commit failed" or "git reported a problem with the commit". Loom's own fixed reasons go to everyone.

### The git side

`trace/settle_commit.rs` and `trace/settle_head.rs` commit the settled paths: the document and, on settle, the plan's brief bundle (an unsettle commits the document alone). The message is `docs(<feature>): settle|unsettle <path under doc/>` with no trailers. The commit is the user's own, run through `git::user_git::user_git` (their hooks, signing and identity, never `--no-verify`; loom's `git::runner` calls switch hooks off and are not used for it). Outside a git repository, or while a merge, rebase, cherry-pick or revert is in progress (marker files in the git directory), the commit is skipped with a reason. Details that each fix a misbehaviour with hooks ([the mistake](../mistakes/planner-ui-repair.md#a-settle-commit-through-git-commit---only-misbehaved-under-hooks)):

- Pathspecs are `:(literal)<path>` per argument (`git/user_git.rs` `literal`), never the global `--literal-pathspecs`, which would export `GIT_LITERAL_PATHSPECS=1` to the hooks and change what their own git commands match. `user_git` removes `GIT_LITERAL_PATHSPECS`, `GIT_GLOB_PATHSPECS`, `GIT_NOGLOB_PATHSPECS` and `GIT_ICASE_PATHSPECS` from the environment it passes on; `run_literal` runs loom's own git with the same four set to `0`. The run commit (`plan_server/run/commit.rs`) uses the same helpers.
- Before `git add`, `IndexBefore::read` (`git/user_git.rs`) records HEAD, the paths the user has staged (`git diff-index --cached --name-only -z --no-renames <HEAD>`; on an unborn branch every index entry, `git ls-files -z --full-name -- ':(top)'`) and where the project root sits under the work tree's top (`git rev-parse --show-prefix`). A new brief is then `git add`ed (`commit --only` takes only paths git knows); a `git add` that fails unstages what it added (`git rm --cached --ignore-unmatch`). `run_commit` returns `Result<(), String>`: `Err` carries git's refusal, a timeout or a start failure, and git may have made the commit all the same.
- `after_commit` (`settle_head.rs`) trusts HEAD, not git's exit status. Git ignores a `post-commit` hook's exit status, but a hook past the deadline, past the output limit or leaving a descendant on git's pipes ends the run badly after the commit exists. HEAD unmoved: nothing was committed, and the briefs the settle added are unstaged. HEAD moved to the settle's own commit, or git succeeded: `IndexBefore::reset` puts the index right. HEAD moved while git failed and the commit is not the settle's: the job ends `not_committed`, the index left as it was but for the added briefs HEAD does not hold (`git cat-file -e HEAD:./<path>` fails), which are unstaged.
- `IndexBefore::reset` exists because a commit given pathspecs has `--only` semantics: git commits a temporary index built from HEAD and the pathspec's paths, on which the hooks run, and keeps the real index with the pathspec's paths as the work tree held them before the hooks. A hook's `git add`, of a settled file or any other, reaches only the temporary index, so the real one would hold a staged reversal of the hook's work. The reset lists the paths the commit changed (`git diff-tree -r --name-only -z --no-renames <before> <commit>`, `--root` on an unborn branch; `HEAD` when the commit's id is unknown) and resets to the commit (`git reset -q` over `:(top,literal)` pathspecs) the settled paths and every changed path the user had not staged; a reset path the commit does not hold leaves the index, which unstages an uncommitted new brief. A changed path the user had staged keeps its entry, and when that entry differs from the commit the outcome says "A commit hook also committed <paths>, whose changes staged before the commit stay staged and differ from it; check them before the next commit." A listing or reset git refused adds "The index could not be reset to the commit (<why>), so it may still hold the text from before the commit hooks ran." The run commit reads `IndexBefore` before its `git add` and resets after any commit that moved HEAD, each note one `git reset` stderr line.
- `own_commit` finds the settle's commit: the oldest commit since the old HEAD (at most `OWN_COMMIT_DEPTH`, 8, back) whose only parent is the old HEAD (no parent on an unborn branch) and whose subject is the settle message, read with `git log --encoding=UTF-8` so `i18n.logOutputEncoding` cannot change it. Git failing after the commit ends `committed` with "The commit was made, but <reason>."; HEAD moved to a commit that is not the settle's ends `committed` without a sha when git succeeded and `not_committed` when it failed.
- `COMMIT_TIMEOUT` is 10 minutes (revisit if projects' hooks routinely run longer). On expiry `process::run_bounded_terminating_output` sends SIGTERM to the process group, then SIGKILL after `TERM_GRACE` (5 s) (`process/owned.rs` `Expiry::Terminate`), because git removes `index.lock` on SIGTERM and not on SIGKILL. A lock that outlives the kill is named in the reason.

### The job

`trace/settle_job.rs` runs one job and decides how it ended:

- Before the commit it skips the job when the document's normalized hash on disk differs from `written` ("the document changed before it could be committed; settle again") or when a brief no longer matches its `BriefSeen` ("the plan's briefs changed before they could be committed; settle again"). An unsettle checks no brief.
- After a commit, `changed_since` compares what the settle took with the commit and with the work tree. When the settle's commit is known and its blobs (`settle_commit.rs` `committed_bytes`, `git cat-file blob <sha>:./<path>`; the document normalized as the settle hashes it, a brief matched by its `BriefSeen`) differ from what was settled, the job ends `committed` with "A commit hook changed the document after it was settled. Settle this version to record it.": the work tree held the settled text when the commit started, so a hook changed what went in. A commit that holds the settled text beside a work tree that does not, or a commit whose id is unknown beside a changed work tree, ends with "The document changed after it was settled. Settle this version to record it.": a hook's write beside the commit and a reader's edit while the hooks ran read the same. A git that cannot read a blob claims no difference. Either way the line describes the text from before, so the document reads Revised until the reader settles again; only a reader's settle writes the line.

### Outcomes in the browser

- `trace/settle-commits.ts` `useSettleCommits(path, onOutcome)` subscribes to `settle_commit` frames of one document. `useCommitNote` (`trace/settle-note.ts`) keeps one `Waiting` record per press, in press order, so a press while an earlier press's commit still runs waits beside it. An outcome ends the record with its job id; one that arrives before the POST answer names the job is buffered in the last press's `early`. The note follows the last press; an earlier press's commit that ends meanwhile changes the note only when it went wrong. An outcome with another job id, such as another server's or another browser's settle, is ignored.
- The note beside the control is "Committing…" while pending, "Committed <sha7>" for `COMMITTED_NOTE_MS` (5 s), and an alert for a failure ("Settled, but not committed: <reason>", "Unsettled, …"; "Settled and committed. <reason>" when the commit left a note, including the hook-changed and changed-after sentences). `unchanged` leaves no note. A reconnect while presses wait (a change of `connectionEpochAtom`) marks each lost, and the last press's note turns into the alert "The commit result was lost; check git log." once its job is known; an outcome that arrives after all still replaces it.
- `useSettle` and `useWorkingEnds` (`trace/settle-flow.ts`) release the control (`working` to idle) once the trace's settle state differs from the press-time state and the opened document's hash moved off the press-time hash; after `SETTLE_WAIT_MS` (10 s) it releases with the `late` notice, which clears when the trace's state changes.
- `trace/settled-changes.tsx` `useSettledVersion` asks `/api/settled-version` on mount, when the document's settle state or body changes, and on any `settle_commit` for the document. A settled version never committed (`commit: null`) disables See what changed with the reason "never committed".

## Plan Summaries and the Bundle

A plan's summary covers its brief bundle: the plan may cite every brief file, must cite each brief with Markdown text, and carries a `bundle` front matter map; a changed brief makes the summary out of date ([Summary Store](summary-store.md#file-format)). The plan's summary and source pages list its briefs (`TraceDoc.bundle`) in a Briefs section of the plan page (`plan-extras.tsx`, `briefs-card.tsx`, `brief-groups.ts`): mono file names in a two-column list grouped by stage folder, each linked to its source. Briefs are not spine rows, because the 18rem column cannot hold them. Summaries exist for drafts and settled documents alike.

## Browser

The screens follow `doc/plans/briefs/trace-screens-redesign/design.md`; the spacing, type and look values are in `web/src/plan/ui/DESIGN.md`. The rule behind them: state is drawn only where it needs attention, and detail opens on demand ([the mistake](../mistakes/planner-design-brainstorm.md#trace-mockups-showed-every-concept-at-once-and-were-checked-only-in-chrome)).

- **State** (`trace/state.ts`): `traceAtom(feature)` is fetched on first use and refetched on `trace_changed` for that feature and on resync; a failed refetch keeps the loaded view and records the error. `trace-gate.tsx` draws the load and error states for the two trace pages. Every reader of a settle state goes through `shownSettle` (null unless `settleable`).
- **Spine head** (`trace/spine-head.tsx`, `frontierHead` in `trace/model.ts`): the trace's first frontier gap as one link to the place that needs the reader, in the instruments' well: a "Next" label, the gap's glyph (`HeadGlyph`: a row glyph kind or the Findings instrument glyph) with a verb and the document's name on one ellipsis-cut line (Triage "3 findings", Cover <heading> landing on its Coverage row, Revisit, Review, Read; a plan's short slug in mono), then a muted reason line and, for a revised section, the flagged plan. `FrontierHead` is `{verb, name, nameIsSlug, reason, detail, glyph, to}`. It is not a primary button. Nothing when the frontier is empty or the trace is not loaded. The spine's row glyphs are in [Spine](planner-feature-screens.md#spine).
- **Heading** (`concept/page-heading.tsx`, `ui/doc-heading.tsx`, `trace/trace-heading.css`): the summary-page look is scoped to `.concept-page-column .doc-heading` and done in CSS only (the toolbar dissolves with `display: contents`, grid `order` sets breadcrumb and switch, title, scope standfirst, chip row, action row), because the shared bar CSS is frozen by `doc-heading` tests and Files mode keeps the bar. Standalone plan summaries share the concept column and get the same look. The chip row is one line (freshness, Rebuild, settle state, coverage chip); the action row holds Edit, Discuss and the settle control, with Open all collapsing to a 32px glyph (its words stay its accessible name) when the row would overflow. `DocHeading` takes a `standfirst` prop drawn between the title row and the toolbar.
- **Scope standfirst** (`trace/scope-line.tsx`, `.trace-standfirst`): the stub under the title, linked "from the vision ↗" or "from the metaplan ↗", with the amber "changed since you settled this" note and the one See what changed link for a changed stub. Reading text carries no chips; an opened passage ends in a "Covered by <plan> › <stage> · n open findings" line (`trace/passage-coverage.tsx`).
- **Settle control** (`settle-control.tsx`, `settle-menu.tsx`, `settle-surface.tsx`, `settle-confirm.tsx`, `settle-flow.ts`): one always-mounted button anchored by Radix `Popover.Anchor`, so focus survives the label change. The label is the state, read from the trace's `doc.settle`, not from the post's answer, so `useSettle(feature, path, hash, state)` keeps the control pending after a `saved` answer: the `working` phase records the state and the opened document's hash at the press and holds until the trace shows a different state and the hash has moved off the press-time hash. A refusal, a notice or a confirm answer releases it at once; after `SETTLE_WAIT_MS` (10 s) it releases with the notice "Saved, but this page has not caught up yet. Reload the page to see the new state." (the `late` phase, which clears once the trace's state changes). The commit note beside the button is described under [Settle Commits](#settle-commits). A synchronous `busy` ref stops a second post before the first renders. While pending the button carries `aria-busy` and `aria-disabled` and reads "Settling…" or "Unsettling…"; it stays the same element, so focus stays ([the mistake](../mistakes/planner-ui-repair.md#mark-settled-returned-to-idle-before-its-label-changed)). Its menu (Unsettle, Settle this version) and the unresolved confirm share one popover, which is a bottom sheet under 760px. A 409 `unresolved` opens a popover titled "Settle with open items?" quoting the points; `settlePoints` (`trace/doc-model.ts`) mirrors the server's open-question count (`planning/pressure.rs` `open_questions`): top-level `-`, `*` and `N.` items under a heading titled "Open questions" (ASCII case-insensitive), with a TS port of the scanner's fence rules (`fenceMask`) also used for My call lines, so a change to either side changes both. Cancel and Escape return focus to the button. The hash posted is the opened source document's save hash (`useKeptDoc(path).doc.hash`), never a summary page's `file_hash`. The link is "See what changed" (`settled-changes.tsx`, the review module's commit comparison against `/api/settled-version`). Locked state comes from the loaded `DocView` (`docIsLocked`), falling back to the file-name rule only until it loads.
- **Plan page** (`trace/plan-extras.tsx`, `briefs-card.tsx`): between the heading and the summary, the pressure record (only when the plan has one), What it implements (one row per spec heading with its section's settle state) and Briefs.
- **Turn footer** (`chat/turn-footer.tsx`, `trace/impact-rows.tsx`): under each changed document, "Now out of step with what you settled" lists the settled documents now `revised`, `stub_changed` or `upstream_changed` and the plans covering a changed section, each once. Sessions keep writing files directly; the footer is the review surface, because a pre-acceptance changeset would need sessions that propose without writing. A stage sandbox cannot start a session, so only the unit tests cover it.
- **Tone**: one `--tone-warning` for revised, stub changed and upstream changed, `--tone-completed` for settled and a muted outline for draft (`web/src/plan/ui/DESIGN.md`).

## Coverage and Findings Pages

`/f/<f>/coverage` (`coverage-page.tsx`, `coverage-rows.tsx`, `coverage-model.ts`, `coverage-marks.tsx`; `maps.css` holds the width steps and imports the base `maps-columns.css`): the spec headings grouped by section, one aligned row each (heading, Covered by, Findings, state glyph and word), under four count tiles (All headings, Not covered, Changed since covered, Built) that filter (`aria-pressed`, named by their visible text, count then word, WCAG 2.5.3). A row expands (`aria-expanded`) to Why (the vision quote), How (Entry, Plan and Stage chains) and Findings. Keys: Up and Down move between rows, Enter opens; `OPEN_DIALOG` lives in `web/src/lib/open-dialog.ts`. A coverage chip or Covered-by link lands on `#section_NN` and the addressed row is scrolled into view.

`/f/<f>/findings` (`findings-page.tsx`, `findings-model.ts`, `findings-cards.tsx`, `findings-fold.tsx`, `ledger-hash.ts`, `trace-gate.tsx`; style `maps-findings.css`, `maps-findings-forms.css`): findings grouped under "Run of <short slug>" headings, newest run first (the run whose first finding is latest in the ledger), then Reviews. An open finding is a soft card with About pills (a plan stage reads `<plan> › <stage>`), the text (raw for HTML and Markdown, never rendered) and, while open, Plan this, Fold into entry (a radio picker with a suggested entry, entries whose plan has not started running, and a note for those left out) and Dismiss (reason required, the confirm disabled until one is typed; `dismissReason` mirrors the server's cleaning). A decided finding folds to one line. The ledger hash comes from `ledger-hash.ts`, fetched when a trace loads, so the 409 guard compares against the text the cards were drawn from. After a saved dismissal focus moves to the finding's heading. The Run page is the Plans overview (`/f/<f>/run` redirects), and the spine's last row in Product spec and in Plans leads to Coverage and to Findings ([spine](planner-feature-screens.md#spine)); the heading chips and the Run panel's Findings link also reach them, and the product overview draws no Coverage link of its own.

## Skill Duties

The authoring skills in `plan-plugin/skills/` and `skills/loom-plan-writer/SKILL.md` carry the duties: the metaplan skill writes a `Covers:` line naming the most specific headings and sets a folded finding's Status; the plan skill writes `Implements:` with heading anchors where a plan covers part of a section and an `Implements (stage:<id>):` line for each narrower stage; every authoring skill never writes a `Settled:` line and says so when it edits a settled document. A seed takes precedence over the Plan follow-ups opening target.
