# Subagent Hierarchy

> Fan-out vs coordinators vs teams; model mix

## Subagent Hierarchy + Ultracode Guidance (2026-06-12)

Loom teaches a 2-level subagent hierarchy (main agent → coordinator subagents → worker subagents) for large well-defined fan-out, and a per-stage `ultracode: bool` flag that licenses Workflow orchestration. The guidance is mirrored across multiple surfaces that MUST stay consistent.

**Capability facts:**

- Nested subagents are supported since Claude Code 2.1.172 (changelog: "Sub-agents can now spawn their own sub-agents (up to 5 levels deep)"); empirically confirmed 2026-06-12 on 2.1.175 (a subagent spawned a nested Explore agent, no flags needed). On older versions the Task tool is simply absent one level down; the coordinator does the work itself.
- The platform allows 5 levels; **loom caps trees at 2 by policy** (auditable file-exclusivity, bounded cost/failure blast radius), enforced via the WORKER PREAMBLE prose, not code.
- The `tools:` frontmatter in `agents/*.md` governs capability. As of the doctrine-surfaces stage (2026-09-19) NO agent type lists `Task`: `loom-software-engineer` and `loom-senior-software-engineer` are leaves. A coordinator is spawned as `general-purpose` with an explicit `model` override (`skills/loom-orchestration/SKILL.md` Rule 6, "2-level cap"), because an engineer agent type cannot fan out any more. When a change declares an agent a leaf, `rg -n 'coordinat|fan-out|spawn'` the WHOLE agent file: the first pass left "sonnet coordinators", a "Coordinator Turn Allowance" section and a codex "coordinators may spawn loom-codex-forwarder" bullet behind in `agents/loom-senior-software-engineer.md`, contradicting the new `tools:` line.
- **Model-inheritance trap:** a nested worker spawned WITHOUT an agent type defaults to the MAIN session model — on an `opus` stage that silently makes every worker opus. Hence "spawn workers BY AGENT TYPE" on every surface.
- **Ultracode licensing:** Claude Code's Workflow tool requires explicit opt-in; the documented trigger is the literal keyword `ultracode` in the session's prompt. Loom controls every spawned session's initial prompt, so `stage.ultracode` injects the keyword at spawn (`orchestrator/terminal/native/mod.rs`, `SessionType::Stage` prompt arm).
- **Ultracode fan-out is Claude-only.** The Workflow tool can only spawn Claude subagents — the codex lane (`gpt-5.6-terra` / `gpt-6-luna`) is not addressable from a Workflow script. On a stage licensed for both `ultracode` and codex, codex-tier work goes through normal `loom-codex-forwarder` Agent spawns outside the Workflow, never through the Workflow itself (the "## Ultracode Mode" block in `format/sections.rs` states this).
- **Plan-authoring preference:** one ultracode stage is preferred over three or more parallel sibling stages performing the same operation across disjoint file sets — fewer worktrees, fewer merges. The tradeoff is cost, roughly 15x the tokens of a single session with up to ~16 agents concurrent; full guidance lives in `/loom-plan-writer`.
- **The codex lane is a worker substitution, not a new level, and it splits into two tiers.** On stages listing codex in `implementers`, routine implementation may go through the `loom-codex-forwarder` shim to GPT-5.6 Terra (common implementation, integration tests) or GPT-6 Luna (boilerplate, scaffolding, simple unit tests), both at `xhigh` effort, instead of sonnet `loom-software-engineer`. It does NOT replace opus for mainstream architecture/algorithm work, fable for visual/UI design, a bug that survived a delegated fix attempt, or extremely challenging algorithmic design (no agent type pins fable — the model override is explicit at spawn), or `loom-advisor` for debugging. It is foreground-only (background fan-out is forbidden — [Codex Concurrency](../architecture/codex-concurrency.md)), and it never verifies: verification stays with the orchestrator.
- **The codex lane also requires the codex CLI and plugin to actually be installed**, independent of stage licensing. `loom run` preflights this at startup (`codex_lane_status()` / memoized `codex_lane_available()` in `loom/src/codex.rs`, mirroring the Remote Control capability/preflight/resolve shape) and prints an advisory warning — never a hard failure — when the CLI or the plugin's companion runtime (`~/.claude/plugins/cache/openai-codex/codex/*/scripts/codex-companion.mjs`) is missing. When unavailable, the stage signal's `## Codex Implementers` section switches to a fallback note: route terra-/luna-tier work to sonnet, and do not spawn `loom-codex-forwarder`.
- **Lanes are a PER-SUBAGENT choice, not a per-stage mode.** `implementers` is a list of licensed lanes; listing one makes it available, not mandatory. One stage — and one fan-out wave — may hold codex and sonnet workers side by side. File exclusivity is enforced ACROSS lanes: a codex worker and a sonnet worker writing one file is lost work exactly as two same-lane workers would be, so keep ONE file-ownership table covering every worker in every lane, with each row's lane noted.
- **One owned `loom subagents` wait, not deadlines (revised 2026-09-13: `--worker`-bound, superseding the earlier bare `--timeout`-only form).** Checking on subagents goes through the `loom subagents` CLI, never a hand-rolled poll loop. Spawn every worker first and capture each worker ID — the Claude agent ID from the spawn result, or the Codex unit ID assigned via `--unit-id` — then run exactly ONE `loom subagents watch --worker claude:<agent-id> --worker codex:<unit-id> --timeout 3600` (one `--worker` per worker; `--session` names only the Claude parent UUID, to disambiguate) through the Bash tool's `run_in_background`: it binds that worker set once, holds one lease for the parent session, prints one initial and one terminal record, then exits — the harness re-invokes the session when it exits, and no request is made while it waits. The bare `--timeout <secs>`-only form with no `--worker` is REJECTED (`loom/src/commands/subagents/mod.rs`). Do not re-arm a foreground watch every few minutes, and do not poll with `git status`, `wc -l`, `ls`, or similar. `loom subagents list`/`harvest` give a one-shot look at per-subagent state (`done`, `tool-wait`, `generating`, `unknown`) and remain one-shot diagnostics only, never a wait substitute. Exit codes: 0 every bound worker has fresh correlated success evidence; 2 the wait deadline passed (NOT proof any worker died); 3 a bound worker failed or was cancelled; 4 a wait for this parent session already exists (`AlreadyWaiting` same set, `Busy` different set); 5 worker identity or terminal evidence is unknown (never success). Three death-judgment cases, not one: (1) `done` but silent — harvest from disk and proceed immediately, a missing notification is not a missing result; (2) `tool-wait`/`generating` — genuinely alive, KEEP WAITING ON THE BACKGROUND WATCH (do not re-arm), slow is not dead; (3) idle past the budget with no transcript growth — the only case with positive evidence of death, `TaskStop` it, confirm it stopped, then RE-DELEGATE the remainder to a fresh subagent, never absorb the work into yourself (hard stop 6). `--timeout` (3600 normal) and per-stage `subagent_timeout_secs` (default 300) are DIFFERENT numbers for different purposes: `--timeout` is how long the one background watch itself blocks; `subagent_timeout_secs` is the advisory IDLE budget death is judged against — it only widens the cadence, it is never passed directly as `--timeout`. The "appears hung" warning stays advisory only ([concerns.md](../concerns.md)). Canonical text: `skills/loom-orchestration/SKILL.md` Rule 6, BLOCK-C, pinned by `tests_doctrine_waiting.rs` (`block_c_lives_in_the_orchestration_skill`, `block_c_absent_from_every_stable_prefix`, `block_c_pins_the_owned_wait_contract`); `CLAUDE.md.template` Rule 6 keeps a one-line pointer to the skill. **Named workers and stage-only scope (2026-09-19):** the watch binds inside a loom stage session; interactively it exits 5 with `LOOM_STAGE_ID is required`, so the harness completion notification is the only signal there. A harness-named id (`<name>@session-<hex>`) is accepted since commit `b84d6bc8`: its transcript is found by listing `subagents/` for `agent-a<name>-*.jsonl` (`wait/model.rs::resolve_claude_transcript`), and zero or several matches is an error, never a guess. Binaries older than that commit rejected the `@` form as `worker id is empty or unsafe`, and a name with no started worker reports `worker set does not resolve to one Claude parent UUID`. Take the id from one `loom subagents list` (format `a<name>-<hex>`) when in doubt, and rely on the completion notification for a named in-process worker the watch cannot resolve; do not re-arm it.

## Model Playbook: Orchestration Model Is Per Stage Type, Configurable (2026-07-28)

Every stage's main agent runs the model and reasoning effort configured for its stage type
(`models/stage/defaults.rs::default_model` / `default_reasoning_effort`): `standard`, `knowledge`,
and `integration-verify` default to opus, `knowledge-distill` to sonnet; default effort is
`high`, `medium`, `xhigh`, and `high` respectively. The operator can change either per stage
type via `[models]` in `~/.loom/config.toml` (user tier) or `<repo>/.loom/work/config.toml`
(project tier, resolved per key — see conventions/model-and-effort-config.md); a plan stage's
`model` / `reasoning_effort` field overrides both config tiers for that stage.

Savings come from **delegation, not downgrade**, and delegation is a cost decision (tokens times
model tier; BLOCK-B point 1 in `skills/loom-orchestration/SKILL.md`): the main agent makes a change
itself only when it is at most 20 lines in at most 2 files it has already read, needs no further
exploration and one command proves it (a fable main session delegates even those; the
`worktree-file-guard.sh` edit advisory warns past that size). Everything larger goes to subagents
spawned by agent type across five tiers — haiku (`model: haiku` on `loom-software-engineer`,
mechanical edits such as a rename), fable (visual/UI design, a bug that survived a
delegated fix attempt, extremely challenging algorithmic design; no agent type pins it, so the
model override is explicit at spawn), opus (`loom-senior-software-engineer`, mainstream architecture and algorithm
implementation), sonnet or GPT-5.6 Terra (`loom-software-engineer` or the `loom-codex-forwarder`
codex lane, common implementation and integration tests), and GPT-6 Luna (codex lane,
boilerplate, scaffolding, simple unit tests). The codex tiers are licensed only on stages listing
codex in `implementers`; elsewhere terra- and luna-tier work goes to sonnet. The codex tiers also
require the `codex` CLI and plugin to be installed; when either is missing, `loom run` warns at
startup (never aborts) and the same terra-/luna-to-sonnet fallback applies for the run — see
[Codex Plugin](../architecture/codex-plugin.md). A knowledge stage runs on its configured
default (opus at medium effort unless overridden) and delegates its code spot-reads to sonnet;
the two facts are easy to conflate.
