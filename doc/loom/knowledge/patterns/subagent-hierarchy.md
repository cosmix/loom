# Subagent Hierarchy

>

## Subagent Hierarchy + Ultracode Guidance

Loom teaches a 2-level subagent hierarchy (main agent → coordinator subagents → worker subagents) for large well-defined fan-out, and a per-stage `ultracode: bool` flag that licenses Workflow orchestration. The guidance is mirrored across multiple surfaces that MUST stay consistent.

**Capability facts:**

- Nested subagents are supported since Claude Code 2.1.172 (changelog: "Sub-agents can now spawn their own sub-agents (up to 5 levels deep)"); confirmed on 2.1.175 (a subagent spawned a nested Explore agent, no flags needed). On older versions the Task tool is absent one level down; the coordinator does the work itself.
- The platform allows 5 levels; **loom caps trees at 2 by policy** (auditable file-exclusivity, bounded cost/failure blast radius), enforced via the WORKER PREAMBLE prose, not code.
- The `tools:` frontmatter in `agents/*.md` governs capability. NO agent type lists `Task`: `loom-software-engineer` and `loom-senior-software-engineer` are leaves. Rule 6 (`skills/loom-orchestration/SKILL.md`, "2-level cap") says a coordinator is spawned as `general-purpose` with an explicit `model` override, because an engineer agent type cannot fan out; the spawn guard denies every `general-purpose` spawn inside a gated stage session, so the instruction cannot be followed there ([code-quality-and-hook-debt](../concerns/code-quality-and-hook-debt.md)). When a change declares an agent a leaf, `rg -n 'coordinat|fan-out|spawn'` the WHOLE agent file: coordinator prose left anywhere in it contradicts its `tools:` line.
- **Model-inheritance trap:** an untyped spawn defaults to the spawning session's model — on an `opus` session that silently makes every worker opus. Hence "spawn workers BY AGENT TYPE" on every surface. Inside a gated stage the spawn guard denies an untyped spawn; outside one it sets `model: sonnet` when the input names none ([hook-system.md](../architecture/hook-system.md#spawn-guard-untyped-spawns-loom-hooksspawn-guardsh)). [Mistake](../mistakes/plan-authoring.md).
- **Ultracode licensing:** Claude Code's Workflow tool requires explicit opt-in; the documented trigger is the literal keyword `ultracode` in the session's prompt. Loom controls every spawned session's initial prompt, so `stage.ultracode` injects the keyword at spawn (`orchestrator/terminal/native/launch.rs::initial_prompt`, the `SessionType::Stage` arm).
- **Ultracode fan-out is Claude-only.** The Workflow tool can only spawn Claude subagents — the codex lane (`gpt-6.1-terra` / `gpt-6.1-sol` / `gpt-6-luna`) is not addressable from a Workflow script. On a stage licensed for both `ultracode` and codex, codex-tier work goes through the stage's codex lane outside the Workflow (a `loom-codex-forwarder` Agent spawn on the Legacy lane, `loom subagents start --provider codex` from the main agent on the Native lane), never through the Workflow itself (the "## Ultracode Mode" block in `format/sections.rs` states this).
- **Plan-authoring preference:** one ultracode stage is preferred over three or more parallel sibling stages performing the same operation across disjoint file sets — fewer worktrees, fewer merges. The tradeoff is cost, roughly 15x the tokens of a single session with up to ~16 agents concurrent; full guidance lives in `/loom-plan-writer`.
- **The codex lane is a worker substitution, not a new level, and it has three model tiers and two backends.** On stages listing codex in `implementers`, straightforward, well-specified implementation (one concern, pinned interfaces, mechanical acceptance, no git, no `.loom/`) may go through the stage's lane, all at `xhigh` effort. The launch text is chosen by `CodexLane` (`codex_backend.rs::codex_lane`, `orchestrator/signals/format/codex.rs` and `codex_native.rs`): **Legacy** (`codex.backend = legacy`) is the `loom-codex-forwarder` shim; **Native** (`codex.backend = native`, the default) has the main agent run `loom subagents start --provider codex --unit-id <unit> --brief <absolute path> --model <tier> --effort <effort>` and no forwarder spawn ([native-codex-workers](../architecture/native-codex-workers.md)); **Unavailable(reason)** is the Claude-only fallback below. Native unit ids forbid dots (`^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`). The tiers: GPT-6.1 Terra for implementation, integration tests, boilerplate, scaffolding and simple unit tests; GPT-6.1 Sol for a substantial well-specified unit (about 4 to 6 file-sized changes) or a terra unit that failed once; GPT-6 Luna only when the user or plan asks. The lane is chosen per piece by its nature and by quota, never as a default or first choice, and the order of `implementers` carries no routing meaning. Claude keeps verification, review, planning, exploration, debugging and anything that iterates on failing tests. The lane does NOT replace opus for architecture, fable for visual/UI design or extremely challenging algorithmic design (no agent type pins fable — the model override is explicit at spawn), or `loom-advisor` for debugging. It is foreground-only (background fan-out is forbidden — [Codex Concurrency](../architecture/codex-concurrency.md)), and it never verifies: verification stays with the orchestrator.
- **The codex lane also requires its backend to actually be available**, independent of stage licensing. Legacy needs the codex CLI and the plugin's companion runtime; `loom run` preflights this at startup (`codex_lane_status()` / memoized `codex_lane_available()` in `loom/src/codex.rs`, mirroring the Remote Control capability/preflight/resolve shape) and prints an advisory warning — never a hard failure — when either is missing (`~/.claude/plugins/cache/openai-codex/codex/*/scripts/codex-companion.mjs`). Native needs the CLI plus `boundary::native_backend_qualified()` (Linux, a working bubblewrap pid namespace); a configured native backend that fails either never falls back to the legacy lane. When the lane is `Unavailable(reason)`, the stage signal's `## Codex Implementers` section switches to a fallback note that names the reason: route terra- and sol-tier work to sonnet and boilerplate, scaffolding and simple unit tests to haiku, and start no codex worker.
- **Lanes are a PER-SUBAGENT choice, not a per-stage mode.** `implementers` is a list of licensed lanes; listing one makes it available, not mandatory. One stage — and one fan-out wave — may hold codex and sonnet workers side by side. File exclusivity is enforced ACROSS lanes: a codex worker and a sonnet worker writing one file is lost work exactly as two same-lane workers would be, so keep ONE file-ownership table covering every worker in every lane, with each row's lane noted.
- **One owned `loom subagents` wait, not deadlines.** Checking on subagents goes through the `loom subagents` CLI, never a hand-rolled poll loop. Spawn every worker first and capture each worker ID — the Claude agent ID from the spawn result, or the Codex unit ID assigned via `--unit-id` (the Legacy forwarder) or `loom subagents start` (the Native lane) — then run exactly ONE `loom subagents watch --worker claude:<agent-id> --worker codex:<unit-id> --timeout 3600` (one `--worker` per worker; `--session` names only the Claude parent UUID, to disambiguate) through the Bash tool's `run_in_background`: it binds that worker set once, holds one lease for the parent session, prints one initial and one terminal record, then exits — the harness re-invokes the session when it exits, and no request is made while it waits. The bare `--timeout <secs>`-only form with no `--worker` is REJECTED (`loom/src/commands/subagents/mod.rs`). Do not re-arm a foreground watch every few minutes, and do not poll with `git status`, `wc -l`, `ls`, or similar. `loom subagents list`/`harvest` give a one-shot look at per-subagent state (`done`, `tool-wait`, `generating`, `unknown`) and remain one-shot diagnostics only, never a wait substitute. Exit codes: 0 every bound worker has fresh correlated success evidence; 2 the wait deadline passed (NOT proof any worker died); 3 a bound worker failed or was cancelled; 4 a wait for this parent session already exists (`AlreadyWaiting` same set, `Busy` different set); 5 worker identity or terminal evidence is unknown (never success); 6 a bound worker is hung (stalled past the budget). Three death-judgment cases, not one: (1) `done` but silent — harvest from disk and proceed immediately, a missing notification is not a missing result; (2) `tool-wait`/`generating` — genuinely alive, KEEP WAITING ON THE BACKGROUND WATCH (do not re-arm), slow is not dead; (3) idle past the budget with no transcript growth — the only case with positive evidence of death, `TaskStop` it, confirm it stopped, then RE-DELEGATE the remainder to a fresh subagent, never absorb the work into yourself (hard stop 6). `--timeout` (3600 normal) and per-stage `subagent_timeout_secs` (default 300) are DIFFERENT numbers for different purposes: `--timeout` is how long the one background watch itself blocks; `subagent_timeout_secs` is the advisory IDLE budget death is judged against — it only widens the cadence, it is never passed directly as `--timeout`. The "appears hung" warning stays advisory only ([concerns.md](../concerns.md)). Canonical text: `skills/loom-orchestration/SKILL.md` Rule 6, BLOCK-C, pinned by `tests_doctrine_waiting.rs` (`block_c_lives_in_the_orchestration_skill`, `block_c_absent_from_every_stable_prefix`, `block_c_pins_the_owned_wait_contract`); `CLAUDE.md.template` Rule 6 keeps a one-bullet summary of the wait and points at the skill. **Named workers and stage-only scope:** the watch binds inside a loom stage session; interactively it exits 5 with `LOOM_STAGE_ID is required`, so the harness completion notification is the only signal there. A harness-named id (`<name>@session-<hex>`) is accepted: its transcript is found by listing `subagents/` for `agent-a<name>-*.jsonl` (`wait/model.rs::resolve_claude_transcript`), and zero or several matches is an error, never a guess. A name with no started worker reports `worker set does not resolve to one Claude parent UUID`. Take the id from one `loom subagents list` (format `a<name>-<hex>`) when in doubt, and rely on the completion notification for a named in-process worker the watch cannot resolve; do not re-arm it.

## Model Playbook: Orchestration Model Is Per Stage Type, Configurable

Every stage's main agent runs the model and reasoning effort configured for its stage type
(`models/stage/defaults.rs::default_model` / `default_reasoning_effort`): `knowledge` and
`integration-verify` default to opus, `standard` and `knowledge-distill` to sonnet; default effort
is `high` (`standard`), `medium` (`knowledge`), `xhigh` (`integration-verify`) and `high`
(`knowledge-distill`). The operator can change either per stage
type via `[models]` in `~/.loom/config.toml` (user tier) or `<repo>/.loom/work/config.toml`
(project tier, resolved per key — see conventions/model-and-effort-config.md); a plan stage's
`model` / `reasoning_effort` field overrides both config tiers for that stage. The first-round
`loom-code-reviewer` (opus, high), the integration-verify session (opus, xhigh), contract writer
and merge sessions keep their configured defaults.

Savings come from **delegation, not downgrade**, and delegation is a cost decision (tokens times
model tier; BLOCK-B point 1 in `skills/loom-orchestration/SKILL.md`): the main agent makes a change
itself only when it is at most 20 lines in at most 2 files it has already read, needs no further
exploration and one command proves it (a fable main session delegates even those;
`_loom_main_edit_advisory` in `loom-hooks/post-tool-use.sh` gives a stage's main session a one-time
advisory past that size; see [hook-system.md](../architecture/hook-system.md)). Everything larger goes to subagents
spawned by agent type across these tiers (BLOCK-B point 3). The doctrine lives in
`skills/loom-orchestration/SKILL.md` Rule 7, `CLAUDE.md.template` Rule 7, `format/codex.rs`, the
agent files and the plan-writer skill; the README restates the tiers and effort.

- haiku (`loom-software-developer`, `agents/loom-software-developer.md`: `model: haiku`,
  `effort: high`, has the `Skill` tool and loads the skills its brief names): pieces that are
  extremely simple, or whose brief is highly detailed (files, exact change and acceptance
  stated). It takes no open decisions, bugs of unknown cause, concurrency, security-sensitive
  code or data-loss paths. `Explore` runs with `model: haiku` for locate-only sweeps (paths,
  symbols, call sites) and at its default sonnet when the answer needs behavior read.
- sonnet (`loom-software-engineer`): pieces that need exploration or the initial iteration on
  failing tests, or are too large to brief in that detail. A piece that seems to sit between
  sonnet and opus goes to sonnet. Fixes for review findings in code a cheaper tier wrote return to
  the tier that wrote the piece and escalate only on a failed fix.
- opus (`loom-senior-software-engineer`, agent-file `effort: medium`): architecture across
  modules, new algorithms, concurrency and distributed systems, security-sensitive code, and
  bugs of unknown cause. It implements its own work as a leaf. It takes no visual or CSS fixes,
  no mainstream feature code, and no fixes for review findings in code a cheaper tier wrote.
  Orchestrators pass no `effort` on a first attempt; a failed attempt is respawned at
  `effort: high` with every attempt and its evidence in the brief. `effort: xhigh` is no
  subagent setting; `loom-advisor`'s own frontmatter (`effort: xhigh`) is the one exception.
- fable: visual/UI design and extremely challenging algorithmic design; no agent type pins it,
  so the model override is explicit at spawn. Fable implements no bug fix.
- codex (`loom-codex-forwarder`, effort `xhigh`): terra, sol and luna as described under
  [Subagent Hierarchy](#subagent-hierarchy--ultracode-guidance); chosen per piece by its nature and
  by quota, never first or default.

Escalation on a failed attempt moves one tier: haiku to sonnet, sonnet to opus at medium, opus
at medium to opus at `effort: high`; codex terra to sol, then Claude at the tier the piece needs.
After an opus failure at high, `loom-advisor` (fable by default, a `model` the caller may
override, read-only) diagnoses and an opus implementer at `effort: high` applies the diagnosis;
that is rare.
The codex tiers are licensed only on stages listing codex in `implementers` and require the
`codex` CLI and plugin; without either, terra- and sol-tier work goes to sonnet and
boilerplate and simple unit tests to haiku, and `loom run` warns at startup (never aborts) — see
[Codex Plugin](../architecture/codex-plugin.md). Plan authors list codex on a standard stage
with straightforward, well-specified pieces and write `["claude"]` otherwise.

**Quota-aware routing.** A stage signal's `## Model Budget` section carries each provider's fresh
windows and at most one `Routing:` line: Claude under pressure sends codex-fit pieces to codex
(where licensed and available) and fully briefed pieces to haiku, codex under pressure sends them
to the matching Claude tier, and routing never moves a piece below the tier Rule 7 names or
overrides `implementers` ([signal-generation.md](../architecture/signal-generation.md#model-budget-section-formatbudgetrs)).
`loom usage --quota` prints the same section for plan authors.

**Reading by range.** A brief to an opus or fable worker names `file:line` ranges. Agents read a
plan file by range: its Overview, any Decisions section and their own stage's section.

**Frontend changes.** Implementers check for an existing message, toast, control, component,
string or helper before adding one; one event gets one message in one place; the project's own UI
conventions win. `loom-code-reviewer` and the review skill check the same, and every departure
from a convention is a finding whose `rule` cites the convention and where it is defined
(`agents/loom-code-reviewer.md`, `skills/loom-code-review/SKILL.md`, the two Claude implementer
agent files, `AGENTS.md.template`). `loom-senior-software-engineer` carries no frontend text.

**Measurement.** `loom usage` attributes every transcript to its stage and every subagent to its
requested model without a hook ledger ([usage-evidence.md](../architecture/usage-evidence.md#attribution-without-a-hook-ledger)),
which is how a misrouting is found ([mistake](../mistakes/plan-authoring.md)).

A knowledge stage runs on its configured default (opus at medium effort unless overridden) and
delegates its code spot-reads to sonnet; the two facts are easy to conflate.
