# Memory Relay Drain Gap

> loom-relay.sh misses memory:resolve; ticket-cap deadlock and recovery

## `loom-relay.sh` Never Recognizes `loom memory resolve`, So Its Tickets Can Deadlock a Sandboxed Session (2026-09-14)

**What happened:** inside a stage worktree, `loom memory resolve <id> --outcome ...` succeeds locally (prints `✓ Resolved ... as receipt ...` and a trailing `LOOM_RELAY_V1 kind=memory id=... sha256=... bytes=...` line) but the entry never actually lands in the daemon's memory journal — `loom memory pending` still lists it. Running 32 `resolve` calls in a row (piped through a script that redirected their stdout away) hard-deadlocked the session: every further `loom memory` write failed outright with `Error: this session already has 32 unconsumed relay tickets (limit 32); wait for the relay hook to drain them before retrying`, and nothing drained on its own.

**Why:** `loom` commands that must record something outside a sandboxed session's write reach (`.loom/work` in a worktree) leave a ticket file in `$LOOM_SCRATCH_DIR` and print one `LOOM_RELAY_V1 kind=<kind> id=<id> sha256=<hex> bytes=<n>` line as their last stdout line — but a ticket is only ever drained by `loom-hooks/loom-relay.sh`, the `PostToolUse:Bash` hook that runs OUTSIDE the sandbox after the Bash tool call ends. That hook computes which `RequestKind`s the Bash command's own TEXT is allowed to relay by tokenizing it and pattern-matching `sub:verb` pairs in `relay_kind_at()` — and its case statement lists `memory:note`, `memory:decision`, `memory:change`, `memory:question`, but **not `memory:resolve`**. So even though `loom memory resolve` writes a real `kind=memory` ticket and prints a real relay line, the hook computes an empty `--allowed-kinds` for that command text, and `loom hook relay`'s `admit()` refuses every such ticket with "this Bash call did not run the loom command that writes memory requests" — the ticket is kept (not consumed) for a future attempt, but nothing about running `resolve` again ever produces a DIFFERENT, allowed command text, so the backlog only grows until the 32-ticket cap locks out all further memory writes.

Piping a `resolve` call's stdout to a file (to keep noise out of context) makes this worse in an unrelated way: even for a KIND the hook does recognize (e.g. `memory:note`), the hook only sees `LOOM_RELAY_V1` if it is in the Bash tool call's own stdout/`tool_response`, unfiltered — redirecting it to a file hides the line from the hook entirely, so nothing gets relayed even for an otherwise-recognized command.

**Prevention:** never redirect a `loom memory`/other relay-eligible command's stdout away; run it standalone so the hook sees its relay line. For `loom memory resolve` specifically, this alone is not enough (the kind still isn't recognized) — see Recovery below. Batching many `resolve` calls with `&&`/`;` in one Bash command does NOT help either: the hook computes one shared `--allowed-kinds` for the whole compound command from whatever `loom memory <verb>` segments it can tokenize, but each ticket's `admit()` check still requires its own kind be in that set, and `resolve` never contributes one.

**Recovery (verified working, 2026-09-14):** an unconsumed `.req` ticket file in `$LOOM_SCRATCH_DIR` is immutable and self-describing (`{"v":1,"id":...,"kind":"memory",...}`); its announced `sha256`/`bytes` are just the hash and length of that exact file. Recompute them (`sha256sum` or equivalent) for every stuck ticket, build the `LOOM_RELAY_V1 kind=memory id=<id> sha256=<hash> bytes=<n>` lines yourself, `cat` them to real stdout in the SAME (unredirected, foreground) Bash call as one genuinely recognized command — `loom memory note --help` is ideal: it tokenizes as `memory:note` (so `relay_allowed_kinds` includes `memory`) but creates NO new ticket of its own (a `--help` invocation never writes one), so this recovery step never grows the backlog it is draining. The real hook (unsandboxed, so `caller_is_inside_session`'s process-tree check succeeds where a manual sandboxed `loom hook relay` invocation cannot — the stage sandbox's own PID namespace hides the host PID the session record was registered under, the same limitation documented in [`loom status` Marks the Caller's Own Executing Stage Orphaned](../architecture/execution-containment.md)) then relays every ticket whose reconstructed line matches a real file on disk — up to 16 per call (`MAX_PENDING_ENTRIES`); repeat for more. This is recovery of the session's OWN genuine tickets by their real on-disk hash, not forgery: it cannot relay a ticket that was not already legitimately written.

**A `loom hook relay` bug filed here for a future stage to fix:** add `memory:resolve` (and audit for any other `loom memory`/`loom stage`/`loom handoff` subcommand missing from `relay_kind_at()`'s case statement in `loom-hooks/loom-relay.sh`) so a sandboxed session's own natural, unredirected `resolve` calls drain without hand-reconstructing relay lines.
