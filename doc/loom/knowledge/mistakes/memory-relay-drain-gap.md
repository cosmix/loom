# Memory Relay Drain Gap

> Relay tickets leaked for good when their line never reached the hook; ticket-cap deadlock, the sweep that fixes it, and recovery

## A Ticket Whose Line Never Reached the Hook Was Leaked Forever (2026-09-18)

**What happened:** knowledge-distill stages in several projects deadlocked with `this session already has 32 unconsumed relay tickets (limit 32); wait for the relay hook to drain them`, AFTER the `memory:resolve` fix below was installed. Some resolves had landed; the rest never did, and waiting changed nothing.

**Why:** a ticket was relayed only when its own `LOOM_RELAY_V1` line appeared in the output of the Bash call that wrote it, and nothing ever retried one that was missed. Four ordinary shapes hide the line: `RelayLine::extract` stops at `MAX_LINES_PER_CALL` = 16, so a loop of 40 resolves in one call relayed 16 and leaked 24 without a word; stdout redirected or piped through `tail` (which Rule 14 encourages); the command run from a script file (`bash resolve-all.sh` derives no allowed kinds); a background call. The daemon only logs a `tracing::warn!` for tickets older than 60 s, which the agent never sees, and the quota error's "wait for the relay hook to drain them" described something that could not happen. The `memory:resolve` gap below was one instance of this class, fixed as if it were the whole defect.

**Prevention:** a queue whose only drain is tied to one event needs a second drain, or a miss is permanent. When fixing a leak, ask what else can produce the same leftover state and test that state directly: the regression test writes 17 tickets in one call and asserts on the inbox entries and the `.req` files left on disk (`commands/hook/relay/tests_sweep.rs`), never on reply strings. An error message that tells an agent to wait must name something that actually happens.

**Fix:** `loom hook relay` sweeps leftover `memory` and `telemetry` tickets on every call whose command text allows that kind (`commands/hook/relay/sweep.rs`; control kinds are never swept, see [Session Requests Travel Through a Hook-Written Inbox](../architecture/security-and-isolation.md)). `loom-relay.sh`'s fast path lets a payload containing ` memory ` reach the helper even with no relay line. The quota error now names the recovery: run `loom memory note --help` in the foreground with its output unfiltered. The knowledge-distill signal's receipt step tells the curator to keep `resolve` output unfiltered. Sessions still running a pre-fix binary or hook need the manual Recovery below.

## `loom-relay.sh` Never Recognizes `loom memory resolve`, So Its Tickets Can Deadlock a Sandboxed Session (2026-09-14)

**What happened:** inside a stage worktree, `loom memory resolve <id> --outcome ...` succeeds locally (prints `✓ Resolved ... as receipt ...` and a trailing `LOOM_RELAY_V1 kind=memory id=... sha256=... bytes=...` line) but the entry never actually lands in the daemon's memory journal — `loom memory pending` still lists it. Running 32 `resolve` calls in a row (piped through a script that redirected their stdout away) hard-deadlocked the session: every further `loom memory` write failed outright with `Error: this session already has 32 unconsumed relay tickets (limit 32); wait for the relay hook to drain them before retrying`, and nothing drained on its own.

**Why:** `loom` commands that must record something outside a sandboxed session's write reach (`.loom/work` in a worktree) leave a ticket file in `$LOOM_SCRATCH_DIR` and print one `LOOM_RELAY_V1 kind=<kind> id=<id> sha256=<hex> bytes=<n>` line as their last stdout line — but a ticket is only ever drained by `loom-hooks/loom-relay.sh`, the `PostToolUse:Bash` hook that runs OUTSIDE the sandbox after the Bash tool call ends. That hook computes which `RequestKind`s the Bash command's own TEXT is allowed to relay by tokenizing it and pattern-matching `sub:verb` pairs in `relay_kind_at()` — and its case statement listed `memory:note`, `memory:decision`, `memory:change`, `memory:question`, but **not `memory:resolve`**. So even though `loom memory resolve` writes a real `kind=memory` ticket and prints a real relay line, the hook computed an empty `--allowed-kinds` for that command text, and `loom hook relay`'s `admit()` refused every such ticket with "this Bash call did not run the loom command that writes memory requests" — the ticket was kept (not consumed) for a future attempt, but nothing about running `resolve` again ever produced a DIFFERENT, allowed command text, so the backlog only grew until the 32-ticket cap locked out all further memory writes.

Piping a `resolve` call's stdout to a file (to keep noise out of context) makes this worse in an unrelated way: even for a KIND the hook does recognize (e.g. `memory:note`), the hook only sees `LOOM_RELAY_V1` if it is in the Bash tool call's own stdout/`tool_response`, unfiltered — redirecting it to a file hides the line from the hook entirely, so nothing gets relayed even for an otherwise-recognized command.

**Prevention:** never redirect a `loom memory`/other relay-eligible command's stdout away; run it standalone so the hook sees its relay line. Batching many `resolve` calls with `&&`/`;` in one Bash command does NOT help either: the hook computes one shared `--allowed-kinds` for the whole compound command from whatever `loom memory <verb>` segments it can tokenize, and each ticket's `admit()` check still requires its own kind be in that set.

**Recovery (verified working, 2026-09-14, still needed for sessions stuck under the old hook):** an unconsumed `.req` ticket file in `$LOOM_SCRATCH_DIR` is immutable and self-describing (`{"v":1,"id":...,"kind":"memory",...}`); its announced `sha256`/`bytes` are just the hash and length of that exact file. Recompute them (`sha256sum` or equivalent) for every stuck ticket, build the `LOOM_RELAY_V1 kind=memory id=<id> sha256=<hash> bytes=<n>` lines yourself, `cat` them to real stdout in the SAME (unredirected, foreground) Bash call as one genuinely recognized command — `loom memory note --help` is ideal: it tokenizes as `memory:note` (so `relay_allowed_kinds` includes `memory`) but creates NO new ticket of its own (a `--help` invocation never writes one), so this recovery step never grows the backlog it is draining. The real hook (unsandboxed, so `caller_is_inside_session`'s process-tree check succeeds where a manual sandboxed `loom hook relay` invocation cannot — the stage sandbox's own PID namespace hides the host PID the session record was registered under, the same limitation documented in [`loom status` Marks the Caller's Own Executing Stage Orphaned](../architecture/execution-containment.md)) then relays every ticket whose reconstructed line matches a real file on disk — up to 16 per call (`MAX_LINES_PER_CALL`, `loom/src/relay/mod.rs:32`; an earlier version of this entry wrongly named `MAX_PENDING_ENTRIES`, which is the 128-entry inbox capacity); repeat for more. This is recovery of the session's OWN genuine tickets by their real on-disk hash, not forgery: it cannot relay a ticket that was not already legitimately written.

**Fixed 2026-09-16:** `memory:resolve` was added to `relay_kind_at()`'s case statement in `loom-hooks/loom-relay.sh`, pinned by a new `expect memory 'loom memory resolve ...'` (and a companion `expect '' 'loom memory pending'`, confirming that read-only verb still relays nothing) in `loom-hooks/tests/loom-relay-kinds.sh`. An audit of every `context.emit(RequestKind::...)` call site confirmed the other emitted kinds — `block`, `dispute-criteria`, `merge --resolved`, `adjudicate`, `handoff`, and `knowledge context`'s telemetry — were already recognized by the case statement; `resolve` was the only gap. Sessions launched before their installed hook copy is refreshed with this fix still run the old `loom-relay.sh` and will keep hitting the deadlock described above — the Recovery procedure remains the only way to drain tickets already stuck under those sessions.
