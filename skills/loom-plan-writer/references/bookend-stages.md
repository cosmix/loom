# Bookend Stages — full text

Read when: writing the knowledge-bootstrap, integration-verify or knowledge-distill stage and the short forms in `SKILL.md` Section 3 leave a question open.

## knowledge-bootstrap (first)

Captures codebase understanding before implementation. `stage_type: knowledge`, defaults to opus at medium effort (`SKILL.md` Section 4) — may write `doc/loom/knowledge/**`. It should: run `loom knowledge sync` to rebuild the derived retrieval artifacts and perform any one-time flat-to-hierarchical upgrade; the knowledge directory scaffold and source graph are created automatically at `loom init` and at run startup, so this stage exists to write CONTENT, never to create the directory or seed it from static analysis; then spawn parallel `Explore` subagents for entry-points, patterns, conventions, each returning `loom knowledge update <file> "..."` commands (tier routing below). Review existing `mistakes.md` before completing. **Use `loom knowledge` CLI, never Write/Edit on knowledge files.** Its acceptance is `loom knowledge check --strict --baseline doc/loom/knowledge/check-baseline.txt`: it fails only on structural issues the committed baseline does not record (a missing baseline file counts as empty), so it goes red when the stage breaks the tree and cannot pass while doing nothing about a regression.

**Skip ONLY if** `doc/loom/knowledge/` is already populated with real content (the tier-1 files carry `##` sections describing this codebase, not just the scaffold) AND `loom knowledge sync` runs clean.

## Knowledge tier routing (bootstrap & distill)

`doc/loom/knowledge/` may be FLAT (tier-1 files only) or HIERARCHICAL (tier-1 summaries plus tier-2 topic files under per-category directories, e.g. `architecture/signal-generation.md`, `mistakes/phantom-merges.md`). Detect which with ONE predicate: hierarchical iff `doc/loom/knowledge/INDEX.md` exists at the root. Route every finding by size: something that fits in roughly 40 lines or fewer goes INLINE into the tier-1 file (`architecture.md`, `entry-points.md`, `patterns.md`, `conventions.md`, `mistakes.md`, `stack.md`, `concerns.md`); anything larger goes to `loom knowledge update <category>/<slug>`, leaving a 2-4 line summary plus a link in the tier-1 file. `INDEX.md` regenerates automatically on every knowledge write; there is no index command or final index step. Every file except `mistakes.md` and `mistakes/*` states current truth only — no dated headings, no "was"/"used to" narrative, no change log; a lesson worth keeping goes into a mistakes topic instead, and the current-state entry links to it.

## integration-verify (second-to-last)

> ⚠️ **TESTS PASSING ≠ FEATURE WORKING.** We have had MANY cases where all tests pass, code compiles, but the feature is NEVER WIRED UP. This stage is the gate that catches it.

`stage_type: integration-verify`, defaults to opus at xhigh effort (`SKILL.md` Section 4) — the highest-effort default of any stage type, since it is the last quality gate. It runs AFTER all feature stages and must:

- **Build & test** with ZERO tolerance — fix ALL warnings/lints/failures, nothing is "pre-existing."
- **Code review** — spawn parallel `loom-code-reviewer` subagents (security via `Skill(skill="loom-skills", args="loom-security-audit")`; architecture; test coverage); fix all findings with an engineer agent (reviewer is read-only). (The 6-dimension mini adversarial review is already injected at the signal layer — don't restate it. To require specific dimensions, use plan-level `code_review` config, not prose.)
- **Functional verification** — prove the feature is WIRED IN and usable: CLI command registered/callable, API endpoint mounted/reachable, UI component rendered; run a smoke test of the primary use case end-to-end.
- Record discoveries to `loom memory` for knowledge-distill to curate. Do NOT do knowledge/docs curation here.

In a `version: 2` plan (`v2-contracts.md` Section 5):

- **Full test command** — its `acceptance` lists a whole-suite run an adapter recognises (`cargo test`, `cargo test --all-targets`); `loom plan verify` rejects the stage without one.
- **Never defers a finding** — every finding of a recorded review round, and every finding an earlier stage deferred to it, is fixed and closed by a later round or disputed with `loom stage dispute-findings`. An adjudicator cannot defer a finding from integration-verify.
- **Reviewer suggestions** — its signal lists every pending `suggestion` memory entry of the plan's stages. It weighs each one and implements, defers or ignores it, resolves each one it implements with `loom memory resolve <id> --outcome implemented --reason <what changed>`, and leaves the rest pending for knowledge-distill.

## knowledge-distill (last)

`stage_type: knowledge-distill`, defaults to sonnet at high effort (`SKILL.md` Section 4) — the ONE bookend whose default model is NOT opus: distillation is a linear read-synthesize-write pass, run **single-agent with NO subagents**. Curates all stage memories into permanent knowledge and updates user-facing docs. Reads the plan, `loom memory show --all`, and current knowledge, starting from `loom memory pending --group` (pending entries grouped as `corrections`, `mistakes`, `decisions`, `other`); FIRST applies every `stale-knowledge:` memory in place with `loom knowledge replace-section <file> "<heading>" "<body>"` (never `update`, which appends the fix below the stale text) and, in the same pass, rewrites any history it finds outside `mistakes.md`/`mistakes/*` — dated headings, "was"/"used to" language, a change log — into current-state text, moving the lesson to a mistakes topic when it carries one; then synthesizes mistakes as actionable prevention rules, patterns, decisions, conventions via `loom knowledge update`, following the same tier-routing rule as knowledge-bootstrap (above); `INDEX.md` regenerates on each knowledge write, so then run `loom review` to prune stale entries; updates README/CONTRIBUTING for changed behavior (only relevant sections). Every Note/Decision/Question entry taken into knowledge gets a receipt: `loom memory resolve <id> --outcome promoted --target <file#heading>` right after the write that used it (`merged` into an existing section, `discarded --reason "..."` for a duplicate or wrong entry, `deferred --reason "..."` when it needs evidence not available now); finish with `loom memory pending --strict` and resolve whatever it lists. In a `version: 2` plan that includes the reviewer suggestions nobody implemented (`loom memory pending --group` lists them under `suggestions`): record each one in knowledge, in `concerns` or the topic it belongs to, then resolve it `promoted` or `merged` with `--target`, or `discarded` with `--reason`. When the stage removed structural issues, its last step is `loom knowledge check --write-baseline doc/loom/knowledge/check-baseline.txt`, which ratchets the baseline down (the check prints a "baseline can be tightened" line when it can). Add `loom knowledge check --strict --baseline doc/loom/knowledge/check-baseline.txt` AND `loom memory pending --strict` to this stage's acceptance — both are acceptance-safe: the former validates the knowledge tree's structure and never opens the context store, the latter reads `.loom/work/memory` only. Never add a heading-presence grep on a tier-1 knowledge file: every tier-1 file carries `##` headings from the scaffold on, so the criterion passes at base and cannot fail (logged: 119 such slots across 38 plans). **Context discipline (200k window):** the memories are compact summaries — lean on them and keep code spot-reads narrow; do NOT fan out to subagents. **Skip ONLY if** the plan produces no new knowledge worth preserving (rare).
